## 0. 规则层级与本文件定位

上游文档已经确认以下边界：目标具有独立状态；正式目标的创建、修改和状态变更必须经确认中心；目标不能仅因所有关联行动完成而自动完成；正式对象由 Local Core 写入，并保留来源、版本、关键变更记录和索引更新任务。技术架构总览同时明确，**目标状态机的完整允许和禁止转移此前尚未确定**。

因此，本文件用两类标记避免把不同确定性混为一谈：

- **【上游已确认】**：继承既有详细需求，实施时必须满足。
- **【本轮采用】**：为补齐状态机而给出的 v1 推荐规则；在产品/技术负责人确认前，是本文件的工作基线，不应倒写为上游已确认事实。
- **【待决策】**：不阻塞状态机核心闭环，但不得伪装成已冻结实现细节。

除非后文特别说明，“状态”均指正式目标的 `当前状态`；目标候选的“待确认、已确认、已取消、已过期”等候选生命周期，仍由《v1-确认中心》定义，不能与目标状态混用。

## 1. 关键问题 → 推荐答案

### 问题 1：目标创建后默认处于什么状态？

**推荐答案：**【本轮采用】正式目标默认以“规划中”创建。用户在同一次确认中明确表达“已经开始推进”时，可以创建为“进行中”；不得由模型、卡片默认勾选或关联行动的状态推断为“进行中”。

原因是“已被记录”为正式目标，不等于“已经开始执行”。这样也避免一条输入中的目标候选在确认后被静默视为当前执行承诺。

### 问题 2：行动全部完成，目标是否应自动完成？

**推荐答案：**【上游已确认】不应自动完成。

行动完成只能构成目标可能达成的依据。系统可以在摘要、提醒或复盘中提示“关联行动均已完成，是否确认目标已完成”，并生成目标状态变更候选；只有用户明确确认且 Local Core 写入成功后，目标才变为“已完成”。

### 问题 3：截止时间过去后，目标是否自动进入“已过期”？

**推荐答案：**【本轮采用】不自动改变正式目标状态。系统可本地计算“已到截止时间且未完成”的观察结果，用于提示、RAG 状态标记和复盘，但必须由用户确认“已过期”、延期后继续、暂停或放弃中的一个正式处理结果。

“已过期”表达的是目标在原时效下不再有效的正式结论；它不等于设备时钟跨过截止时间这一事实。没有截止时间的目标不能仅因长期未更新而自动过期。

### 问题 4：已完成、已放弃是否绝对不可恢复？

**推荐答案：**【本轮采用】二者在日常流转中均为结束状态，不自动恢复；用户可以通过确认中心明确恢复。

- 从“已完成”恢复，表示目标完成判断被撤销或目标出现后续阶段；应说明恢复原因，并转为“规划中”或“进行中”。
- 从“已放弃”恢复，表示用户重新决定追求原目标；应转为“规划中”或“进行中”。

这不是对历史状态的静默覆盖，而是保留新的变更记录。若恢复语义已经是一个实质不同的目标，产品可建议新建目标；是否强制新建属于后续交互决策。

### 问题 5：暂停和放弃如何区分？

**推荐答案：**【本轮采用】“已暂停”是明确暂缓，仍可能恢复；“已放弃”是明确不再追求。两者都不等于用户暂时没有操作，也不应由未完成行动或未读提醒自动触发。

### 问题 6：目标状态是否可以被行动、处境模型、RAG 或后台任务直接改写？

**推荐答案：**【上游已确认】不可以。它们可以提供依据、生成候选、展示提示或登记索引/刷新任务；任何正式目标状态变更仍须经确认中心，并由 Local Core 完成校验与事务写入。

## 2. 状态定义

### 2.1 初步状态集合

【上游已确认】v1 目标初步状态固定为以下六种：

```text
规划中
进行中
已完成
已暂停
已放弃
已过期
```

本轮不新增“待确认”“已删除”“已归档”等目标状态：

- “待确认”属于目标候选，不是正式 `Goal` 的状态。
- 删除状态、归档状态按《v1-原始记录与结构化存储》与删除规则独立保存，不能用“已放弃”替代删除。
- 截止时间是否已到是时间观察字段，不替代“已过期”的正式状态。

### 2.2 各状态的业务含义

| 状态 | 定义 | 日常建议中的定位 | 退出该状态的方式 |
|---|---|---|---|
| 规划中 | 用户认可目标存在，但尚未明确开始持续推进。可继续拆分、澄清、安排行动。 | 可作为当前意图和规划依据；不应被表述为已在执行。 | 用户确认开始、暂停、放弃、完成或对到期结果作出处理。 |
| 进行中 | 用户明确正在推进该目标。允许关联行动和进展追踪。 | 当前建议和行动排序的正常依据。 | 用户确认完成、暂停、放弃、已过期，或恢复为规划中。 |
| 已完成 | 用户确认目标已达成。可保留结果、依据与复盘价值。 | 默认不作为当前待推进目标；可供历史说明、复盘和相似建议参考。 | 仅用户确认恢复为规划中或进行中，或通过符合条件的撤销恢复前状态。 |
| 已暂停 | 用户明确暂缓，未来仍可能继续。 | 默认不产生主动执行建议；可在复盘、用户主动查询或恢复候选中出现。 | 用户确认恢复为规划中/进行中，或确认完成、放弃、已过期。 |
| 已放弃 | 用户明确不再追求该目标。 | 不作为正向当前目标；可在复盘中解释取舍与未完成原因。 | 仅用户确认恢复为规划中或进行中，或通过符合条件的撤销恢复前状态。 |
| 已过期 | 目标有截止时间，原时效已过且用户确认不以原计划继续。它不表示完成，也不等于删除。 | 不作为当前有效目标；可在复盘、历史查询和重新规划时使用。 | 用户确认重新规划、恢复推进、暂停、放弃或确认完成。 |

### 2.3 与截止时间的分离

【本轮采用】目标保留可选截止时间，并额外以派生观察表达“是否已到期”：

```text
当前状态：进行中
截止时间：2026 年 9 月 10 日
时间观察：未到期 / 已到期
```

当系统时间超过截止时间时，只更新或计算“已到期”观察，不直接将 `当前状态` 改成“已过期”。用户确认后的“已过期”才是正式状态变更。具体日期精度、时区、宽限期和通知频率仍由后续提醒子需求确定。

## 3. 允许/禁止转移

### 3.1 状态转移总图

【本轮采用】所有箭头均表示“用户在确认中心明确确认，且 Local Core 校验成功后”的正式转移；不存在由模型、RAG、行动完成、定时任务或客户端本地状态直接触发的箭头。

```text
创建目标
  └─ 默认 → 规划中
             ├─→ 进行中
             ├─→ 已暂停
             ├─→ 已放弃
             ├─→ 已完成
             └─→ 已过期（仅目标有截止时间且已到期）

进行中 ──────→ 已完成 / 已暂停 / 已放弃 / 已过期 / 规划中
已暂停 ──────→ 规划中 / 进行中 / 已完成 / 已放弃 / 已过期
已过期 ──────→ 规划中 / 进行中 / 已暂停 / 已放弃 / 已完成
已完成 ──────→ 规划中 / 进行中（仅明确恢复或符合撤销条件）
已放弃 ──────→ 规划中 / 进行中（仅明确恢复或符合撤销条件）
```

### 3.2 允许转移表

| 当前状态 | 允许转为 | 关键校验或说明 |
|---|---|---|
| 不存在（新建） | 规划中 | 默认新建状态。 |
| 不存在（新建） | 进行中 | 同次确认中用户明确表明已开始；不靠模型推断。 |
| 规划中 | 进行中、已暂停、已放弃、已完成、已过期 | 转“已过期”要求存在截止时间且已到期；转“已完成”须用户确认目标已达成。 |
| 进行中 | 规划中、已暂停、已放弃、已完成、已过期 | 回到“规划中”表示停止当前推进、重新规划，不是删除行动历史。 |
| 已暂停 | 规划中、进行中、已放弃、已完成、已过期 | 恢复为“进行中”需要用户明确开始继续。 |
| 已过期 | 规划中、进行中、已暂停、已放弃、已完成 | 恢复推进时，如原截止时间不再适用，应在同一候选中显式保留、修改或清空截止时间。 |
| 已完成 | 规划中、进行中 | 仅“恢复/重新开启”确认或合法撤销；必须保留原完成记录。 |
| 已放弃 | 规划中、进行中 | 仅“恢复继续”确认或合法撤销；不得因新行动自动恢复。 |

### 3.3 禁止转移与禁止推断

以下规则【本轮采用】为 v1 的硬禁止项：

1. **不自动完成。** 任意数量的关联行动完成、行动结果良好、建议被采纳、处境模型显示进展，均不得直接把目标改为“已完成”。
2. **不自动过期。** 截止时间到达、设备补偿执行、每日摘要或未处理提醒均不得直接把目标改为“已过期”。
3. **不从候选直达正式状态。** 目标候选被展示、默认选中、编辑草稿、暂不处理或被 RAG 召回，不产生正式 `Goal`，也不改变任何现有目标。
4. **不以关联关系推断状态。** 行动新增、删除、取消、延期、搁置或与多个目标关联，不能单独推断目标开始、暂停、放弃、完成或恢复。
5. **不静默覆盖结束状态。** 已完成、已放弃目标不能因新输入、复盘推断、处境刷新或再次被检索而自动变回进行中。
6. **不以状态替代删除。** 已放弃和已过期目标仍是可追溯的正式对象；物理删除仍需独立删除流程及二次确认。
7. **不跳过确认中心。** 客户端离线草稿、后台任务重试、导入后分析或模型重试均不得绕开确认中心直接写入状态。

### 3.4 对“已过期”转移的补充

【本轮采用】仅允许具有明确截止时间且该时间已过的目标转为“已过期”。若用户想继续追求该目标，应优先生成“修改截止时间并转为规划中/进行中”的候选，而不是把“已过期”当成可继续执行的当前状态。

若用户在到期后确认目标实际上已达成，允许直接确认“已完成”；不得要求用户先标为“已过期”再完成。

## 4. 确认和事务边界

### 4.1 进入确认中心的操作

【上游已确认】正式目标创建、目标内容修改、目标截止时间修改和目标状态变更必须进入确认中心。本轮将状态机操作统一为以下候选意图：

```text
创建目标（含初始状态）
修改目标内容或说明
修改截止时间
目标状态变更
恢复已完成/已放弃目标
```

一次输入可产生多个独立候选；用户可逐项修改、取消或暂不处理。候选的“暂不处理”仍保持待确认，不代表取消，也不得改变正式目标。

### 4.2 确认命令的最小校验边界

【本轮采用】任何目标状态确认命令至少应由 Local Core 校验：

```text
确认操作幂等标识（confirmation_operation_id）
候选标识及候选版本
目标标识（新建时为空）
目标当前版本（更新时必填）
原状态（更新时必填）
目标状态
目标截止时间及其本次变更意图
用户明确的确认、修改后确认或取消动作
来源原始记录 / 分析结果 / 确认批次引用
必要的高风险确认标记
```

状态转移必须同时满足：候选仍可处理、目标未删除、版本未冲突、转移存在于第 3 节、`已过期`的时间前提成立，以及所需的高风险确认已完成。客户端显示的状态和按钮不构成最终校验依据。

### 4.3 单次确认命令的事务

【上游已确认】单次确认命令不得留下部分正式写入；同一确认批次可跨多次用户操作部分处理，但每次实际提交必须原子完成。

【本轮采用】确认一个或多个目标候选时，事务边界为：

```text
校验候选、版本和状态转移
→ 创建或更新 Goal
→ 写入状态前后值和变更原因
→ 写入来源关系、用户确认操作和关键变更记录
→ 登记目标相关索引更新/处境刷新任务
→ 标记本次被提交候选为已确认或已修改后确认
→ 提交事务
```

任一正式对象、来源关系、关键变更记录或任务登记写入失败，应整体回滚：目标状态不变，候选保持可重试的待确认状态，并可使用同一 `confirmation_operation_id` 安全重试。

索引的**实际执行**可在事务后异步进行。正式目标写入已经成功而索引执行失败时，确认结果仍为成功；索引任务进入失败待重试，结构化查询仍以正式对象为准。

### 4.4 多对象确认时的边界

一个确认命令可以同时创建目标、创建关联行动或修改多个目标，但本文件不允许用行动事务结果推断目标完成：

```text
创建目标 + 创建行动：可以在同一命令中原子写入
行动完成 + 目标完成：必须是两个明确候选；只确认行动时，目标保持原状态
复盘建议调整目标 + 调整行动：可以同次提交，但每项均须独立明确列入命令
```

## 5. 与行动/提醒/复盘的松耦合关系

### 5.1 与行动的关系

【上游已确认】一个目标可关联多个行动；一个行动也可关联多个目标或独立存在。目标和行动各自拥有状态与生命周期。

【本轮采用】二者只通过关联关系、进展依据和确认候选协作：

- 行动完成可作为“目标可能完成”的依据，但不能更新目标状态。
- 目标完成、暂停、放弃或过期，不自动完成、取消、搁置、删除或延期关联行动。
- 若目标进入结束状态，系统可把仍未完成的关联行动列为待处理影响，供用户分别决定保留、改关联、延期、搁置或取消；这些仍是行动自己的确认操作。
- 新行动可以关联历史目标用于记录或复盘，但日常建议不应把已完成、已放弃或已过期目标当作当前执行目标来自动生成行动。
- 目标恢复为进行中不自动恢复先前搁置或取消的行动；需分别确认行动状态或创建新行动。

### 5.2 与提醒的关系

【上游已确认】v1 后台任务可以生成每日行动摘要、明确截止时间提醒、逾期行动集中提醒、每周目标复盘和待确认内容提醒；后台任务必须幂等，且不得重复产生正式副作用。

【本轮采用】本状态机只向提醒能力提供状态和截止时间，不定义具体提醒排程：

- 每日摘要可展示进行中目标、规划中目标、截止时间观察、关联行动和待确认目标候选。
- 到期观察可以产生“请处理该目标”的提示或状态变更候选，不直接写入“已过期”。
- 已暂停、已完成、已放弃和已过期目标默认不触发持续的目标推进提醒；用户主动恢复或后续提醒子需求可另行定义例外。
- 一条提醒中的“完成、延期、搁置”等快捷操作若涉及目标状态，必须转化为确认中心命令，不能仅因通知点击而直接写入。
- 重复调度、补偿执行或通知展示失败不改变目标状态。

### 5.3 与每日摘要和每周复盘的关系

【上游已确认】每日摘要使用当前处境，每周复盘可使用当前和历史处境；二者都不能自动写回正式对象，所提出的正式变更须进入确认中心。

【本轮采用】

- 每日摘要只消费目标状态：展示当前重点、可能到期、关联行动进度和待确认事项；不重新定义目标状态，也不把摘要结论保存为状态变更。
- 每周复盘可根据完成/未完成行动、延期、到期观察、计划与实际差异和用户反馈，提出完成、暂停、放弃、过期、恢复或重新规划的**候选**。
- 复盘页面可以清楚区分“事实依据”“系统建议”“待确认状态变更”和“已确认正式状态”。用户跳过复盘、没有阅读复盘或关闭页面均不代表确认。

### 5.4 与 RAG 和处境模型的关系

【上游已确认】RAG 只提供依据，不直接产生正式事实或状态变更；处境模型是可追溯、可版本化的聚合快照，不是新的事实来源，且不得自动修改正式目标。

【本轮采用】状态机向 RAG 和处境模型提供可解释输入，而不是接受其回写：

| 目标状态 | 普通建议 / 当前处境中的使用 | 历史复盘 / 用户主动查询中的使用 |
|---|---|---|
| 进行中 | 正常作为当前重要目标和行动排序依据。 | 可正常使用。 |
| 规划中 | 可作为当前规划意图，但应表明尚未开始。 | 可正常使用。 |
| 已暂停 | 默认不作为当前行动硬约束；可提示暂停背景。 | 可使用并保留状态。 |
| 已完成 | 默认不作为待推进目标；可作为结果和经验依据。 | 可使用。 |
| 已放弃 | 不作为正向当前目标；可作为取舍、失败模式和历史依据。 | 可使用。 |
| 已过期 | 不作为当前有效目标；不得把旧时效当作当前约束。 | 可使用，并标记为历史状态。 |

待确认目标候选如被受限召回，必须保留“待确认”标记，不能被处境模型写成当前目标、不能作为硬限制，也不能触发任何状态转移。目标状态变更成功后可触发处境刷新候选或索引任务；其失败不回滚已成功的目标确认事务。

## 6. 异常/幂等/撤销

### 6.1 幂等与并发

【上游已确认】确认操作、正式对象和后台任务均需要幂等与版本控制；已提交事务不得重复应用，未提交事务不得留下半成品。

【本轮采用】目标状态命令遵循以下规则：

1. 同一个 `confirmation_operation_id` 重复提交：若第一次已成功，返回同一成功结果与变更记录，不再写入第二次状态历史。
2. 同一个命令第一次未提交成功：候选维持待确认，可用原幂等标识重试。
3. 提交时的目标版本与当前版本不一致：拒绝本次变更，不影响同批次未提交候选；客户端重新加载当前状态后，必要时生成新候选。
4. 两个候选都试图基于同一版本改变目标状态：只有先成功提交者生效，后者进入版本冲突处理，不进行“后写覆盖前写”。
5. 状态本身相同不等于可跳过记录：若用户请求重复操作而幂等键不同，Local Core 应按业务语义拒绝无意义的重复状态变更或提示当前已经是该状态，而不是重复制造变更历史。

### 6.2 常见异常处理

| 异常 | 处理结果 |
|---|---|
| 候选已取消、已过期或不存在 | 不写入目标，返回明确原因。 |
| 目标已删除或归档策略不允许修改 | 不写入目标，要求先按删除/归档规则处理。 |
| 转移不在允许表中 | 不写入目标，显示当前状态与允许处理方式。 |
| 目标无截止时间或尚未到期，却请求转“已过期” | 拒绝状态变更；可建议修改截止时间、暂停或放弃。 |
| 行动全部完成但用户未确认 | 保持目标原状态，仅允许生成“可能完成”候选。 |
| 后台任务发现到期 | 只记录/展示到期观察或候选，不写入“已过期”。 |
| 确认事务写入失败 | 整体回滚；候选可重试；不产生部分状态历史。 |
| 索引或处境刷新异步失败 | 正式状态保留；相应任务失败待重试；提示检索可能稍后更新。 |
| 进程在提交前崩溃 | 数据库事务回滚，目标保持旧状态。 |
| 进程在提交后、响应前崩溃 | 依赖幂等标识返回既有成功结果，不重复变更。 |

### 6.3 撤销

【上游已确认】撤销是新的反向操作，不删除原确认记录；须校验仍可逆、没有后续冲突，并使用独立幂等标识。

【本轮采用】目标状态撤销的最小规则：

```text
原状态变更已成功
→ 用户请求撤销
→ 校验目标当前版本仍等于原操作产生的版本
→ 校验没有无法安全恢复的后续状态或外部副作用冲突
→ 写入反向状态变更、撤销操作和关键变更记录
→ 触发索引/处境刷新任务
```

- 新建目标的撤销按确认中心规则转为软删除、取消或归档，不物理删除原确认和来源记录。
- “进行中 → 已完成”“进行中 → 已暂停”等状态变更，在没有后续修改时可恢复为原状态。
- 已完成或已放弃后的恢复，也应作为新的确认操作；若只是撤销刚刚发生且无冲突的状态变更，可使用上述撤销路径。
- 已彻底删除的数据、已有后续版本的目标、已被后续对象合并替代而无法确定恢复结果的情况，不承诺自动撤销；应提示用户生成新的目标修改候选。
- 已发出的通知、用户已经执行的外部行动等外部副作用无法回收；撤销只回退本地正式目标状态。

## 7. 已确认与待决策

### 7.1 已确认的上游边界

以下内容不是本文件新作的决定，而是已形成详细子需求中已经确认的约束：

1. 正式目标具有独立状态；初步状态集合为“规划中、进行中、已完成、已暂停、已放弃、已过期”。
2. 正式目标创建和修改进入确认中心；状态变更属于正式业务变更，不能自动写入。
3. 目标不能仅因所有关联行动完成而自动完成，须用户直接确认或由助手提出后用户确认。
4. 模型只产生候选和建议；候选在确认前不等于正式目标，且不得直接参与正式业务写入。
5. Local Core 负责最终校验、事务、来源关系、版本、关键变更记录、幂等和失败恢复。
6. 单次确认命令原子提交；索引实际更新失败不推翻已成功的正式对象写入。
7. RAG、处境模型、每日摘要、提醒和周复盘不得自动修改正式目标；涉及正式变更时进入确认中心。
8. 删除、归档和彻底删除独立于正常业务状态；彻底删除需要二次确认。

### 7.2 本轮采用的详细规则

本文件为了让 v1 可实现而补齐、但此前未完全确定的规则包括：

1. 正式目标默认以“规划中”创建；只有用户同次明确表达时可初始为“进行中”。
2. 到期是派生观察；“已过期”必须由用户确认，且目标有明确截止时间并已到期。
3. 第 3 节的允许/禁止转移表；“已完成”“已放弃”在日常流转中结束，但可经明确确认恢复。
4. 目标与行动、提醒、复盘、RAG、处境模型之间仅松耦合：提供依据和候选，不产生直接回写。
5. 状态命令的最低版本校验、幂等处理、事务内容和撤销前提。
6. 各状态在普通建议和历史复盘中的默认使用方式。

这些规则应在产品/技术负责人确认后，再升级为“已确认的 v1 详细子需求基线”。在此之前，开发实现应将它们集中在目标状态机模块和可配置/可迁移的数据模型边界中，避免分散硬编码到摘要、提醒、RAG 或客户端。

### 7.3 仍待决策，不由本文件冻结

1. 目标是否支持层级、父子目标、进度百分比、里程碑、优先级和标签。
2. 目标截止时间的日期/时间精度、时区、宽限期、修改权限提示及具体逾期文案。
3. 已完成或已放弃目标恢复时，何时建议新建目标、何时允许原目标恢复的具体交互。
4. “规划中 → 已完成”在产品界面是否需要额外确认文案或完成结果字段。
5. 目标状态变更原因、完成结果、放弃原因、暂停原因的必填/选填策略和保留期限。
6. 目标归档的触发条件、归档后是否允许恢复、归档与状态筛选的页面交互。
7. 目标级提醒是否单独存在；目前只继承行动提醒与摘要/复盘的上游边界。
8. 待确认目标候选的有效期、再提醒间隔和批量确认界面细节。
9. 数据库枚举、状态历史表字段、索引字段、接口命名和迁移策略等实现细节。

## 8. 验收标准

### 8.1 状态与创建

- 用户确认创建一个普通目标后，系统创建正式目标，默认状态为“规划中”，并保留候选、来源、确认操作和变更记录关联。
- 用户在同次确认中明确“已经开始推进”时，目标可以创建为“进行中”；仅模型推断、默认勾选或关联行动存在时不得创建为“进行中”。
- 系统中不存在把“待确认”“已删除”“已归档”混入目标六种业务状态的实现。
- 没有明确截止时间的目标不能被系统或用户命令直接转为“已过期”。

### 8.2 转移与禁止项

- 第 3.2 节列出的每个允许转移，在候选、用户明确确认和 Local Core 校验成功后可以完成，并写入状态前后值。
- 不在第 3.2 节的转移被拒绝，不写入目标、不影响其他候选，并向用户说明原因。
- 关联行动全部完成时，目标仍保持原状态；系统至多产生“确认目标已完成”的候选。
- 截止时间过去、每日摘要生成、后台补偿、重复提醒或处境模型刷新时，目标不自动变为“已过期”。
- 已完成、已放弃目标不会因为新输入、RAG 召回、新行动或复盘推断而自动恢复。
- 目标状态变化不会自动修改关联行动的状态、截止时间、删除状态或提醒状态。

### 8.3 确认、事务与幂等

- 正式目标创建、内容/截止时间修改、状态变更和恢复均通过确认中心；展示卡片、默认全选、编辑草稿、暂不处理和关闭页面均不构成确认。
- 单次提交中任一目标写入、来源关系、关键变更记录或任务登记失败时，所有本次提交的目标状态均回滚，候选保持可重试。
- 同一 `confirmation_operation_id` 的重复提交只产生一次目标状态变更和一次关键变更记录。
- 并发提交基于旧版本时，后提交者被识别为版本冲突，不覆盖已成功的新状态。
- 正式状态已成功而索引或处境刷新任务实际失败时，目标状态保持成功，任务可重试，结构化查询可立即读到新状态。

### 8.4 与行动、提醒、复盘、RAG 和处境模型

- 每日摘要能读取目标正式状态和到期观察，但不能写入目标状态。
- 每周复盘能基于历史与当前依据生成目标变更候选；用户未提交确认前，正式目标不变。
- 已暂停、已完成、已放弃和已过期目标不会被普通建议误表述为当前待推进目标；历史复盘或用户主动查询时保留其历史状态。
- 待确认目标候选即使被受限检索，也带有待确认标记，不能被处境模型当作当前正式目标，不能触发状态变更。
- 目标状态变更触发的处境刷新只产生快照/候选或任务，不回写目标；处境模型也不能反向改写目标。

### 8.5 异常与撤销

- 候选无效、候选过期、目标删除、版本冲突、状态转移不允许或高风险确认缺失时，不产生部分状态变更。
- “已过期”状态候选在提交时重新校验截止时间；到期条件不成立时被拒绝。
- 对刚发生且无后续冲突的状态变更执行撤销后，系统新增反向变更记录并恢复原状态，不删除原确认记录。
- 对已有后续修改、已彻底删除或无法安全恢复的状态变更，系统拒绝自动撤销并引导用户生成新的确认候选。
- 进程在提交前或提交后异常退出时，分别不会留下半成品或重复应用同一状态转移。
