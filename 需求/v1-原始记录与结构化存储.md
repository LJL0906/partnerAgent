# v1 原始记录与结构化存储

> 状态：已确认的 v1 详细子需求基线
>
> 基线日期：2026 年 9 月 3 日
>
> 上游架构：[`v1-技术架构总览.md`](./v1-技术架构总览.md)
>
> 适用范围：个人助手 v1.0 的原始记录、分析结果、候选项、正式结构化对象、来源关系和派生索引。

## 1. 文档目的

本文件回答一个核心问题：

```text
用户输入和模型分析结果，如何在本地被可靠保存、确认、追溯、检索和导出？
```

本文件不决定具体数据库产品、客户端框架、模型接入框架或 RAG 框架，只定义它们必须遵守的数据边界。

本文件的设计原则是：

```text
原始内容不可被分析结果替代
分析结果不可被候选项替代
候选项不可被正式对象替代
正式对象不可被检索索引替代
所有派生数据都必须能够回指来源
```

## 2. 关键问题与默认答案

### 问题 1：什么是一条原始记录？

**推荐答案：** 每次用户确认发送的内容形成一条原始记录。

这里的“发送”是指用户已经确认内容可以提交给助手分析，而不是录音完成、转写完成或附件选中完成。

因此：

```text
用户确认发送文字
→ 形成一条原始记录

用户确认语音转写
→ 转写文本作为一条原始记录的正文输入
→ 原始音频作为该记录的附件（如果保留）

用户选择附件但尚未提交
→ 不形成正式原始记录

用户取消或修改语音转写后重新确认
→ 以最终确认内容形成原始记录
```

### 问题 2：聊天消息和原始记录是否是同一个对象？

**推荐答案：** 不是。二者分层保存。

```text
聊天会话
├── 用户消息引用原始记录
├── 助手回复
├── 结构化分析结果引用
└── 界面交互信息

原始记录
├── 用户确认发送的原始内容
├── 附件
├── 创建时间
├── 来源和设备信息
└── 生命周期状态
```

聊天会话服务于即时交互上下文；原始记录服务于长期保存、追溯、RAG 和导出。

### 问题 3：语音转写在用户确认前保存在哪里？

**推荐答案：** 作为客户端或本地核心的临时输入，不进入正式原始记录和长期数据索引。

确认前可以临时保存：

- 音频临时文件；
- 语音识别临时文本；
- 用户编辑中的文本；
- 转写错误或重试状态。

确认前不得：

- 调用内容分析模型；
- 提取事实、目标、行动或记忆；
- 创建正式原始记录；
- 写入长期记忆；
- 创建或修改行动状态；
- 进入正式 RAG 索引。

用户确认后，临时输入要么转化为正式原始记录，要么按取消规则清理。

### 问题 4：附件和原始记录是什么关系？

**推荐答案：** 附件是原始记录的从属内容，不单独取代原始记录。

```text
原始记录
├── 正文：文字或确认后的语音转写
├── 附件：图片、网页链接、文件、原始音频
└── 附件解析结果（可选、异步）
```

附件必须先保存原始内容，再尝试解析。解析失败只能改变解析任务状态，不能删除或覆盖原始附件。

### 问题 5：一条输入包含多个目标和行动时如何保存？

**推荐答案：** 一条原始记录对应一份分析结果，分析结果内部包含多个独立候选项。

```text
一条原始记录
→ 一次分析运行
→ 一份结构化分析结果
→ 多个候选项
→ 用户逐项修改或取消
→ 一次确认
→ 分别创建正式对象
```

不能为了方便建模而把一次输入拆成多条互不关联的原始记录。原始输入的完整上下文必须保持可追溯。

### 问题 6：事实和长期记忆如何区分？

**推荐答案：** 事实是分析结果，长期记忆是经过确认、允许未来持续使用的正式对象。

```text
原始记录
→ 提取事实
→ 用户确认记忆候选
→ 保存长期记忆
```

事实可以被保存和检索，但不自动升级为长期记忆。长期记忆必须关联事实或原始记录来源，并保存确认状态、可信程度和生命周期。

### 问题 7：正式对象由谁创建？

**推荐答案：** 只有本地核心服务可以创建或修改正式目标、行动、长期记忆、决策等对象，且必须以用户确认命令为前提。

模型只能产生：

```text
分析结果
候选项
建议
待确认内容
```

客户端只能提交用户意图，不能直接写入数据库或索引。

### 问题 8：删除原始记录后，正式对象是否跟着删除？

**推荐答案：** 不自动删除。

```text
删除原始记录
→ 原始正文不再参与普通检索
→ 已确认目标、行动、记忆和决策继续保留
→ 来源关系保留为“原始记录已删除”
```

这样既符合已确认产品规则，也避免用户删除一条记录时意外丢失已经确认的行动和长期记忆。

### 问题 9：结构化数据和索引谁是权威？

**推荐答案：** 结构化数据是权威来源，检索索引是可重建的派生数据。

```text
结构化对象发生变化
→ 提交事务
→ 更新对象状态
→ 标记索引更新任务
→ 索引成功更新或进入补偿队列
```

索引丢失、损坏或过期时，可以依据结构化数据和原始记录重建，不依赖索引反向恢复业务事实。

### 问题 10：是否采用完整事件溯源？

**推荐答案：** v1 不采用完整事件溯源，但保存必要的操作历史和版本关系。

推荐形态：

```text
当前结构化对象
+ 来源关系
+ 关键变更历史
+ 软删除状态
+ 版本号
```

v1 不为每个字段变化都建立可重放事件流，不提前引入事件总线和复杂事件溯源。对记忆过期、目标截止时间修改、行动状态变化、删除和恢复等关键操作保留变更记录即可。

## 3. 数据总体分层

### 3.1 原始内容层

保存用户确认发送的原始内容和原始附件：

```text
用户文字
确认后的语音转写
原始音频（若 v1 具体规则确认保留）
图片
网页链接
上传文件
```

原始内容层的要求：

- 尽量保留用户确认发送时的完整内容。
- 不用模型摘要替代原文。
- 不因附件解析失败而丢失附件。
- 允许后续重新分析。
- 保留原始记录与附件的关联。
- 删除时进入明确生命周期，不由客户端直接物理删除。

### 3.2 分析结果层

保存对一次原始记录执行的分析结果：

```text
内容摘要
事实候选
问题候选
目标候选
行动候选
截止时间候选
现实限制候选
长期记忆候选
建议
模型分析状态
```

分析结果层记录模型对原始记录的解释，但不等于用户已经认可这些解释。

### 3.3 候选和待确认层

候选项从分析结果中独立出来，拥有自己的确认状态：

```text
待确认
已确认
已取消
已修改后确认
已过期
```

推荐把一次需要用户处理的候选集合保存为一个确认批次：

```text
确认批次
├── 来源原始记录
├── 来源分析结果
├── 多个候选项
├── 当前展示版本
├── 用户处理时间
└── 确认结果
```

这样可以支持：

- 默认全部选中；
- 逐项取消；
- 逐项修改；
- 一次确认多个不同类型的候选；
- 用户稍后从待确认列表继续处理。

### 3.4 正式结构化对象层

保存确认后的业务对象：

```text
事实
目标
行动
长期记忆
决策
行动结果
建议及采纳记录
建议效果
处境模型版本
提醒
```

正式对象必须具备稳定标识、创建时间、更新时间、当前状态和来源关系。

### 3.5 派生索引层

保存用于检索和召回的派生内容：

```text
原始记录索引
事实索引
长期记忆索引
目标索引
行动及结果索引
决策和复盘索引
处境模型索引
```

索引内容必须携带状态和来源信息。索引不是新的事实来源，不能脱离权威对象独立存在。

## 4. 核心数据对象

以下是 v1 建议的逻辑对象，不代表具体数据库表名。

### 4.1 ChatSession：聊天会话

用途：承载一次或一组连续的交互上下文。

建议包含：

```text
会话标识
会话标题（可选）
创建时间
最后活动时间
归档状态
删除状态
```

边界：

- 一个会话可以包含多条用户消息和助手回复。
- 会话不是长期事实的唯一来源。
- 删除或归档会话不能自动删除原始记录和正式对象。
- 后台任务可以生成独立会话消息，也可以挂载到系统任务会话；具体 UI 方式后续确定。

### 4.2 OriginalRecord：原始记录

用途：保存每次用户确认发送的内容，是长期保存和追溯的核心对象。

建议包含：

```text
原始记录标识
所属聊天会话标识（可选）
记录类型：文字 / 语音转写 / 混合附件
正文内容
创建时间
用户确认发送时间
来源设备标识（本地设备范围内）
原始内容状态
删除状态
归档状态
```

规则：

- 正文必须是用户确认发送的版本。
- 用户修改结构化分析结果不改写原始正文。
- 原始记录可以没有附件。
- 一条原始记录可以有多个附件。
- 原始记录可以产生多次分析运行，但保留每次分析的关系。
- 原始记录被删除后，正文不可进入普通 RAG 原文检索。

### 4.3 Attachment：附件

用途：保存原始附件及其元数据。

建议包含：

```text
附件标识
所属原始记录标识
附件类别：图片 / 网页链接 / 文件 / 音频
原始文件或链接引用
展示名称
媒体类型（如果可得）
文件大小（如果可得）
内容哈希（如果可得）
保存时间
解析状态
删除状态
```

规则：

- 原始附件先保存，再执行解析。
- 附件解析结果不能覆盖原始附件。
- 同一附件可以有多个解析尝试，但只保留一个当前解析状态。
- v1 的具体格式、大小限制和是否保留原始音频仍由附件子需求确定。
- 物理路径不发送给外部模型，也不作为用户可见来源信息。

### 4.4 AnalysisRun：分析运行

用途：记录一次对原始记录或后台任务上下文的结构化分析。

建议包含：

```text
分析运行标识
来源原始记录标识（可选）
任务类型
开始时间
结束时间
分析状态：排队中 / 执行中 / 成功 / 失败 / 部分成功
使用模型标识
推理等级标识
是否调用个人记忆
是否检测到敏感信息
是否发生模型切换
错误摘要
结果引用
```

规则：

- 分析运行是技术执行记录，不等于模型调用详细日志。
- 不在这里保存完整模型输入上下文和原始返回内容作为普通日志。
- 模型失败时保留失败状态和可展示的简要错误。
- 重试可以产生同一分析任务下的多个尝试记录，但最终结果必须能回指最终成功或最终失败状态。
- 分析失败不删除原始记录。

### 4.5 StructuredAnalysis：结构化分析结果

用途：保存一次分析运行输出的结构化解释。

建议包含：

```text
分析结果标识
所属分析运行标识
所属原始记录标识
内容摘要
事实集合
问题集合
目标候选集合
行动候选集合
截止时间候选集合
现实限制候选集合
长期记忆候选集合
建议集合
生成时间
结果版本
```

规则：

- 一条原始记录对应一次分析运行时，通常产生一份结构化分析结果。
- 同一原始记录重新分析时，保留不同分析结果之间的版本关系。
- 新分析结果不能静默覆盖已确认的正式对象。
- 分析结果中的候选项必须可逐项处理。
- 普通闲聊可以只保存摘要或普通回复，不强制生成结构化卡片。

### 4.6 CandidateItem：候选项

用途：保存待用户确认的目标、行动、记忆、事实、限制或其他建议。

建议包含：

```text
候选项标识
所属确认批次标识
所属分析结果标识
候选类型
候选内容
模型置信度（如果有）
是否敏感
建议影响说明
确认状态
用户修改后的内容（如果有）
创建时间
处理时间
```

规则：

- 每个候选项独立保存确认状态。
- 默认展示为选中，但默认选中不等于已确认。
- 用户取消候选项后不创建正式对象。
- 用户修改后，以修改后的内容创建正式对象，不额外保存错误的中间识别版本。
- 候选项被拒绝后允许未来重新提出，但必须重新基于新的上下文生成。
- 候选项不能绕过确认直接进入正式对象层。

### 4.7 ConfirmationBatch：确认批次

用途：把一次结构化分析中需要用户处理的候选项组成一个统一确认单元。

建议包含：

```text
确认批次标识
来源原始记录标识
来源分析结果标识
候选项集合
批次状态：待处理 / 部分处理 / 已确认 / 已取消 / 已过期
首次展示时间
最后处理时间
```

规则：

- 一次确认可以同时保存目标、创建行动和保存长期记忆。
- 候选项可以逐项取消或修改。
- 批次确认必须是原子操作：确认的候选全部成功写入，或整体失败并保留待处理状态。
- 具体确认卡片交互由《v1-确认中心》定义。

### 4.8 Fact：事实

用途：保存从原始记录或其他来源提取出的陈述，不自动升级为长期记忆。

建议包含：

```text
事实标识
事实内容
来源关系
首次出现时间
最后确认或观察时间
可信程度
事实来源类型：用户明确表达 / 助手抽取 / 外部材料
事实状态：抽取 / 可参考 / 过期 / 有争议 / 已删除
是否进入长期记忆
敏感标记
```

规则：

- 事实必须有来源。
- 用户明确表达和助手抽取必须区分保存。
- 事实抽取结果可以自动保存为普通分析或事实记录，不要求像长期记忆一样逐条确认。
- 未经用户确认的抽取事实不能标记为用户确认事实，重要建议使用时必须携带可信程度和来源状态。
- 事实冲突时保留来源和状态，不直接覆盖历史。
- 事实不能因为被保存或被检索就自动升级为长期记忆；升级仍必须经过用户确认。

### 4.9 Goal：目标

用途：保存用户确认的目标及其进展。

建议包含：

```text
目标标识
目标内容
目标说明
截止时间（可选）
当前状态
关联行动关系
来源关系
创建时间
更新时间
归档状态
删除状态
```

规则：

- 一个目标可以包含多个行动。
- 目标需要独立状态机。
- 目标不能因为所有关联行动完成而自动完成，必须由用户直接确认或经助手提出后由用户确认。
- 目标状态的完整允许和禁止转移在《v1-目标状态机》中定义。

### 4.10 Action：行动

用途：保存用户确认后可以执行和追踪的细粒度行动。

建议包含：

```text
行动标识
行动内容
行动说明
所属或关联目标关系
截止时间（可选）
提醒配置引用（可选）
当前状态
创建时间
更新时间
开始时间（可选）
完成时间（可选）
延期信息（可选）
搁置信息（可选）
取消信息（可选）
来源关系
归档状态
删除状态
```

规则：

- 行动可以独立存在，也可以关联一个或多个目标。
- 创建行动必须经过用户确认。
- 修改行动状态必须经过用户确认。
- 助手识别到可能完成时，只能提出确认，不能自动标记完成。
- 行动完成后可以保存执行结果。
- 行动状态的完整允许和禁止转移在《v1-行动状态机》中定义。

### 4.11 ActionResult：行动结果

用途：保存行动完成或中断后的实际结果，供复盘和未来建议使用。

建议包含：

```text
行动结果标识
关联行动标识
结果内容
结果类型：完成 / 中断 / 取消 / 其他
实际花费时间（可选）
发生时间
来源关系
用户确认状态
```

规则：

- 行动完成后，助手可以自动提取执行结果，但正式结果仍要有明确来源。
- 没有结果内容时允许为空。
- 行动结果不反向覆盖行动原始内容。
- 周复盘可以引用行动结果，但不在每次完成后强制打断用户复盘。

### 4.12 Memory：长期记忆

用途：保存用户确认、允许未来持续用于个人理解的内容。

建议包含：

```text
记忆标识
记忆内容
记忆类型
来源关系集合
创建时间
最后确认时间
可信程度
是否用户明确表达
是否助手推断
当前状态：有效 / 过期 / 有争议 / 已删除
确认状态
是否敏感
```

第一期类型包括：

```text
个人基本信息
长期偏好
长期目标
现实限制
重要经历
能力与资源
价值观和判断标准
决策经验
```

规则：

- 保存长期记忆必须经过用户确认。
- 敏感长期记忆可以保存到本地，但对外模型使用前必须脱敏。
- 新记忆与旧记忆冲突时，旧记忆标记过期或不再适用，新记忆作为新版本保存。
- 复杂记忆合并不自动执行；相似记忆保留多个来源，合并需要用户确认。
- 普通建议只使用当前有效记忆，历史复盘允许使用过期记忆。

### 4.13 Decision：决策记录

用途：记录重要选择及其后续验证，支持决策复盘。

建议包含：

```text
决策标识
决策内容
当时目标
可选方案
选择理由
当时限制条件
预期结果
计划验证时间
实际结果
复盘结论
来源关系
创建时间
更新时间
状态
```

规则：

- 助手可以提出建立决策记录的建议。
- 正式保存需要用户确认。
- 决策记录的完整复盘字段可以为空。
- 决策记录可以关联目标、行动、记忆和原始记录。

### 4.14 Suggestion：建议及采纳记录

用途：区分建议提出、用户采纳、执行和效果评价。

建议包含：

```text
建议标识
建议内容
推荐行动
备选行动
建议原因
依据关系集合
关联目标或行动
状态：已提出 / 已采纳 / 未采纳 / 已转行动 / 已失效
用户反馈
效果评价：有效 / 部分有效 / 无效 / 无法判断
创建时间
更新时间
```

规则：

```text
建议生成
→ 用户采纳或创建行动
→ 用户开始执行
→ 行动完成或中断
→ 保存结果
→ 周复盘判断效果
```

建议本身不是行动。采纳建议时，仍然需要经过创建行动的确认规则。

### 4.15 ContextSnapshot：个人处境模型版本

用途：保存由正式数据对象聚合形成的当前状态快照。

建议包含：

```text
处境版本标识
当前重要目标
进行中的目标
行动及状态
截止时间
已确认现实限制
当前问题
最近重要变化
风险和阻碍
最近重要决策
来源关系集合
生成时间
用户确认时间
版本状态：候选 / 当前 / 历史 / 已作废
```

规则：

- 处境模型是聚合快照，不是新的事实来源。
- 输入没有影响当前处境时不生成新版本。
- 有影响时先生成候选版本；需要作为重要决策依据时由用户确认。
- 当前版本用于日常建议，历史版本用于复盘和解释过去决策。
- 处境模型的重要判断必须关联正式对象或原始来源。

### 4.16 支撑对象

以下对象不直接代表用户业务意图，但用于支撑本地隔离、交互追踪、异步处理、索引一致性和重要操作解释。

#### 4.16.1 LocalDataSpace：本地数据空间

用途：表示一台设备上的独立个人数据边界。

建议包含：

```text
本地数据空间标识
设备实例标识
创建时间
本地数据版本
```

规则：

- v1 每台设备独立拥有一个本地数据空间。
- 本地数据空间不是云端账号，也不是多设备同步主库。
- 手机和电脑可以使用相同的逻辑模型，但互不自动同步。
- 未来服务器化时可以把本地数据空间作为迁移和同步边界，v1 不实现同步。

#### 4.16.2 SessionMessage：会话消息

用途：保存聊天界面中的一条用户消息或助手回复，并连接交互上下文与长期数据。

建议包含：

```text
消息标识
所属聊天会话标识
消息角色：用户 / 助手 / 系统
关联原始记录标识（用户消息可有）
关联分析结果标识（助手消息可有）
消息正文或展示内容
消息顺序
创建时间
消息状态
```

规则：

- 用户消息和助手回复必须区分。
- 用户消息可以引用一条原始记录；助手回复不能直接成为用户事实来源。
- 消息顺序只服务聊天展示，不代替原始记录的发生时间。
- 删除会话消息不能自动删除原始记录或正式对象。

#### 4.16.3 AttachmentParseResult：附件解析结果

用途：保存对原始附件进行解析后的派生结果。

建议包含：

```text
解析结果标识
所属附件标识
解析尝试编号
解析类型
解析状态：排队中 / 执行中 / 成功 / 失败
提取文本或结构化结果（如果有）
错误摘要（如果失败）
创建时间
完成时间
```

规则：

- 解析结果是附件的派生数据，不覆盖原始附件。
- 同一附件可以有多次解析尝试，但需要标记当前采用的结果。
- v1 即使解析失败，也必须保留附件和失败状态。
- 解析结果是否参与 RAG 取决于解析成功、来源可追溯和当前生命周期状态。

#### 4.16.4 UserConfirmationAction：用户确认操作

用途：保存用户对候选项或重要变更执行的确认、修改、取消和撤销动作。

建议包含：

```text
确认操作标识
所属确认批次标识
关联候选项标识
操作类型：确认 / 修改后确认 / 取消 / 撤销
用户提交内容（如果有）
操作时间
客户端来源
幂等键
```

规则：

- 默认选中、展开查看和界面点击不等于正式确认；只有明确提交确认才形成确认操作。
- 确认操作必须能回指候选项和确认批次。
- 重要操作的撤销需要通过新的反向操作记录完成，不直接删除原操作历史。
- 确认操作不保存完整模型上下文，只保存完成业务审计所需的最小内容。

#### 4.16.5 BackgroundJob：后台任务

用途：保存异步分析、附件解析、摘要、提醒、复盘和索引更新任务的持久化状态。

建议包含：

```text
任务标识
任务类型
关联对象类型和标识
计划执行时间
实际开始时间
实际完成时间
任务状态：排队中 / 执行中 / 成功 / 失败 / 取消
重试次数
最近错误
幂等键
结果引用
创建时间
更新时间
```

规则：

- 任务记录用于崩溃恢复、重试、补偿和幂等判断。
- 任务失败不能自动删除输入、附件或正式对象。
- 每日摘要、提醒和每周复盘必须通过幂等键限制重复副作用。
- 任务记录不保存完整模型上下文；需要展示的结果应引用分析结果、建议或提醒对象。

#### 4.16.6 IndexUpdateJob：索引更新任务

用途：保存正式对象或原始记录变更后，更新、删除或重建派生索引的任务。

建议包含：

```text
索引任务标识
关联对象类型和标识
关联对象版本
操作类型：新增 / 更新 / 删除 / 重建
任务状态：待更新 / 更新中 / 已完成 / 失败待重试
重试次数
最近错误
幂等键
创建时间
完成时间
```

规则：

- 正式对象事务成功时必须同时登记索引更新任务。
- 索引更新失败不回滚正式对象写入。
- 索引任务必须带对象版本，旧任务不能覆盖新版本索引。
- 索引不可用时，结构化查询仍应能够工作。

#### 4.16.7 ChangeHistory：关键变更记录

用途：记录删除、恢复、状态变化、记忆过期、截止时间修改和重要确认等关键操作。

建议包含：

```text
变更记录标识
对象类型和标识
变更类型
变更前摘要或状态
变更后摘要或状态
触发来源：用户 / 后台任务 / 系统补偿
关联确认操作标识（如果有）
发生时间
是否可撤销
```

规则：

- 只记录关键变更，不采用完整事件溯源。
- 不保存可还原敏感原文，也不复制完整模型上下文。
- 撤销通过新增一条反向变更完成，保留原变更记录。

### 4.17 Reminder：提醒

用途：保存行动提醒和主动行为的可追踪状态。

建议包含：

```text
提醒标识
关联行动或任务标识
计划时间
实际提醒时间
提醒类型
提醒状态：待发送 / 已发送 / 已处理 / 已取消 / 失败
用户处理结果
幂等键
创建时间
```

规则：

- 有明确截止时间的行动可以生成提醒。
- 同一明确提醒时间最多提醒一次。
- 逾期行动每天最多集中提醒一次。
- 提醒点击后的完成、延期或搁置仍必须通过确认规则变更行动状态。
- 具体渠道、时区和提醒间隔由《v1-行动摘要与提醒》确定。

## 5. 通用字段和通用规则

### 5.1 稳定标识

所有正式对象使用稳定、不可复用的标识。标识只用于本地关联、迁移和导出，不发送给外部模型作为上下文内容。

推荐使用随机生成的全局唯一标识，而不是依赖数据库自增整数。这样可以：

- 避免删除后复用标识；
- 支持离线本地创建；
- 为未来服务器同步和数据迁移保留空间；
- 让导出文件保持稳定引用。

### 5.2 时间字段

所有时间至少区分：

```text
创建时间
更新时间
发生时间
用户确认时间
计划执行时间
实际执行时间
```

本地存储建议统一保存绝对时间，并保留用户时区或时区偏移信息用于展示。默认时区和提醒规则尚未冻结，不在本文件中指定具体值。

### 5.3 状态字段与删除字段分离

业务状态和生命周期状态不能共用一个字段：

```text
业务状态：行动进行中、目标已完成、记忆过期等
生命周期状态：正常、归档、删除、彻底删除
```

这样可以表达：

```text
已完成 + 已归档
已过期 + 正常
进行中 + 删除
```

实际界面是否允许所有组合，由各业务子需求限制；数据层不能因为界面简化而丢失语义。

### 5.4 来源关系

来源关系作为独立的通用关系保存，不把来源硬编码成单一字段。

推荐支持：

```text
目标 / 行动 / 记忆 / 事实 / 决策 / 建议
→ 一个或多个来源

来源可以是：
→ 原始记录
→ 附件
→ 分析结果
→ 行动结果
→ 另一正式对象
→ 处境模型版本
```

每条来源关系建议携带：

```text
来源关系标识
被引用对象类型和标识
来源对象类型和标识
来源片段或摘要（可选）
关系类型
创建时间
来源是否已删除
```

来源摘要只用于删除后展示和迁移说明，不能替代原始内容本身。

### 5.5 版本和覆盖规则

以下内容禁止静默覆盖历史：

- 长期记忆内容变化。
- 目标截止时间变化。
- 行动关键字段和状态变化。
- 处境模型变化。
- 决策复盘结论变化。

推荐采用：

```text
当前对象
+ 关键变更记录
+ 旧版本或旧状态引用
```

普通展示可以只显示当前版本；历史复盘可以读取旧版本。

### 5.6 敏感标记

敏感标记至少可以出现在：

```text
原始记录
附件
事实
长期记忆
目标
行动
行动结果
处境模型
索引内容
```

敏感标记用于触发外发前策略，不代表本地禁止保存。敏感标记本身不能代替识别器，也不能保证所有敏感内容都已正确识别。

## 6. 关键业务流程的存储规则

### 6.1 用户文字发送

```text
客户端提交用户文字
→ Local Core 创建 OriginalRecord
→ 提交分析任务
→ 创建 AnalysisRun
→ 保存 StructuredAnalysis
→ 创建 CandidateItem 和 ConfirmationBatch（如有候选）
→ 更新派生索引
→ 返回助手回复和待确认内容
```

原始记录保存与模型分析解耦：模型失败时，原始记录仍然存在。

### 6.2 用户语音发送

```text
录音
→ 临时保存音频和转写文本
→ 用户检查、修改并确认
→ 创建 OriginalRecord
→ 关联原始音频（如果保留）
→ 开始 AnalysisRun
```

取消时：

```text
删除临时转写状态
→ 按保留规则清理临时音频
→ 不产生正式原始记录
```

### 6.3 附件发送

```text
创建 OriginalRecord
→ 保存 Attachment 原始内容
→ 创建解析任务
→ 解析成功：保存解析结果并关联来源
→ 解析失败：记录失败状态，不改变原始附件
```

解析结果是附件的派生分析，不能成为附件原始内容的替代品。

### 6.4 候选确认

```text
用户修改或取消候选项
→ 保存本次确认操作
→ 提交确认批次
→ 本地核心校验候选状态和操作权限
→ 在一个事务中创建或更新正式对象
→ 写入来源关系
→ 更新索引任务
→ 返回正式对象结果
```

确认批次的事务边界建议为：

```text
正式对象写入成功
+ 来源关系写入成功
+ 索引更新任务登记成功
```

索引本身可以异步完成，但索引更新任务必须和正式对象写入一起登记，避免正式对象已经存在却没有后续索引补偿记录。

### 6.5 用户拒绝候选

```text
候选项标记为已取消
→ 不创建正式对象
→ 保留来源和处理时间
→ 不作为已确认事实参与普通建议
```

被拒绝的候选可保留用于交互历史，但默认不进入正式 RAG 内容；未来重新提出必须基于新的分析结果。

### 6.6 记忆冲突更新

```text
发现新内容与当前记忆冲突
→ 生成新的记忆候选
→ 用户确认
→ 旧记忆标记为过期或不再适用
→ 创建新的有效记忆
→ 两者保留来源和先后关系
→ 更新索引状态
```

不直接修改旧记忆正文，避免历史复盘失去当时信息。

### 6.7 删除原始记录

```text
用户请求删除原始记录
→ 二次确认（按删除类型）
→ 原始记录进入删除状态
→ 原始正文从普通 RAG 检索中排除
→ 附件按删除规则处理
→ 正式目标、行动、记忆和决策不自动删除
→ 来源关系显示原始记录已删除
```

彻底删除时，物理清除范围、备份处理和是否保留最小操作记录由数据导出与安全子需求进一步确定。

### 6.8 归档

```text
对象进入归档状态
→ 保留数据和来源
→ 默认不参与日常界面
→ 是否参与普通建议由业务规则决定
```

归档不是删除，不应从结构化数据和索引中物理移除。

## 7. 一致性和失败处理

### 7.1 原始记录保存与模型失败

必须满足：


```text
原始记录保存成功
≠
模型分析必须成功
```

模型调用失败时保存：

```text
原始记录：保留
分析运行：失败
助手回复：展示失败或稍后重试状态
正式对象：不创建
候选项：只有模型实际返回并通过校验时才创建
```

### 7.2 正式对象写入与索引失败

推荐采用：

```text
正式对象事务成功
→ 索引更新任务登记成功
→ 索引异步更新
→ 索引失败进入补偿队列
```

不能因为索引暂时不可用而回滚用户已确认的正式对象，也不能因为索引成功而认为正式对象已经写入。

### 7.3 附件保存与附件解析失败

必须满足：

```text
附件保存成功
≠
附件解析必须成功
```

解析失败只影响：

- 解析状态；
- 附件的可搜索文本；
- 与解析结果相关的分析能力。

不会影响：

- 原始附件保存；
- 原始记录保存；
- 导出原始附件。

### 7.4 重复请求和幂等

以下操作需要幂等保护：

- 用户重复点击确认。
- 用户重复点击完成、延期或搁置。
- 每日摘要补偿执行。
- 同一提醒时间的重复调度。
- 索引更新任务重试。
- 附件解析任务重试。

重复请求不能创建重复的正式对象或重复的主动提醒。正式对象创建和确认批次应有可识别的确认操作标识。

### 7.5 删除和并发修改

v1 暂不实现多设备同步，但同一设备仍可能出现重复客户端请求或后台任务并发。因此正式写入需要：

- 检查对象当前版本或更新时间；
- 检查候选项仍处于可确认状态；
- 检查删除状态；
- 在失败时返回需要重新加载的结果，而不是静默覆盖。

## 8. 检索索引边界

### 8.1 进入索引的内容

推荐进入基础索引：

```text
原始记录
事实
已确认长期记忆
目标
行动
行动结果
决策及复盘结果
当前和历史处境模型
```

候选项和待确认内容可以进入受限索引，但必须带状态并在召回时降权或显式标记。具体排序规则由 RAG 子需求确定。

### 8.2 不进入普通检索的内容

默认排除：

```text
已彻底删除内容
已删除原始记录的原文
确认前的语音转写临时文本
确认前的临时附件
失败且无有效结果的分析临时内容
```

已取消候选默认不作为正式建议依据；是否保留用于“曾经拒绝过的建议”分析，由建议子需求确定。

### 8.3 索引记录的最低来源字段

每条索引记录至少要能表达：

```text
索引标识
被索引对象类型和标识
可检索文本或向量引用
来源记录引用
发生时间
当前状态
可信度
是否用户确认
是否敏感
是否已删除
索引版本
更新时间
```

索引层不保存外部模型所需的内部数据库字段作为业务上下文；上下文组装时转换为用户可理解的来源信息。

### 8.4 索引更新状态

建议索引更新拥有独立状态：

```text
待更新
更新中
已完成
失败待重试
已跳过
```

索引更新失败不改变正式对象业务状态。重建索引时以结构化对象和仍可访问的原始记录为输入。

## 9. 导出、迁移和未来服务器化

### 9.1 导出边界

v1 需要支持：

```text
Markdown
JSON
原始文件压缩包
```

导出应覆盖：

- 原始记录；
- 附件元数据和原始文件；
- 分析结果和候选处理状态；
- 正式目标、行动、记忆、事实和决策；
- 来源关系；
- 处境模型历史版本；
- 建议和建议效果；
- 必要的创建、更新时间和生命周期状态。

导出时不能只导出当前列表而丢失来源关系和历史状态。

导出加密格式、密码规则和具体目录结构仍由《v1-数据导出》确定。

### 9.2 迁移原则

JSON 导出需要能够重建：

```text
稳定标识
对象类型
对象关系
来源关系
状态
关键时间
```

原始文件压缩包需要能够通过附件标识与 JSON 元数据重新关联。

### 9.3 未来服务器化

v1 的业务模块只依赖逻辑存储接口，不把业务规则写死在某一种本地数据库 API 中：

```text
业务服务
→ Repository / Storage 接口
→ 本地结构化存储和文件存储
```

后续增加服务器时，优先增加：

```text
远端存储实现
同步层
冲突处理层
账号和权限层
```

不改变：

- 用户确认是正式写入门槛；
- 客户端不直接调用模型；
- 外部模型请求必须经过敏感信息钩子；
- 原始内容、正式对象和索引分层；
- 删除原始记录不自动删除正式对象的规则。

## 10. 事务边界建议

### 10.1 原始记录事务

```text
写入原始记录
+ 写入附件关联
+ 写入聊天消息引用
+ 登记分析任务
```

分析任务可以异步执行，但任务登记必须与原始记录保存处于同一成功边界内。

### 10.2 分析结果事务

```text
写入分析运行结果
+ 写入结构化分析
+ 写入候选项
+ 写入确认批次
```

如果模型结果不完整或不符合结构化格式：

```text
分析运行标记失败或部分成功
→ 保存可追溯的错误摘要
→ 不创建非法候选
```

### 10.3 确认事务

```text
校验候选项版本和确认状态
+ 创建或更新正式对象
+ 写入来源关系
+ 写入关键变更记录
+ 登记索引更新任务
```

### 10.4 删除事务

```text
更新删除状态
+ 更新来源可见性
+ 登记索引删除或降权任务
+ 登记附件处理任务（如需要）
```

物理清除是独立且需要二次确认的操作，不与普通软删除混为一谈。

## 12. 自问自答后的默认决策汇总

本文件中已经采用的推荐方案：

1. 每次用户确认发送的内容形成一条原始记录。
2. 聊天会话和原始记录分层保存。
3. 语音转写确认前只作为临时输入，不进入正式数据和 RAG。
4. 附件从属于原始记录，先保存原始附件再异步解析。
5. 一条输入对应一份分析结果，内部包含多个独立候选项。
6. 候选项拥有独立确认状态，并通过确认批次统一处理。
7. 事实和长期记忆分离，事实不自动升级为长期记忆。
8. 模型只能提出候选和建议，本地核心根据确认命令写入正式对象。
9. 正式结构化数据是权威来源，检索索引是可重建派生数据。
10. v1 不采用完整事件溯源，但保留关键变更历史、版本和来源关系。
11. 业务状态与删除、归档等生命周期状态分离。
12. 删除原始记录不自动删除已确认的正式对象。
13. 关键确认、删除和索引任务具备事务边界和幂等保护。
14. 数据模型使用稳定标识和通用来源关系，为导出和未来服务器化保留空间。
15. 不为未来多用户和跨设备同步提前引入账号、冲突和分布式复杂度。

## 14. 验收标准

完成后续实现时，至少应满足以下行为：

### 原始记录

- 用户确认发送文字后，存在一条可追溯原始记录。
- 用户未确认语音转写时，不存在正式原始记录。
- 模型调用失败不影响原始记录保存。
- 一条原始记录可以关联多个附件和多次分析运行。

### 分析和候选

- 一次输入的多个候选项可以独立取消或修改。
- 候选默认选中不等于已确认。
- 未确认候选不会创建正式行动或长期记忆。
- 模型返回不合法时，不会产生非法正式对象。

### 正式对象

- 创建行动、修改行动状态和保存长期记忆都经过用户确认。
- 目标、行动、记忆、事实和决策可以追溯到来源。
- 记忆更新不会静默覆盖旧记忆。
- 目标不会仅因所有行动完成而自动标记完成。

### 删除和索引

- 删除原始记录后，已确认正式对象仍然存在。
- 删除后的原始正文不再参与普通原文检索。
- 索引失败时，正式对象仍然保留并有可重试的索引任务。
- 索引可以依据结构化数据和仍可访问的原始内容重建。

### 导出和迁移

- Markdown、JSON 和原始附件包能够覆盖核心数据。
- JSON 能保留稳定标识、关系、来源、状态和关键时间。
- 原始附件能够通过标识与元数据重新关联。
