## 1. 文档目的与规则层级

### 1.1 本文件要解决的问题

当前 12 份详细子需求已经分别覆盖输入、分析、确认、模型、敏感信息、事实、记忆、RAG、处境、行动、目标、提醒、建议、决策和导出，但分别编写会自然产生以下问题：

- 同一个状态在不同对象上使用相同名称。
- 产品状态、技术任务状态、提醒投递状态和对象生命周期状态混在一起。
- 部分文档把推荐方案写成待决策，另一些文档把它写成已确认。
- 同一条数据流在不同文档中有不同的提交时点。
- 索引、处境模型、提醒和后台任务的派生结果容易被误当成权威业务状态。
- Local Core 的命令、查询、异步任务边界尚未形成统一入口。

本文件将这些内容统一为：

```text
全局不变量
→ 统一术语和状态维度
→ 对象权威性矩阵
→ 端到端数据流
→ 跨模块允许/禁止转换
→ Local Core 逻辑接口
→ 技术选型前待决策项
```

### 1.2 规则层级

后续阅读和实现时，按照以下优先级理解：

```text
第一层：上游已确认产品约束
第二层：本文件本轮整合采用的工作基线
第三层：各详细子需求中的实现建议
第四层：具体技术选型和实现细节
```

当下层内容与上层内容冲突时：

- 不得用技术实现反推或修改产品约束。
- 详细子需求应按本文件的统一规则解释。
- 尚未进入本文件“本轮整合采用”的内容，不得在代码中硬编码为不可变产品行为。

### 1.3 统一文档状态

从本轮开始，文档状态使用以下分类：

| 状态 | 含义 | 实现含义 |
|---|---|---|
| 上游已确认约束 | 已在产品需求或架构基线中明确确认 | 必须遵守 |
| 本轮整合采用 | 为了让 v1 可以进入技术设计而采用的推荐工作基线 | 作为当前设计默认值，但保留变更记录能力 |
| 技术待决策 | 需要在技术选型或详细交互阶段确定 | 不得提前硬编码 |
| 后续版本 | 明确不属于当前 v1.0 交付范围 | 当前不实现 |

本文件中的“已统一”表示已形成当前整合基线，不等于所有细节都已经完成产品验收或技术选型。

## 3. 全局不变量

以下规则跨越所有模块，是后续接口和存储设计必须保持的系统不变量。

### 3.1 私有核心主机与客户端边界

- v1 只服务单个用户本人。
- 手机和电脑均提供基础客户端入口。
- 核心业务数据和服务运行在用户可控制的私有核心主机上。
- v1 不默认使用公共云托管，不做多用户产品化和多租户。
- v1 不实现多个私有核心之间的同步和同步冲突处理。
- 手机和电脑默认访问同一个私有核心，不承诺移动端离线时完整可用。
- 后续公共云化或多设备同步不能改变用户确认、来源追踪、敏感外发和正式对象写入边界。

### 3.2 客户端与 Local Core

客户端负责：

```text
输入
展示
编辑
确认意图收集
设备能力适配
```

Local Core 负责：

```text
权威数据读写
业务状态校验
确认事务
模型调用编排
敏感信息处理
RAG 和上下文组装
后台任务
索引任务登记
提醒计划和导出任务
```

客户端不得：

- 直接写业务数据库。
- 直接写检索索引。
- 直接调用外部模型或外部数据处理服务。
- 根据模型文本自行判断正式对象是否已经创建或完成。
- 绕过确认中心执行正式目标、行动、记忆、决策或状态变更。

### 3.3 数据分层不可替代

必须保持以下层级：

```text
原始输入
→ 分析运行与结构化分析
→ 事实/建议/候选
→ 用户确认
→ 正式业务对象
→ 派生索引、处境、摘要、提醒和复盘
```

并满足：

```text
原始内容不能被分析结果替代
分析结果不能被候选项替代
候选项不能被正式对象替代
正式对象不能被索引替代
派生数据必须能够回指来源
```

### 3.4 正式业务变更统一确认

以下变更必须通过确认中心和 Local Core 正式事务：

- 创建或修改正式目标。
- 创建行动。
- 修改行动内容、状态、截止时间或计划。
- 保存、更新、过期或合并长期记忆。
- 保存正式决策记录。
- 修改正式处境判断。
- 删除或彻底删除对象。
- 将建议转为正式行动。
- 周复盘产生的正式目标、行动、记忆、决策或提醒计划变更。

以下不等于业务变更确认：

```text
默认全选
展示确认卡片
展开候选
编辑候选草稿
打开 App
收到提醒
关闭提醒
用户采纳建议
确认语音转写
同意某次隐私外发
```

### 3.5 三类确认必须分开

| 确认类型 | 作用 | 不能替代 |
|---|---|---|
| 输入提交/语音转写确认 | 确认内容是否作为原始输入保存和分析 | 业务变更确认、隐私外发确认 |
| 隐私外发确认 | 确认某次最终外发载荷能否按策略离开设备 | 业务变更确认 |
| 业务变更确认 | 确认目标、行动、记忆、决策或状态变更是否正式生效 | 隐私外发确认、输入提交确认 |

导出预览确认是第四种独立的操作确认：

```text
确认导出范围和保护选项
≠ 修改业务对象
```

### 3.6 模型、RAG、提醒和后台任务不得直接写正式对象

模型、RAG、处境模型、每日摘要、周复盘、提醒和后台任务可以产生：

```text
普通回复
分析结果
事实记录
建议
候选项
待确认内容
摘要
复盘结果
索引任务
```

不得直接产生已生效的：

```text
正式目标
正式行动
长期记忆
正式决策
正式状态变更
正式提醒计划变更
删除或彻底删除
```

唯一正式写入路径为：

```text
候选或用户明确变更意图
→ 用户确认
→ Local Core 校验
→ 原子事务写入
→ 来源关系和关键变更记录
→ 索引/处境刷新任务登记
```

### 3.7 所有外部服务统一经过外发策略

任何实际将用户内容发送到设备外部的接收方，都属于统一外发策略边界：

```text
大模型
Embedding
语音识别
OCR
网页解析
第三方工具
未来远程服务
```

统一链路：

```text
最终载荷组装
→ External Data Egress Policy
→ 允许、脱敏后允许、等待隐私决定或阻止
→ 供应商适配器
```

Model Gateway、外部语音识别、OCR、Embedding 和网页解析不得存在旁路。

### 3.8 来源可追溯

所有正式对象、事实、建议、处境版本、索引结果和导出内容都必须尽可能回指：

```text
原始记录
附件
附件解析结果
分析运行
结构化分析
候选项
用户确认操作
行动结果
决策记录
```

删除来源后：

- 不恢复已删除正文。
- 保留必要的来源删除状态和最小摘要。
- 重新评估事实、记忆、处境和建议依据的支持强度。
- 不因来源删除自动级联删除已经确认的正式对象。

### 3.9 索引是可重建派生层

正式对象或原始记录变更时：

```text
正式事务成功
+ 同事务登记 IndexUpdateJob
→ 事务提交
→ 索引异步更新
```

索引失败：

- 不回滚正式对象。
- 进入失败待重试状态。
- 结构化查询继续可用。
- 不得直接向用户断言“没有相关记录”。
- 查询层仍需依据权威对象状态过滤残留索引。

### 3.10 后台任务不得重复产生副作用

所有后台主动行为都必须具备：

```text
持久化任务记录
稳定逻辑键
幂等检查
失败状态
补偿路径
```

补偿的目标是：

```text
补齐未完成产物
```

不是：

```text
重放已经成功的正式写入或通知副作用
```

## 4. 统一术语和状态模型

### 4.1 输入和分析对象

| 对象 | 统一含义 |
|---|---|
| `InputSubmission` | 一次用户提交操作的幂等边界，不等同于原始记录 |
| `OriginalRecord` | 用户明确提交且 Local Core 成功保存的原始输入 |
| `SessionMessage` | 聊天界面中的用户消息、助手回复或系统消息 |
| `Attachment` | 从属于原始记录的原始附件或原始链接 |
| `AttachmentParseResult` | 附件解析后的派生结果，可多次尝试 |
| `AnalysisRun` | 一次输入分析、补充分析或重新分析执行 |
| `StructuredAnalysis` | 一次分析运行输出的结构化解释 |
| `Fact` | 有来源的结构化陈述，不天然等于客观真相或当前有效状态 |
| `Suggestion` | 模型提出的可选建议，不等于行动或用户采纳 |
| `CandidateItem` | 等待用户确认的正式业务变更意图 |
| `ConfirmationBatch` | 组织多个候选并提交确认的事务单元 |

### 4.2 正式业务对象

```text
Goal
Action
Memory
Decision
ActionResult
ContextSnapshot
ReminderPlan
```

这些对象的正式创建、修改和业务状态变化由 Local Core 负责。

### 4.3 派生和运行对象

```text
ContextView
BackgroundJob
IndexUpdateJob
ReminderInstance
ModelCallLog
ExportJob
ChangeHistory
```

它们可以记录、聚合、调度、解释或加速业务，但不能替代核心正式对象。

### 4.4 状态维度分离

任何对象都不使用没有作用域的通用 `status` 表达所有语义。建议在逻辑接口和存储中使用明确字段：

```text
candidate_status
confirmation_batch_status
fact_business_status
memory_business_status
action_execution_status
action_plan_status
action_timeliness_status
goal_business_status
goal_deadline_observation
context_version_status
reminder_plan_status
reminder_instance_status
background_job_status
index_job_status
lifecycle_status
```

### 4.5 Action 行动状态

#### 执行状态

```text
待开始
进行中
暂时搁置
已完成
已取消
```

#### 计划状态

```text
正常
已延期
```

#### 时效状态

```text
无截止时间
未过期
已过期
不适用
```

统一语义：

- `已延期`表示用户确认修改了计划日期，行动仍然要做。
- `已过期`表示截止时间观察，不自动修改执行状态。
- 截止时间到达不得自动暂停、取消、完成或延期行动。
- 完成、取消、暂时搁置、恢复和延期都需要确认。
- 已完成和已取消不能普通前向重开。

### 4.6 Goal 目标状态

正式业务状态：

```text
规划中
进行中
已完成
已暂停
已放弃
已过期
```

另行保存：

```text
目标截止时间观察：未到期 / 已到期
生命周期：正常 / 归档 / 软删除 / 彻底删除
```

统一语义：

- 目标 `已过期`是用户确认后的正式业务状态。
- 目标截止时间“已到期”只是时间观察，不自动改变正式状态。
- 关联行动全部完成不能自动完成目标。
- 目标状态变化不能自动改写关联行动。

### 4.7 Candidate 和 ConfirmationBatch

候选状态：

```text
待确认
已确认
已修改后确认
已取消
已过期
```

确认批次状态：

```text
待处理
部分处理
已确认
已取消
已过期
```

统一语义：

- 默认全选仍是待确认。
- 暂不处理保持待确认，只记录提醒抑制或下次处理信息。
- 拒绝和取消在候选生命周期上统一为已取消；操作记录可以保留不同来源。
- 同一批次可以跨多次用户操作处于部分处理。
- 单次确认提交必须全有或全无。
- 省略候选不等于取消。

### 4.8 Fact 事实和 Memory 记忆

事实业务状态建议为：

```text
抽取
可参考
有争议
过期
错误
```

`已删除`属于生命周期字段，不作为事实业务状态。

长期记忆业务状态建议为：

```text
有效
过期
有争议
```

`已删除`、`归档`、`彻底删除`属于生命周期字段。

统一规则：

- 事实可以自动抽取和保存，但必须带来源、时间、可信度、表达方式、确认状态和敏感标记。
- 事实被保存、检索或重复提及，不自动升级为用户确认事实或长期记忆。
- 事实若要改变长期理解、现实限制、正式对象或重要建议依据，必须生成确认候选。
- 长期记忆创建、更新、过期、合并和删除必须经过确认中心。
- 冲突记忆使用新候选和版本化更新，不直接覆盖旧记忆。
- 相似记忆 v1 不自动合并。

### 4.9 ContextView 和 ContextSnapshot

为解决“自动刷新”和“用户确认”混淆，统一拆分：

```text
ContextView
= 查询时自动聚合的临时视图，不是正式事实

ContextSnapshotCandidate
= 需要用户确认的重要处境判断候选

ContextSnapshot
= 用户确认后可作为正式当前处境版本的快照

HistoricalContextSnapshot
= 被新正式版本替代的历史快照
```

普通建议可以消费 `ContextView`；重要处境判断、现实限制、风险和优先级变化进入确认中心后才形成正式当前快照。

### 4.10 ReminderPlan 和 ReminderInstance

提醒拆为两层：

```text
ReminderPlan
= 未来调度意图

ReminderInstance
= 某一次具体投递、展示、关闭或稍后处理记录
```

提醒计划状态：

```text
有效
已抑制
已失效
```

提醒实例状态：

```text
待触发
已投递
已关闭
已稍后
投递失败待补偿
已失效
```

提醒不能用来表达行动是否完成、延期、搁置或取消。

### 4.11 BackgroundJob 和 IndexUpdateJob

通用后台任务状态：

```text
未登记
排队中
执行中
成功
失败
已取消
```

独立字段表达：

```text
可恢复失败
不可恢复失败
等待隐私决定
部分成功
```

索引更新任务状态：

```text
待更新
更新中
已完成
失败待重试
已取消
```

“部分成功”属于业务结果，不等同于通用任务执行状态。

## 5. 对象权威性和行为矩阵

| 对象 | 可自动产生 | 是否正式业务对象 | 是否需要业务确认 | 普通 RAG | 历史复盘 | 默认导出 |
|---|---:|---:|---:|---:|---:|---:|
| `OriginalRecord` | 用户提交后 | 原始输入权威记录 | 输入提交确认 | 可作为证据 | 可 | 是 |
| `AnalysisRun` | 是 | 否 | 否 | 否 | 可 | 可选 |
| `StructuredAnalysis` | 是 | 否 | 否 | 受任务使用 | 可 | 可选 |
| `Fact` | 是 | 陈述记录 | 通常否；影响正式理解时是 | 受限 | 可 | 是 |
| `CandidateItem` | 是 | 否 | 是 | 受限且带状态 | 可 | 可选 |
| `Suggestion` | 是 | 否 | 转正式变更时是 | 可作为依据 | 可 | 可选 |
| `Goal` | 否 | 是 | 是 | 当前状态依据 | 可 | 是 |
| `Action` | 否 | 是 | 是 | 当前执行依据 | 可 | 是 |
| `Memory` | 否 | 是 | 是 | 当前有效记忆优先 | 过期可用 | 是 |
| `Decision` | 否 | 是历史对象 | 是 | 可作为历史依据 | 可 | 是 |
| `ActionResult` | 可生成候选 | 是结果对象 | 保存/确认时是 | 可 | 可 | 是 |
| `ContextView` | 是 | 否 | 否 | 当前临时上下文 | 不适用 | 否 |
| `ContextSnapshotCandidate` | 是 | 否 | 是 | 受限 | 可 | 可选 |
| `ContextSnapshot` | 确认后 | 是聚合快照 | 重要版本需确认 | 当前版本可用 | 可 | 是 |
| `ReminderPlan` | 可由正式行动产生 | 调度对象 | 重大业务计划变更需确认 | 否 | 可 | 可选 |
| `ReminderInstance` | 是 | 否 | 关闭/稍后不需要业务确认 | 否 | 可 | 可选 |
| `BackgroundJob` | 是 | 否 | 否 | 否 | 可 | 可选 |
| `IndexRecord` | 是 | 否 | 否 | 派生召回 | 可 | 否 |
| `ExportJob` | 用户发起后 | 否 | 导出范围需确认 | 否 | 可 | 否 |

## 6. 端到端统一数据流

### 6.1 文字输入

```text

→ SubmitTextInput
→ Local Core 校验
→ 输入提交事务：
   OriginalRecord
   + SessionMessage 引用
   + AnalysisRun/分析任务登记
→ 返回已提交、分析中
→ 按需 RAG
→ 最小上下文组装
→ 外发策略
→ Model Gateway
→ 分析结果和候选
→ 普通回复和/或确认卡片
```

### 6.2 语音输入

```text

→ 临时音频
→ 转写
→ 用户查看和编辑
→ 用户确认发送
→ SubmitVoiceInput
→ 与文字输入链路合流
```

确认前：

- 不创建正式原始记录。
- 不创建正式聊天消息。
- 不启动内容分析。
- 不提取事实、候选或记忆。
- 不进入正式 RAG。

### 6.3 附件输入

```text

→ 本地临时草稿
→ 用户确认提交
→ 输入提交事务：
   OriginalRecord
   + Attachment 原始内容/原始链接
   + 来源关系
   + “未安排深度解析”或可执行解析任务登记
→ 返回附件已保存
```

v1.0 不支持的深度解析不能创建永远无法执行的伪任务。

### 6.4 输入分析

```text
AnalysisRun
→ 判断任务类型和输出模式
→ 判断是否需要个人 RAG
→ 结构化硬筛
→ 关键词/语义召回
→ 权威状态复核
→ 最小上下文组装
→ External Data Egress Policy
→ Model Gateway
→ 模型响应解析
→ 结构化结果校验
→ 业务边界和来源校验
→ 保存 StructuredAnalysis / Fact / Suggestion / CandidateItem
→ 需要正式变更时创建 ConfirmationBatch
```

### 6.5 确认和正式写入

```text
用户明确提交确认
→ SubmitConfirmationBatch
→ 校验批次、候选、正式对象版本和风险确认
→ 确认事务：
   UserConfirmationAction
   + 正式对象创建/更新
   + 候选/批次状态更新
   + SourceRelation
   + ChangeHistory
   + 受影响 ReminderPlan
   + IndexUpdateJob 登记
   + ContextRefreshJob 登记（如需要）
→ 事务提交
→ 索引和处境异步刷新
```

### 6.6 摘要、提醒、复盘和决策辅助

```text
权威结构化查询
→ 当前处境视图
→ 按需 RAG
→ 最小上下文
→ 敏感外发策略
→ 模型生成展示、建议或候选
→ 正式变更回到确认中心
```

不得从模型输出、索引结果或提醒状态直接推断正式业务状态。

### 6.7 导出

```text
用户选择导出形式和范围
→ PreviewExport
→ 显示数量、状态、附件可用性、敏感风险和保护选项
→ 用户确认
→ 冻结导出范围快照
→ StartExport
→ 从权威结构化数据和可访问原始文件读取
→ 生成 Markdown / JSON / 原始文件包
→ 校验清单和保护状态
→ 成功交付或明确失败
```

导出为只读任务，不改变源对象。

## 8. 统一 Local Core 逻辑接口

本节只定义逻辑接口，不锁定 REST、IPC、本地 HTTP、函数调用或具体编程语言。

### 8.1 Command / Query / Background Job 三类边界

```text
Command：表达用户意图，可能产生本地写入或任务
Query：读取权威状态、候选、结果或任务状态
Background Job：由本地调度器执行的异步工作
```

### 8.2 Command 通用信封

所有可能改变本地数据或创建任务的命令，建议具备：

```text
operation_id
client_source
request_fingerprint
expected_version（适用时）
payload
```

统一返回：

```text
operation_id
status
resource_refs
new_versions
task_refs
warnings
validation_errors
```

### 8.3 输入命令

| 接口 | 作用 | 确认边界 |
|---|---|---|
| `SubmitTextInput` | 提交文字并创建原始记录、消息引用和分析任务 | 点击发送只确认输入提交 |
| `SubmitVoiceInput` | 提交用户确认后的最终转写文本和可选音频关联 | 必须先完成语音转写确认 |
| `CreateOrUpdateVoiceDraft` | 保存语音临时草稿 | 只能写临时数据 |

| `SubmitAttachmentInput` | 提交附件并保存原始内容和关联 | 解析与保存解耦 |
| `CancelAnalysis` | 取消尚未完成的输入分析 | 不删除原始记录 |
| `RequestReanalysis` | 重新运行输入分析 | 产生新运行和新结果版本 |
| `RequestAttachmentSupplementAnalysis` | 对成功解析的附件执行补充分析 | 不覆盖原分析 |

### 8.4 模型和隐私命令

### 8.5 正式业务确认命令

统一使用：

```text

```

负责：

- 创建或修改目标。
- 创建或修改行动。

## 9. 后台任务和异步边界

### 9.1 任务类型

```text
输入分析
附件解析
附件补充分析
重新分析
建议生成
行动结果提取
每日摘要
每周复盘
明确截止时间提醒
过期行动集中提醒
待确认提醒
处境刷新
索引更新/重建
导出
```

### 9.2 任务通用状态

```text
未登记
排队中
执行中
成功
失败
已取消
```

另行记录：

```text
retryable
waiting_privacy_decision
partial_result
last_error
attempt_count
idempotency_key
```

### 9.3 任务和业务结果分离

```text
任务成功
≠ 目标完成
任务成功
≠ 建议被采纳
任务成功
≠ 记忆已确认
任务成功
≠ 提醒已处理
```

### 9.4 关键幂等规则

- 同一业务日最多一份有效每日摘要。
- 同一业务周最多一份有效周复盘。
- 同一明确提醒机会最多一个提醒实例。
- 同一确认操作标识不能重复创建正式对象。
- 同一导出操作标识不能产生不同范围的导出。
- 同一索引任务不能让旧版本覆盖新版本。
- 同一附件解析上下文不能产生多个并列当前结果。

## 10. 跨文档冲突收口结果

### 10.1 文档成熟度

统一表述为：

```text
十二份 v1 详细子需求已经形成；
本文件进一步形成跨文档整合工作基线；
其中上游产品约束已确认，本轮新增的细节规则作为当前实施基线；
具体技术实现仍需技术选型。
```

不再把“十二份详细子需求全部已确认”理解为所有算法、参数和交互都已经冻结。

### 10.2 原始记录提交时点

统一为：

> 用户明确提交且 Local Core 成功完成原始记录事务后，才形成正式 `OriginalRecord`。

具体入口：

```text
文字：点击发送
语音：确认最终转写文本发送
附件：确认发送附件
```

以下不构成正式提交：

```text
选择附件
录音结束
转写完成
输入框草稿
```

### 10.3 Action 延期、过期和暂停

统一为三维模型：

```text
执行状态：待开始 / 进行中 / 暂时搁置 / 已完成 / 已取消
计划状态：正常 / 已延期
时效状态：无截止时间 / 未过期 / 已过期
```

### 10.4 Goal 过期和到期观察

统一为：

```text
Goal.deadline_observation = 时间观察
Goal.business_status = 用户确认后的正式业务状态
```

不能用一个通用 `expired` 字段覆盖两者。

### 10.5 Reminder 层级

统一采用：

```text
ReminderPlan
+ ReminderInstance
```

通知投递状态不得代表行动或目标状态。

### 10.6 ContextView 和 ContextSnapshot

统一拆分：

```text
ContextView
ContextSnapshotCandidate
ContextSnapshot
HistoricalContextSnapshot
```

自动聚合不等于用户确认。

### 10.7 敏感外发策略

本轮整合采用：

- 三种用户可见模式：自动脱敏后发送、发送前查看并确认、检测到敏感信息时禁止发送。
- 产品默认模式：自动脱敏后发送。
- 如果策略未初始化、识别器不可用或处理结果不可靠，不得静默发送，进入等待决定或阻止状态。
- 所有外部接收方统一经过外发策略。
- 单次放行只对确定的一次最终载荷有效，不自动延续到重试、后台任务、后续会话或其他供应商。

### 10.8 模型失败和自动切换

本轮整合采用：

- 同一模型最多一次受控自动重试。
- 其他符合能力和权限条件的模型按列表顺序尝试，每个最多一次。
- 跨供应商自动切换默认关闭，用户明确开启后才允许。
- 永久配置错误、能力不支持、上下文超限、内容安全拒绝和用户主动取消不触发默认自动切换。
- 每次重试和切换重新组装载荷并经过敏感处理。

### 10.9 模型日志

统一拆分：

```text
AnalysisRun
= 业务任务运行状态

ModelCallLog
= 最小供应商调用元数据

SensitivePolicyLog
= 最小敏感策略审计元数据
```

三类记录不保存完整模型上下文、完整 RAG 内容、完整原始输出或凭证。

### 10.10 周复盘范围

本轮整合采用：

```text
v1.0：周复盘任务框架、基础统计、历史依据和候选生成
v1.1：复杂经验沉淀、完整决策复盘和高级历史分析
```

v1.0 周复盘不得因为生成成功就自动修改目标、行动、记忆或决策。

### 10.11 附件解析范围

统一为：

```text
v1.0：接收、原始保存、关联、生命周期管理、导出、失败状态
v1.1：OCR、网页抓取、文件抽取、附件语义检索和补充分析
```

v1.0 只登记可追踪的“未安排深度解析”状态，不创建不可执行伪任务。

### 10.12 RAG 责任边界

统一表述为：

> RAG 模块只生成经过状态、来源和权限复核的依据集合；业务分析编排器可以将依据交给模型综合判断，但 RAG 本身不得绕过 Model Gateway 发起外部模型请求。

### 10.13 事实权威性

统一为：

```text
Fact 记录“来源曾表达/支持过某个陈述”
≠ 系统宣告该陈述客观为真
≠ 当前有效限制
≠ 用户确认的长期记忆
```

### 10.14 软删除导出

本轮整合采用：

- 完整导出可包含软删除对象的最小结构、来源关系和删除状态，以保持迁移和审计语义。
- 按范围导出可以排除软删除对象。
- 软删除原文是否仍可导出，服从删除保留策略；导出不能自行恢复被删除正文。
- 彻底删除内容永不导出、恢复或通过索引重建出现。

## 11. 技术选型前必须收口的决策

### P0：不收口不进入核心实现

#### 11.1 Local Core 运行形态和通信

- 手机端采用嵌入式核心还是本地服务进程。
- 电脑端是否使用独立 Local Core 进程。
- 客户端与 Local Core 使用进程内调用、IPC 还是本地 HTTP。
- 客户端断开后任务是否继续。
- Local Core 启停、健康检查和崩溃恢复。
- 查询是否支持流式事件、轮询或两者。

#### 11.2 Command/Query 契约

- 通用信封字段最终命名。
- 操作标识生成规则。
- 幂等冲突返回格式。
- 版本冲突返回格式。
- 同步返回和异步任务返回格式。
- 错误码和错误分类。
- 分页、游标、排序和过滤。
- 查询结果的敏感字段裁剪。
- 接口版本策略。

#### 11.3 正式确认和撤销

- 删除、恢复、撤销是否全部走 `SubmitConfirmationBatch`。
- 高风险候选能否与普通候选同批提交。
- 候选有效期。
- 撤销窗口和可撤销操作范围。
- 多对象确认操作是否整体撤销。
- 失败尝试的最小记录模型。

#### 11.4 状态机正式冻结

- Action 三维状态模型是否升级为正式实现基线。
- Goal 状态转移和“已过期”确认规则。
- 目标和行动的恢复、重建和关联变更。
- Fact 高风险场景是否需要独立确认。

## 13. 验收标准

### 13.1 全局一致性

- 所有正式业务变更都能追溯到用户确认操作。
- 客户端、模型、RAG、提醒和后台任务没有正式对象旁路写入。
- 原始记录、分析结果、候选、正式对象和索引层级清晰。
- 所有派生数据都能回指来源。
- 业务状态、计划状态、时效状态、任务状态、投递状态和生命周期状态不混用。

### 13.2 输入和分析

- 文字、确认后的语音和已确认提交的附件按照统一输入链路处理。
- 语音确认前不进入正式记录、分析或 RAG。
- 附件保存和附件解析可独立成功或失败。
- 重新分析产生新运行和新结果，不覆盖旧结果或正式对象。

### 13.3 确认和状态

- 默认全选不等于确认。
- 暂不处理保持待确认。
- 单次确认提交全有或全无。
- Action 使用执行/计划/时效三维状态。
- Goal 不因行动完成自动完成。
- Reminder 不直接改变 Action 或 Goal。
- Fact 不自动升级为 Memory。

### 13.4 模型、RAG 和安全

- 所有外部服务请求进入统一外发策略。
- 每次模型重试或切换重新执行敏感处理。
- RAG 不绕过 Model Gateway。
- RAG 不直接修改正式对象。
- 外部模型不接收未处理敏感值、内部路径、内部 ID 或 API Key。
- 模型日志、敏感策略日志和任务日志不保存完整上下文和凭证。

### 13.5 后台和导出

- 每日摘要、明确提醒、过期行动集中提醒和周复盘遵守频率上限。
- 后台补偿不重复产生正式副作用。
- 导出是只读任务，使用冻结范围快照。
- API Key 和其他凭证始终排除。
- 彻底删除内容不会出现在导出、索引或历史恢复中。

本轮交叉整合已经完成，并由 2026 年 9 月 4 日确认的全栈技术选型和新版技术架构总览承接。项目下一步进入 Local Core 接口契约、数据库和文件存储方案设计，不直接进入业务代码开发。
