# v1 确认中心

> 状态：已确认的 v1 详细子需求基线
>
> 基线日期：2026 年 9 月 3 日
>
> 上游架构：[`v1-技术架构总览.md`](./v1-技术架构总览.md)
>
> 关联数据边界：[`v1-原始记录与结构化存储.md`](./v1-原始记录与结构化存储.md)
>
> 适用范围：v1 中所有正式业务对象的创建、更新、状态变更、删除和确认交互。

## 1. 文档目的

本文件回答：

```text
模型提出候选之后，用户如何明确表达意图，
系统如何把用户意图安全、可追溯、幂等地转换为正式业务变更？
```

确认中心不是单纯的 UI 卡片，而是由以下部分组成的统一业务边界：

```text
确认卡片展示
+ 候选项生命周期
+ 用户确认命令
+ 风险提示
+ Local Core 校验
+ 正式写入事务
+ 幂等和并发控制
+ 失败恢复
+ 撤销和变更记录
```

核心原则：

```text
模型负责提出候选和建议
→ 用户明确确认
→ Local Core 校验并执行正式变更
```

## 2. 关键问题与默认答案

### 问题 1：确认卡片什么时候出现？

**推荐答案：** 只有当分析结果中存在需要用户确认的正式业务候选时，才展示确认卡片。

需要进入确认中心的候选包括：

- 创建正式目标；
- 修改正式目标；
- 创建正式行动；
- 修改行动内容；
- 修改行动状态，例如完成、延期、搁置或取消；
- 保存长期记忆；
- 使旧记忆过期或保存新的冲突记忆；
- 保存正式决策记录；
- 修改目标截止时间；
- 将建议转化为正式行动；
- 周复盘提出的目标、行动、记忆、决策或处境变更；
- 删除或彻底删除对象。

普通闲聊、摘要、问题、建议依据、RAG 检索结果、分析运行记录和普通事实抽取不强制展示确认卡片。

推荐流程：

```text
原始记录保存成功
→ 分析任务完成
→ 结构化结果通过校验
→ 发现需要正式变更的候选
→ 创建确认批次
→ 展示助手回复和确认卡片
```

如果模型失败、结果不完整或候选无法通过结构化校验：

- 原始记录继续保留；
- 分析运行保留失败或部分成功状态；
- 不创建非法候选；
- 不展示可提交的确认卡片。

确认卡片的出现只表示“存在待用户处理的候选”，不表示正式对象已经创建或修改。

### 问题 2：正式目标是否必须确认？

**推荐答案：** 目标识别可以自动完成，但正式目标的创建和修改统一进入确认中心。

统一为：

```text
目标候选：可以自动生成
正式目标：用户确认后创建
正式目标修改：用户确认后生效
```

这样避免“目标识别后自动成为当前目标”，也避免目标在某些入口需要确认、某些入口不需要确认而造成规则不一致。

### 问题 3：一条输入中的多个候选如何组织？

**推荐答案：** 一条原始记录对应一次分析结果，一次分析结果可以包含多个独立候选项；多个候选项组成一个确认批次。

```text
一条原始记录
→ 一次分析运行
→ 一份结构化分析结果
→ 多个候选项
→ 一个确认批次
```

候选项必须独立处理：

- 可以逐项取消；
- 可以逐项修改；
- 可以部分确认；
- 可以部分暂不处理；
- 可以一次确认不同类型的候选。

候选项不能因为来自同一条输入，就被绑定成不可拆分的整体。

### 问题 4：哪些内容必须经过确认？

**推荐答案：** 任何会创建、更新、删除或改变正式业务对象的操作，都必须经过确认中心。

| 内容或操作 | 是否自动生成 | 是否必须用户确认 |
|---|---:|---:|
| 原始输入 | 是 | 否 |
| 原始附件保存 | 是 | 否 |
| 内容摘要 | 是 | 否 |
| 普通问题 | 是 | 否 |
| 普通事实抽取 | 是 | 通常否，但必须标记来源和可信度 |
| 正式目标创建 | 可以产生候选 | 是 |
| 正式目标修改 | 可以产生候选 | 是 |
| 创建行动 | 可以产生候选 | 是 |
| 修改行动内容 | 可以产生候选 | 是 |
| 修改行动状态 | 可以产生候选 | 是 |
| 保存长期记忆 | 可以产生候选 | 是 |
| 记忆过期或冲突更新 | 可以产生候选 | 是 |
| 保存决策记录 | 可以产生候选 | 是 |
| 修改目标截止时间 | 可以产生候选 | 是 |
| 删除对象 | 可以产生候选 | 是，通常还需二次确认 |
| 彻底删除对象 | 可以产生候选 | 是，必须二次确认 |

### 问题 5：默认全选是否等于确认？

**推荐答案：** 不等于。

```text
默认全选
≠
用户已确认
```

默认全选只表示：

> 如果用户明确提交确认，则这些候选构成本次默认提交集合。

以下行为均不构成正式确认：

- 卡片展示；
- 默认选中；
- 展开候选详情；
- 点击复选框；
- 进入编辑状态；
- 客户端暂存修改；
- 打开待确认列表；
- 返回聊天页面；
- 关闭 App；
- 后台自动提醒。

只有用户明确点击“确认”“提交确认”或等价动作，并且 Local Core 正式写入成功，候选才进入确认完成状态。

### 问题 6：用户暂不处理时发生什么？

**推荐答案：** “暂不处理”保持候选为待确认，不转为取消或拒绝。

```text
用户选择暂不处理
→ 候选仍为待确认
→ 不创建或修改正式对象
→ 记录暂不处理或提醒抑制信息
→ 后续仍可从待确认列表处理
```

暂不处理不能触发：

- 创建行动；
- 保存长期记忆；
- 修改目标或行动状态；
- 正式提醒该候选对应的业务对象；
- 永久移除候选；
- 自动转为拒绝。

v1 不为“暂不处理”新增独立候选业务状态；候选业务状态仍为“待确认”，提醒抑制和下次提醒时间单独记录。

### 问题 7：用户拒绝和取消是否区分？

**推荐答案：** 候选生命周期上统一进入“已取消”，用户操作记录可以区分来源。

```text
取消选择
拒绝建议
放弃本次候选
        ↓
候选状态：已取消
```

这样避免同时维护“已取消”和“已拒绝”两套重复终态。

可以在用户确认操作中记录：

```text
操作来源：取消选择 / 拒绝建议 / 批次放弃
可选拒绝原因
用户反馈
```

被拒绝候选不能直接恢复为待确认。未来再次提出时，必须生成新的分析结果和新的候选标识，并保留与历史候选的关联。

### 问题 8：用户修改候选后何时生效？

**推荐答案：** 只有“修改后确认”提交并成功写入后才生效。

```text
进入编辑
→ 修改候选草稿
→ 预览修改内容
→ 提交修改后确认
→ Local Core 校验
→ 以修改后内容创建或更新正式对象
```

推荐不把每次输入中的修改内容即时写入正式候选历史。客户端可以暂存编辑草稿；本地核心只在最终提交时保存确认操作所需的用户修改内容。

确认成功后：

- 候选状态为“已修改后确认”；
- 正式对象使用用户修改后的内容；
- 原始记录和模型分析结果不被改写；
- 来源关系仍指向原始记录、分析结果和确认批次；
- 不把错误的模型中间版本写入正式对象。

### 问题 9：候选项有哪些状态？

**推荐答案：** 候选项采用以下生命周期：

```text
待确认
已确认
已修改后确认
已取消
已过期
```

| 状态 | 含义 | 是否产生正式对象变更 |
|---|---|---:|
| 待确认 | 候选已生成，用户尚未完成明确处理 | 否 |
| 已确认 | 用户保留原候选并确认，正式写入成功 | 是 |
| 已修改后确认 | 用户修改候选后确认，正式写入成功 | 是，写入修改后内容 |
| 已取消 | 用户取消、拒绝或放弃该候选 | 否 |
| 已过期 | 达到明确有效期，不能直接提交 | 否 |

一次确认事务失败时，候选不能标记为已确认或已修改后确认，仍保持可重试的待确认状态；失败原因记录在确认操作尝试或任务状态中，而不是增加候选失败终态。

### 问题 10：确认批次有哪些状态？

**推荐答案：** 确认批次采用：

```text
待处理
部分处理
已确认
已取消
已过期
```

| 批次状态 | 定义 |
|---|---|
| 待处理 | 尚未形成有效提交，仍有候选等待处理 |
| 部分处理 | 已有候选被确认、修改后确认或取消，但仍有候选待处理 |
| 已确认 | 所有候选均有最终处理结果，且需要写入的内容已成功提交；可以包含取消项 |
| 已取消 | 整个批次被放弃，或所有候选均取消/拒绝且没有正式写入 |
| 已过期 | 仍有未处理候选，但已达到明确有效期 |

必须区分：

```text
跨多次用户操作：允许批次处于部分处理
单次确认命令：不允许部分正式写入
```

例如：

```text
候选 A：已确认
候选 B：已修改后确认
候选 C：已取消
批次：已确认
```

这里“已确认”表示批次已经结案，不表示所有候选都被用户采纳。

如果整个批次从未产生正式对象，且所有候选都被取消或拒绝，则批次为“已取消”。

### 问题 11：省略候选项是否代表取消？

**推荐答案：** 不代表。

确认命令只提交用户明确处理的候选项：

```text
命令中明确确认 → 按确认处理
命令中明确修改后确认 → 按修改后确认处理
命令中明确取消 → 按取消处理
命令中省略 → 继续保持待确认
```

客户端不能通过“不提交某个候选”静默取消该候选。

## 3. 确认中心与其他能力的边界

### 3.1 与语音输入

语音存在两次不同性质的确认：

#### 第一次：确认发送语音转写

确认：

```text
这段转写是否代表用户要提交的原始输入？
```

结果：

- 确认后创建正式原始记录；
- 确认后才能开始内容分析；
- 确认前不提取事实、目标、行动或记忆；
- 确认前不进入正式 RAG。

#### 第二次：确认结构化业务变更

确认：

```text
模型提取出的目标、行动、记忆或状态变更是否正式生效？
```

两次确认不能混成一个按钮，也不能因为用户确认发送语音，就推断用户已经确认创建行动或保存记忆。

### 3.2 与事实和长期记忆

普通事实可以自动提取和保存，但必须携带：

```text
事实来源
事实时间
可信程度
是否用户明确表达
是否助手抽取
敏感标记
```

以下情况必须进入确认中心：

- 事实升级为长期记忆；
- 事实覆盖或使旧记忆过期；
- 事实改变正式目标、行动或处境模型；
- 事实成为重要决策或高风险建议的唯一依据。

### 3.3 与 RAG

待确认内容可以受限参与 RAG，但：

```text
可以召回
≠
可以当作已确认事实
≠
可以触发正式变更
```

| 内容 | RAG 使用方式 |
|---|---|
| 已确认目标、行动、记忆、决策和行动结果 | 正常参与 |
| 已保存原始记录 | 作为历史证据和补充上下文 |
| 自动抽取事实 | 携带可信度和来源，不默认视为当前有效 |
| 待确认目标、行动、记忆候选 | 可以受限召回，必须标记待确认 |
| 待确认建议 | 可以作为候选背景，不得据此自动创建行动 |
| 已取消候选 | 默认不作为普通建议正向依据 |
| 已过期记忆 | 普通建议排除，历史复盘允许使用 |
| 语音确认前临时转写 | 不进入正式 RAG |
| 已删除原始记录原文 | 不再检索原文 |
| 已彻底删除内容 | 不得召回 |

### 3.4 与敏感信息处理

确认中心处理的是业务变更确认；外部模型发送的隐私确认是另一条边界。

```text
业务确认：是否创建或修改正式对象
隐私确认：是否按设置允许特定内容对外发送
```

涉及敏感长期记忆或敏感外发时，确认卡片必须显式展示：

- 是否涉及敏感信息；
- 敏感类别；
- 本地将保存什么；
- 外部模型将收到什么处理后的内容；
- 是否已经脱敏；
- 用户是否需要单独确认外发。

确认业务变更不能替代隐私外发确认；隐私外发也不能替代业务变更确认。

### 3.5 与提醒和后台任务

后台任务可以生成建议、复盘结果、提醒和新候选，但不能绕过确认中心执行正式变更。

```text
每日摘要中的建议
→ 仍是建议
→ 用户要求创建行动
→ 生成确认候选
→ 用户确认
→ 创建正式行动
```

提醒点击后的操作：

| 用户操作 | 确认中心处理 |
|---|---|
| 查看行动 | 直接打开详情，不变更状态 |
| 完成 | 进入确认中心，确认后修改状态 |
| 延期 | 进入确认中心，确认新时间后修改并调整提醒 |
| 搁置 | 进入确认中心，确认后修改状态 |
| 关闭本次提醒 | 只关闭本次通知，不改变行动状态 |
| 稍后提醒 | 只调整提醒计划；不应静默修改业务状态 |

周复盘中的展示统计和分析可以直接呈现；目标调整、新行动、记忆更新、记忆过期、决策保存和正式提醒变更必须进入确认中心。

## 4. 确认命令

### 4.1 命令边界

客户端向 Local Core 提交确认命令，不直接修改数据库、正式对象或索引。

逻辑命令名称：

```text
SubmitConfirmationBatch
```

### 4.2 最小命令结构

```text
SubmitConfirmationBatch
├── confirmation_operation_id：本次提交的稳定唯一标识
├── confirmation_batch_id：确认批次标识
├── batch_version：客户端看到的批次版本
├── items：本次明确处理的候选项
│   ├── candidate_id：候选标识
│   ├── candidate_version：提交时看到的候选版本
│   ├── decision：confirm / modify_confirm / cancel
│   ├── modified_payload：仅修改后确认时提供
│   ├── target_object_id：更新既有对象时提供
│   ├── expected_target_version：更新既有对象时提供
│   └── risk_acknowledged：重要变更是否明确确认
├── client_source：客户端来源
└── command_fingerprint：命令内容指纹
```

本文件定义的是逻辑契约，不锁定具体传输协议或编程语言。

### 4.3 命令规则

1. `confirmation_operation_id` 由客户端为一次用户提交生成。
2. 网络重试、客户端超时重试必须复用同一个操作标识。
3. 同一操作标识与不同命令内容提交时，返回幂等键冲突，不执行写入。
4. 候选内容以 Local Core 已保存的候选为基础，客户端只提交明确的修改字段。
5. 客户端不能通过传入任意正式对象 ID 来创建未经候选授权的变更。
6. 更新既有对象必须同时提交对象标识和预期版本。
7. 重要变更必须明确提供风险确认。
8. 省略的候选项保持原状态，不被推断为取消。
9. 客户端时间只作为展示信息，正式确认时间由 Local Core 生成。

### 4.4 逻辑响应状态

建议至少区分：

```text
committed
already_committed
validation_failed
version_conflict
not_confirmable
risk_confirmation_required
retryable_failure
```

含义：

| 状态 | 含义 |
|---|---|
| committed | 本次确认成功并完成事务提交 |
| already_committed | 相同操作之前已经成功，返回历史结果 |
| validation_failed | 命令格式或业务校验失败 |
| version_conflict | 候选或正式对象版本变化，需要重新加载 |
| not_confirmable | 候选已取消、已处理、已过期或当前不可确认 |
| risk_confirmation_required | 重要变更尚未完成明确风险确认 |
| retryable_failure | 尚未提交成功，可以使用原操作标识重试 |

如果已经提交正式对象但索引实际更新失败，不返回确认失败，而应返回确认成功并标记索引待补偿。

## 5. 确认提交事务

### 5.1 单次提交必须全有或全无

一次 `SubmitConfirmationBatch` 提交中，正式写入必须是原子操作：

```text
全部正式写入成功
→ 提交成功

任一正式写入失败
→ 整体回滚
→ 不留下部分正式对象
```

同一个确认批次可以跨多次用户提交处于“部分处理”，但一次提交内部不允许部分成功。

### 5.2 成功事务包含的内容

一次确认成功时，在同一个事务边界内完成：

```text
校验候选状态和版本
+ 写入用户确认操作
+ 更新已处理候选项状态
+ 创建或更新正式目标 / 行动 / 记忆 / 决策
+ 写入来源关系
+ 写入关键变更记录
+ 登记索引更新任务
+ 更新确认批次状态
```

索引任务登记必须和正式对象写入一起成功登记；索引的实际计算和写入可以异步执行。

### 5.3 取消项与未提交项

- 明确取消的候选在本次事务中标记为已取消。
- 本次命令未提交的候选保持待确认。
- 取消项不会阻塞其他候选的确认。
- 所有候选都取消且未产生正式对象时，批次变为已取消。
- 已有正式写入后，剩余候选全部取消时，批次变为已确认，表示批次结案。

### 5.4 事务失败后的状态

确认事务失败时：

```text
正式对象：不产生部分结果
来源关系：回滚
关键变更记录：回滚生效记录
索引任务登记：回滚
候选：保留可重试状态
确认批次：保持待处理或部分处理
确认操作：不得标记为已生效
```

失败尝试可以记录最小错误摘要，但不能把失败尝试伪装成已确认操作。

## 6. 幂等、并发和超时

### 6.1 重复提交

相同 `confirmation_operation_id` 的相同命令再次提交：

- 不重复创建正式对象；
- 不重复更新正式对象；
- 不重复写入关键变更；
- 不重复登记业务索引任务；
- 返回第一次提交的结果。

相同操作标识但命令内容不同：

```text
返回幂等键冲突
→ 不执行任何写入
```

### 6.2 同批次并发提交

同一批次使用不同操作标识并发提交时：

- 只有满足版本校验的请求可以成功；
- 其他请求因为候选已处理或版本冲突失败；
- 失败请求不能覆盖已经成功的结果；
- 不得创建重复正式对象。

### 6.3 乐观并发控制

至少校验两层版本：

#### 候选项版本

```text
candidate_id
+ candidate_version
+ 候选当前仍可确认
+ 候选属于指定批次
```

#### 正式对象版本

更新既有对象时校验：

```text
target_object_id
+ expected_target_version
+ 对象未删除
+ 当前状态允许该变更
```

不建议只使用 `updated_at` 判断冲突，应使用单调递增版本号；时间字段只用于展示和审计。

### 6.4 客户端超时

```text
客户端提交确认
→ 客户端未收到响应
→ 不生成新的操作标识
→ 使用原操作标识查询操作状态
→ 已提交：返回原正式对象结果
→ 未提交：使用原操作标识重试
```

客户端不能因为不确定结果而创建第二个确认操作。

## 7. 高风险变更

### 7.1 必须显式展示影响的场景

至少包括：

- 保存敏感长期记忆；
- 修改目标截止时间；
- 标记旧记忆过期；
- 删除或彻底删除对象；
- 创建涉及金钱的行动；
- 创建涉及人员的行动；
- 创建涉及工作安排的行动；
- 创建涉及重要文件的行动；
- 将低可信度或待确认事实作为重要变更依据。

### 7.2 风险卡片信息

高风险候选至少展示：

```text
变更类型
影响对象
变更前内容或状态
变更后内容或状态
可能影响
成本或风险
是否涉及敏感信息
是否可撤销
信息是否待确认、过期或低可信度
```

### 7.3 风险确认

普通候选可以批量确认；重要候选必须显式完成风险确认。

破坏性操作采用两步确认：

```text
第一次：确认用户理解将发生的删除或物理清除
第二次：确认执行不可逆或高风险操作
```

“默认全选”不能替代风险确认。

## 8. 撤销

### 8.1 撤销原则

撤销是新的反向操作，不删除原确认记录：

```text
原确认操作
→ 正式对象变更
→ 用户请求撤销
→ 校验仍可逆且没有后续冲突
→ 写入反向变更
→ 写入新的撤销操作和关键变更记录
```

### 8.2 建议支持撤销的范围

- 本地创建的目标、行动或记忆：可撤销为软删除、取消或归档；
- 行动状态变化：在对象没有后续修改时恢复原状态；
- 目标截止时间修改：在没有后续修改时恢复旧时间；
- 记忆过期或内容更新：在没有后续变更时恢复旧版本；
- 同一确认批次产生的多个本地对象：建议以确认操作为单位撤销。

### 8.3 不承诺撤销的范围

- 已物理彻底删除的数据；
- 已经发生的外部副作用；
- 已被后续操作修改的对象；
- 无法安全恢复原状态的破坏性操作；
- 已被后续对象合并或替代且无法确定恢复结果的操作。

### 8.4 撤销冲突

```text
当前对象版本 ≠ 原确认操作产生的版本
→ 拒绝自动撤销
→ 提示对象已有后续变化
→ 要求用户查看当前状态
→ 如需修改，生成新的确认候选
```

撤销本身也必须有幂等标识，重复点击不得重复生成反向操作。

撤销入口的保留时间、最近一次操作范围、多对象批次是否支持逐项撤销，继续由确认中心详细交互或删除子需求确定。

## 9. 错误和恢复

### 9.1 命令或业务校验失败

包括：

- 命令字段缺失或格式错误；
- 确认批次不存在；
- 候选不存在；
- 候选已经处理；
- 候选已取消或已过期；
- 候选版本冲突；
- 正式对象版本冲突；
- 状态转移不允许；
- 正式对象已删除；
- 风险确认缺失。

处理：

```text
不写入正式对象
不改变其他候选
返回明确错误原因
必要时要求重新加载确认卡片
```

### 9.2 确认事务失败

包括：

- 结构化数据库写入失败；
- 正式对象写入失败；
- 来源关系写入失败；
- 关键变更记录写入失败；
- 索引任务登记失败。

处理：

```text
整体回滚
正式对象不留下部分结果
候选和批次保留可重试状态
使用原 confirmation_operation_id 重试
```

### 9.3 正式对象成功、索引实际更新失败

```text
正式对象保留
确认结果保持成功
索引任务进入失败待重试
结构化查询继续可用
```

用户看到的状态应为：

```text
确认已完成，搜索索引稍后更新
```

而不是“确认失败”。

### 9.4 进程崩溃或任务重复执行

依靠以下内容恢复：

- 数据库事务；
- 用户确认操作幂等标识；
- 候选版本；
- 正式对象版本；
- 后台任务幂等键；
- 关键变更记录。

已提交事务不能重复应用，未提交事务不能留下半成品。

## 10. 确认中心与建议生命周期

建议必须与行动分开：

```text
建议生成
→ 用户采纳或拒绝
→ 用户要求创建行动
→ 生成行动候选
→ 用户确认
→ 正式行动创建
→ 用户开始执行
→ 行动完成或中断
→ 记录结果
→ 周复盘评价建议效果
```

### 每日摘要

每日摘要可以直接展示：

- 最推荐行动；
- 一到两个备选行动；
- 推荐原因；
- 依据和历史结果；
- 待确认内容。

但摘要中的新行动不能自动进入正式行动列表。

### 周复盘

周复盘可以直接展示：

- 完成和未完成行动；
- 延期、过期和搁置情况；
- 目标进展；
- 计划与实际差异；
- 建议效果分析；
- 未完成原因。

周复盘提出的以下变更必须进入确认中心：

- 调整目标；
- 修改目标截止时间；
- 创建下周行动；
- 更新长期记忆；
- 使旧记忆过期；
- 保存决策记录；
- 修改处境模型中的正式状态；
- 变更提醒计划。

## 11. 建议的确认中心查询

客户端需要能够查询：

```text
待处理确认批次
批次详情
候选项详情
候选来源
候选当前版本
候选风险标记
候选是否敏感
用户最近处理时间
下次提醒时间
```

查询结果需要显示：

- 候选内容；
- 候选类型；
- 来源记录；
- 当前状态；
- 是否敏感；
- 是否高风险；
- 可能影响；
- 用户是否已经修改；
- 正式对象是否已经存在；
- 依据和相关上下文。

查询接口不能直接返回内部数据库路径、外部模型密钥或不必要的敏感原文。

## 12. 与原始记录和存储的关系

确认中心依赖以下对象：

```text
OriginalRecord
AnalysisRun
StructuredAnalysis
CandidateItem
ConfirmationBatch
UserConfirmationAction
SourceRelation
ChangeHistory
IndexUpdateJob
```

确认成功后的最小来源链：

```text
正式对象
→ 用户确认操作
→ 候选项
→ 结构化分析结果
→ 分析运行
→ 原始记录
```

删除原始记录后：

- 确认操作和正式对象不自动删除；
- 正式对象保留必要的来源摘要；
- 来源显示为原始记录已删除；
- 已删除原始正文不再进入普通 RAG。

## 13. 自问自答后的默认决策汇总

本文件采用以下推荐方案：

1. 确认中心是所有正式业务变更的统一入口。
2. 正式目标的创建和修改统一需要确认。
3. 一条输入对应一份分析结果，多个候选组成一个确认批次。
4. 候选项独立处理，默认全选不等于确认。
5. 暂不处理保持待确认，只调整提醒或处理记录。
6. 拒绝和取消在候选生命周期上统一为已取消。
7. 再次提出必须生成新的候选，不直接恢复旧候选。
8. 修改后的内容只有在明确提交后才生效。
9. 单次确认提交全有或全无，跨多次提交可以处于部分处理。
10. 客户端只能提交确认命令，Local Core 负责校验和正式写入。
11. 同一确认操作标识重试必须幂等。
12. 候选和正式对象都采用乐观版本校验。
13. 确认成功事务包含正式对象、来源关系、关键变更记录和索引任务登记。
14. 索引实际更新异步执行，索引失败不回滚正式对象。
15. 风险变更必须显式展示影响，彻底删除必须二次确认。
16. 撤销通过新的反向操作完成，不删除原操作历史。
17. 语音发送确认和结构化业务确认是两次不同确认。
18. 事实可以自动抽取，但不能自动升级为用户确认事实或长期记忆。
19. 后台任务可以产生候选和提醒，但不能绕过确认中心写入正式对象。
20. 建议、采纳、创建行动、执行和效果评价保持独立生命周期。

## 16. 验收标准

### 确认展示

- 普通闲聊和只有摘要的问题不会强制展示确认卡片。
- 识别到正式目标、行动、记忆或其他正式变更候选时展示确认卡片。
- 确认卡片展示不会造成正式对象提前创建。

### 候选生命周期

- 默认全选仍保持待确认状态。
- 候选可以逐项修改、取消或暂不处理。
- 暂不处理不会变成取消。
- 拒绝和取消进入已取消。
- 已取消候选不会被直接恢复为待确认。
- 再次提出会生成新的候选标识。

### 正式写入

- 创建和修改正式目标需要确认。
- 创建行动、修改行动状态和保存长期记忆需要确认。
- 未确认候选不能创建正式对象。
- 确认事务失败不会留下部分正式对象。
- 确认成功会记录来源、关键变更和索引任务。

### 幂等和并发

- 重复提交相同操作不会重复创建对象。
- 相同操作标识提交不同内容会被拒绝。
- 客户端超时后使用原操作标识查询或重试。
- 候选版本或正式对象版本冲突时不会静默覆盖。

### 风险和撤销

- 高风险候选显式展示影响、成本和风险。
- 彻底删除需要二次确认。
- 撤销不会删除原确认记录。
- 对象发生后续修改时不会自动强制撤销。

### 交叉边界

- 语音转写确认前不进入结构化分析和 RAG。
- 待确认内容进入 RAG 时携带待确认状态。
- 敏感外发确认与业务变更确认不混淆。
- 后台任务不能绕过确认中心创建正式行动或保存记忆。
