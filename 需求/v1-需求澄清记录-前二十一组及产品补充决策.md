# v1 需求澄清记录：前二十一组及产品补充决策

## 文档目的

本文档用于追踪个人助手第一期需求讨论结果，作为后续需求拆分、设计和实现的基准，避免因遗忘或理解偏移导致范围变化。

本文档记录的是**截至 2026 年 9 月 4 日**已经确认的内容，不代表所有第一期需求已经完成。未确认内容必须继续保留为待讨论项，不得擅自视为已决定。

## 1. 产品定位与第一期范围

### 1.1 已确认结论

- 当前只验证个人使用，暂不以通用产品化为第一目标。
- 未来可以再考虑产品化。
- 不重复建设基础模型、通用聊天、通用搜索、语音识别、OCR 或模型训练等底层能力；优先调用现有模型和成熟服务。
- 产品核心方向是“属于个人自己的智能层”，而不是另一个与豆包、DeepSeek 竞争的通用聊天智能体。
- 第一阶段处于需求整理阶段，后续复杂任务点应拆分为独立子文件。
- 采用 `v1`、`v2` 等版本标记实现顺序。

### 1.2 第一阶段的总体愿景

```text
随时表达
→ 助手理解当前意图、情绪和处境
→ 陪伴聊天 / 辅助解答 / 想法梳理 / 经历回顾
→ 根据用户需要进入查找、分析或行动协助
→ 需要正式保存或改变状态时由用户确认
→ 持续交流并根据结果更新对用户的理解
```

### 1.3 第一阶段优先级

用户希望第一期围绕以下三条并列主线提供体验：

1. 陪伴聊天
2. 辅助解答
3. 行动协助

个人记忆、当前处境、经历回顾和知识整理作为支撑能力，让助手能够持续了解用户；行动协助只在用户需要时展开，不是所有聊天的默认终点。

### 1.4 设备

- 手机和电脑都需要支持。
- 两者使用比例尽量接近。
- 第一阶段入口应优先保证手机和电脑都能直接使用。

## 2. 第一组：服务对象与核心价值

### 问题 1：第一期主要服务谁？

**回答：** 目前只验证个人使用，未来再考虑产品化。

**需求结论：** 第一版以单个用户、即用户本人为唯一服务对象，不提前为多用户、账号体系或通用人群扩展范围。

### 问题 2：每天最希望解决的一个问题是什么？

**回答：** 记录整理、知识管理、决策辅助、目标执行、长期记忆等其实都有需要。

**需求结论：** 这些都是产品长期需求，但第一期必须通过优先级和核心闭环控制范围，不能平均实现。

### 问题 3：第一期只能证明一件事，希望证明什么？

**回答：** 以上能力其实都想要，包括越来越了解用户、帮助决策、促进执行、整理知识和降低整理成本。

**需求结论：** 第一阶段同时验证陪伴聊天、辅助解答和行动协助三条主线，重点观察助手是否能持续理解用户，并在用户需要时提供合适的聊天、解答或行动帮助。

### 问题 4：预计使用设备？

**回答：** 手机为主，电脑为辅，但希望两者尽量相等。

**需求结论：** 不能只按手机端或只按电脑端设计；第一期需要兼顾手机和电脑的基础使用体验。

## 3. 第二组：第一期主闭环

### 问题 1：优先把哪类内容交给助手？

**回答：** `E`，以上内容都可以输入，但先不区分入口。

**需求结论：** 第一阶段允许输入个人想法、经历、问题、灵感、网页、书籍、文件等多种内容，不要求用户先选择内容类型。

### 问题 2：第一期最主要输出什么？

**回答：** `B`，告诉用户“我现在最应该做什么”。

**需求结论：** 助手的输出根据用户当前需要，可以是自然陪伴、情绪和想法梳理、问题解答、经历回顾、建议分析，也可以在用户需要时转化为可执行的行动。

### 问题 3：更倾向哪种使用方式？

**回答：** `D`，三种都要，但第一期以 `C` 为主：用户输入后，助手主动追问、提醒和跟进。

**需求结论：** 第一阶段不是只做被动问答，也不是把所有输入都任务化。用户输入后，助手需要先理解用户当前意图，在适合时主动澄清、陪伴、解答、梳理或提出行动建议，并根据用户需要进行后续跟进。

### 问题 4：五类价值排序

**回答：**

```text
陪伴聊天 + 辅助解答 + 行动协助
```

**需求结论：** 见“1.3 第一阶段优先级”。

## 4. 第三组：行动执行

### 问题 1：判断“最应该做什么”的依据

**第一期必须考虑：**

- 当前明确目标
- 截止日期
- 事情的重要程度
- 当前可用时间
- 资金、人员、技术等现实限制
- 过去类似事情的执行效果

**暂未列为第一期必需因素：** 紧急程度、当前精力、最近反复提及但一直未行动等。这些可以作为后续增强项，不能在未讨论前默认加入核心范围。

### 问题 2：行动输出粒度

**回答：** 较细。

**需求结论：** 默认输出可以立即开始的下一步行动，而不是宽泛方向。例如将“开始设计个人助手”拆成今天可以执行的具体步骤。

### 问题 3：什么时候算创建行动？是否需要确认？

**回答：** 用户提到问题时，助手主动建议行动，但创建行动前需要用户确认。

**需求结论：**

```text
用户输入问题或目标
→ 助手识别并提出可能行动
→ 用户确认
→ 才创建正式行动
```

助手不得未经确认直接创建行动。

### 问题 4：行动状态

**回答：** 最好有状态机。

**已采纳的初步状态机：**

```text
待确认
  ↓
待开始
  ↓
进行中
  ├── 已完成
  ├── 已延期
  ├── 暂时搁置
  └── 已取消
```

状态含义：

- `待确认`：助手提出建议，等待用户确认。
- `待开始`：用户已确认，但尚未开始。
- `进行中`：用户已经开始执行。
- `已完成`：行动完成，并可记录结果。
- `已延期`：仍然要做，但计划时间发生变化。
- `暂时搁置`：暂时不继续，未来可能恢复。
- `已取消`：明确不再执行。

具体状态转移规则、字段和异常情况仍需单独整理。

### 问题 5：主动跟进方式

**回答：**

- 每天生成一次行动摘要
- 到时间提醒
- 每周进行一次目标复盘

**需求结论：** 第一阶段需要日摘要、定时提醒和周度目标复盘。提醒频率、提醒渠道和用户时区等细节后续确定。

## 5. 第四组：输入方式与入口

### 问题 1：第一期开通的输入类型

**回答：**

- 文字
- 语音
- 图片
- 网页链接
- 文件上传

**需求结论：** 以上五种输入类型纳入第一期范围。它们共用统一的输入界面，不要求用户先选择“记录、目标、任务、记忆”等类别。

### 问题 2：自动提取内容

**回答：**

- 内容摘要
- 事实
- 问题
- 可保存的长期记忆
- 需要用户确认的内容

**补充采纳的建议：** 为了支持行动执行，助手还需要提取或识别以下行动相关信息：

- 目标
- 可能的行动
- 截止时间
- 现实限制

因此第一期的处理结果可以包含：

```text
内容摘要
事实
问题
目标
可能的行动
截止时间
现实限制
可保存的长期记忆
需要用户确认的内容
```

其中，目标、行动、长期记忆等内容必须遵守对应的确认规则。

### 问题 3：一段内容包含多个事项时如何处理？

**回答：** 自动拆成多个目标和行动，但创建行动前统一确认。

**需求结论：**

```text
一段输入
→ 自动拆分多个目标、问题和可能行动
→ 统一展示分析结果
→ 用户确认
→ 创建确认后的行动
```

### 问题 4：使用入口如何设计？

经过大白话说明后，**最终确定为：**

```text
打开 App
→ 直接发送文字消息
或
→ 开启语音输入
```

打开 App 后不需要先选择记录类型，直接像聊天一样输入即可。

语音输入流程为：

```text
点击语音输入
→ 录音
→ 转换成文字
→ 用户检查和修改
→ 用户确认发送
→ 助手开始分析
```

语音识别文本不能未经用户确认直接发送、提取记忆或创建行动。

图片、网页链接和文件上传属于第一期输入能力，但具体入口交互后续单独细化。

## 6. 第五组：发送后的交互与确认

### 问题 1：语音输入是否先显示文字？

**回答：** 必须先显示文字，用户确认后才发送。

**需求结论：** 见“5. 问题 4：使用入口如何设计”。

### 问题 2：什么时候展示结构化分析？

**回答：** 只在助手判断内容中有目标、行动或记忆时才展示结构化内容。

**需求结论：**

- 普通闲聊和一般性问题不强制展示结构化卡片。
- 识别到目标、可能行动或长期记忆候选时，展示结构化分析内容。
- 结构化内容用于确认，不代表已经完成正式写入。

### 问题 3：用户不确认时如何处理？

**回答：** 暂存为“待确认内容”，之后再次询问。

**需求结论：**

```text
识别结果
→ 暂存为待确认内容
→ 在后续合适时机再次询问
→ 用户确认后才正式生效
```

待确认内容不能自动成为正式行动或长期记忆。

### 问题 4：哪些内容必须用户确认？

**回答：**

- 创建行动
- 修改行动状态
- 保存长期记忆

**需求结论：** 以上三类操作是第一期的强制确认边界。助手可以主动提出建议，但必须在用户确认后执行对应变更。

## 7. 第六组：长期记忆

### 问题 1：哪些内容可以成为长期记忆？

**回答：** 感觉都可以。

**已采纳的具体化建议：** 只要内容对长期理解用户有帮助，都可以由助手提出为候选记忆，但必须经过用户确认后正式保存。

第一期候选记忆类型包括：

- 个人基本信息
- 长期偏好
- 长期目标
- 现实限制
- 重要经历
- 能力与资源
- 价值观和判断标准
- 决策经验

第一期不为每种类型设计完全不同的复杂流程，统一采用记忆内容、类型、来源、确认状态和时间信息进行管理。

### 问题 2：长期记忆保存哪些附加信息？

**回答：** 采纳建议内容。

**第一期每条记忆建议保留：**

```text
记忆内容
来源
创建时间
最后确认时间
可信程度
是否由用户明确表达
是否由助手推断
```

补充建议：还应有当前状态和确认状态，以便区分当前有效、已过期、待确认等情况。

### 问题 3：旧记忆如何更新？

**回答：** 将旧记忆标记为过期，再保存新记忆。

**需求结论：**

```text
发现新内容与旧记忆冲突
→ 旧记忆标记为过期或不再适用
→ 保存新的当前记忆
→ 保留旧记忆及其来源
```

不直接覆盖历史。这样可以在后续决策复盘时还原当时的目标和限制。

### 问题 4：第一期如何查看和管理记忆？

**回答：**

- 查看所有长期记忆
- 查看记忆来源
- 按类型筛选
- 先通过聊天管理
- 后台需要结构化或文档形式存储好

**已采纳的存储方案：** 后台同时保留原始文档、结构化数据和检索索引，三者不互相替代。

```text
原始记录 / 文档
        +
结构化数据
        +
检索索引
```

原始记录用于追溯和重新分析；结构化数据用于查询、筛选、关联目标和行动；检索索引用于查找相关历史内容。

**第一期管理方式：**

- 主要通过聊天查看、修改和删除记忆。
- 同时提供简单的长期记忆列表页面。
- 列表至少支持查看全部记忆、按类型筛选、查看记忆来源和查看当前有效/已过期状态。
- 复杂的独立记忆管理后台暂不作为第一期重点。

## 8. 第一阶段确认规则汇总

| 内容或操作 | 是否自动识别 | 是否需要用户确认 | 未确认时的处理 |
| --- | --- | --- | --- |
| 原始输入 | 是 | 否 | 自动保存原始记录 |
| 内容摘要 | 是 | 否 | 作为分析结果或记录内容保留 |
| 事实 | 是 | 否 | 暂作为普通分析内容，不自动升级为长期记忆 |
| 问题 | 是 | 否 | 作为上下文保留 |
| 目标 | 是 | 视是否需要正式记录而定 | 暂存为待确认内容 |
| 可能行动 | 是 | 是 | 暂存为待确认内容 |
| 创建行动 | 否 | 是 | 不创建 |
| 修改行动状态 | 否 | 是 | 不修改 |
| 长期记忆候选 | 是 | 是 | 暂存为待确认内容 |
| 保存长期记忆 | 否 | 是 | 不保存为正式记忆 |

## 9. 已确认的第一期闭环

```text
打开 App
→ 进入聊天首页
→ 发送文字，或录音并确认转写文字
→ 可附加图片、网页链接或文件
→ 助手先理解当前意图并自然回应
→ 根据用户需要进入陪伴聊天、辅助解答、想法梳理、经历回顾或行动协助
→ 需要个人上下文时按需检索相关记录
→ 需要结构化处理时按需生成分析、建议或候选
→ 只有正式保存或业务状态变更才进入确认中心
→ 确认后创建或修改正式对象
→ 继续陪伴、解答、行动追踪和每日摘要
```

## 10. 第七组：数据保存和隐私边界

### 问题 1：数据主要保存在哪里？

**回答：** 可以先本地，后期要服务器。

**需求结论：**

```text
v1：保存于用户控制的私有核心主机
v2 或后续：多个核心之间同步和冲突处理
```

第一期的数据结构和业务逻辑不能绑定某一个具体部署位置；v1 的业务权威数据统一保存在用户控制的私有核心主机 PostgreSQL 中。

### 问题 2：调用外部模型时是否允许发送个人数据？

**回答：** 允许发送，但个人助手接收的内容不脱敏；发送给大模型之前需要提醒或脱敏。

**需求结论：**

```text
个人助手本地接收原始内容
→ 原始内容可以不脱敏地保存在个人数据中心
→ 发送给外部大模型前识别敏感信息
→ 根据设置提醒或脱敏
→ 再发送给大模型
```

核心原则是：本地保存保留完整上下文，对外发送进行敏感信息保护，并遵循最小必要发送原则。

### 问题 3：第一批敏感信息

**回答：**

- 身份证件
- 银行卡
- 密码
- 密钥

**需求结论：** 第一阶段必须在外部模型调用前识别以上敏感信息。其他敏感类别暂不列为第一期强制识别范围。

### 问题 4：是否保留模型调用记录？

**回答：** 只保留基础调用记录。

**需求结论：** 第一阶段只保留：

- 使用的模型
- 调用时间
- 任务类型
- 是否调用个人记忆

第一期不把完整模型输入上下文和模型原始返回内容作为详细调用日志保存。

### 问题 5：数据导出

**回答：** Markdown、JSON 和原始文件压缩包都需要。

**需求结论：** 第一阶段需要支持导出：

- Markdown：便于人阅读和长期保存
- JSON：便于程序处理和数据迁移
- 原始文件压缩包：保留图片、音频、网页和上传文件

## 11. 第八组：敏感信息处理和本地保护

### 问题 1：发送前的敏感信息处理方式

**回答：** 通过设置统一配置处理模式（D）。

**需求结论：** 敏感信息处理方式由设置控制，第一阶段需要支持“提醒或脱敏”的处理策略配置。具体设置项和默认模式后续细化。

### 问题 2：脱敏后是否继续发送？

**回答：** 脱敏后继续发送。

**需求结论：**

```text
本地识别敏感信息
→ 按配置提醒或脱敏
→ 脱敏内容继续发送给外部大模型
```

### 问题 3：敏感信息是否写入长期记忆？

**回答：** 写入长期记忆。

**需求结论：** 在用户确认后，敏感信息可以写入本地长期记忆。敏感信息在发送给外部模型时仍必须先经过拦截和脱敏。

### 问题 4：本地数据保护

**回答：** 需要保护，已明确第一期需要：

- 应用登录或设备解锁
- 导出文件加密或设置密码

**需求结论：** 打开助手前需要进行应用访问保护；导出 Markdown、JSON 和原始文件压缩包时支持加密或设置密码。

以下内容暂未确认，不得擅自加入第一期：本地数据库加密、原始文件单独加密、多设备同步、退出账号清除缓存、远程撤销或远程清除。

## 12. 第九组：模型接入策略

### 已确认结论

- 使用现成的模型接入框架，不自行实现完整的模型供应商适配体系。
- 通过以下通用配置接入模型：

```text
Base URL
+ API Key
+ Model ID
```

- 第一阶段可以配置多个模型。
- 发送消息前可以随时切换模型。
- 单次消息处理默认使用发送时选中的一个模型，不按任务类型自动路由。
- 模型列表中的其他模型作为失败后的重试候选，不设置固定的“主模型”和“备用模型”。

### 模型调用和重试流程

```text
用户选择当前模型和推理思考等级
→ 调用当前模型
→ 失败后自动重试
→ 仍失败则按模型列表当前顺序尝试其他模型
→ 全部失败后提示用户
```

敏感信息拦截和脱敏必须在每一个模型请求发出之前执行，包括切换到其他模型的请求。

## 13. 第十组：模型配置

### 每个模型配置的字段

```text
供应商名称
Base URL
API Key
Model ID
```

### 已确认功能

- API Key 保存在本地加密存储中。
- API Key 保存在用户控制的私有核心主机加密存储中；v1 不做多个核心之间的同步。
- 设置中需要提供测试连接功能。
- 模型列表显示供应商名称和 Model ID。
- 模型选择时显示并支持选择推理思考等级。
- 模型列表支持手动拖动排序。
- 列表当前顺序决定失败后的重试顺序。
- 系统不会因为某次失败自动改变模型列表顺序。
- 模型调用失败时默认简洁展示切换过程，用户可以展开查看失败模型、失败原因、重试顺序和最终成功模型。

### 测试连接

测试连接至少检查：

- Base URL 是否可访问
- API Key 是否有效
- Model ID 是否可调用
- 返回格式是否符合接入框架要求

## 14. 第十一组：推理等级与模型选择行为

### 推理思考等级

采用默认值和当前消息临时调整的方式：

```text
设置中配置默认推理等级
→ 发送前可以临时调整
→ 当前消息使用临时选择
→ 不改变默认配置
```

### 模型选择记忆

- 自动记住上次使用的模型。
- 下次发送消息时默认使用上次选择的模型。

### 重试时的推理等级

当前消息选择的推理思考等级在所有重试模型中保持一致。

## 15. 第十二组：结构化结果确认方式

### 已确认交互

助手发现目标、行动或长期记忆候选后：

```text
默认全部选中
→ 用户展开查看
→ 用户可以逐项取消或修改
→ 一次确认完成选中内容的保存或创建
```

一次确认可以同时完成不同类型的操作，例如保存目标、创建行动和保存长期记忆。

### 用户修改结构化内容

```text
保留原始输入
→ 用户修改结构化内容
→ 以修改后的内容作为正式结果
→ 不额外保存错误的中间识别版本
```

### 用户拒绝候选内容

本次不保存，但未来如果新的上下文仍然支持该判断，助手可以再次提出建议。

### 待确认内容

```text
内容未确认
→ 暂存为待确认内容
→ 下一次打开 App 时提醒
→ 用户也可以主动进入待确认内容列表处理
```

## 16. 第十三组：目标、行动与决策

### 目标与行动

- 一个目标可以包含多个行动。
- 行动可以独立存在，也可以关联目标。
- 一个行动可以关联多个目标。
- 目标需要独立状态机。
- 行动和目标的状态不简单强绑定。

目标初步状态为：

```text
规划中
进行中
已完成
已暂停
已放弃
已过期
```

### 重要决策

助手识别到重要选择时，可以主动建议建立决策记录；用户确认后保存。

决策记录支持以下字段，有则保存、无则留空：

```text
决策内容
当时目标
可选方案
选择理由
当时的限制条件
预期结果
计划验证时间
实际结果
复盘结论
```

## 17. 第十四组：目标和行动的完成判断

### 行动完成

```text
助手识别到用户可能已经完成行动
→ 询问用户是否完成
→ 用户确认
→ 行动变为已完成
```

“差不多完成了”由用户手动选择如何处理，第一期不增加“部分完成”状态。

### 行动结果

行动完成后，助手自动提取执行结果；有则保存，无则留空。

### 目标完成

```text
用户直接确认目标完成
或
助手根据相关行动完成情况提出确认
→ 用户确认
→ 目标变为已完成
```

目标不能仅因为所有行动完成就自动完成。

### 状态含义

- **延期**：仍然要做，但截止日期发生调整。
- **过期**：截止日期已到，但尚未完成，也尚未决定下一步。
- **暂停**：主动暂时不做，未来可能恢复。
- **放弃 / 取消**：明确不再继续。

### 复盘

行动完成时先保存结果，每周目标复盘时统一分析，不在每个行动完成后立即打断用户复盘。

## 18. 第十五组：每日摘要、提醒和每周复盘

### 每日行动摘要

采用以下默认内容：

- 今天需要完成的行动
- 即将到期或已经过期的行动
- 当前最重要的目标
- 助手建议今天优先做什么
- 待确认内容

### 生成时间

```text
每天固定时间生成一次
→ 如果当天尚未生成
→ 用户当天第一次打开 App 时补生成
```

### 到时间提醒

采用：

- 有明确截止时间的行动自动提醒
- 用户也可以手动设置提醒

提醒内容和交互为：

```text
提醒行动
→ 展示行动内容
→ 用户可以选择完成、延期或搁置
→ 也可以直接回复当前进展
→ 助手根据确认结果更新状态
```

### 每周目标复盘

每周复盘内容不限定为单一字段，相关信息都有参考价值，包括：

- 本周完成的行动
- 本周未完成的行动
- 延期、过期和搁置的行动
- 各目标当前进展
- 未完成原因
- 实际花费时间
- 计划与实际的差异
- 哪些建议有效
- 哪些建议没有效果
- 是否需要调整目标
- 是否需要更新长期记忆
- 下周最重要的行动

### 复盘后的变更

周复盘可以提出以下建议：

- 调整目标
- 修改截止时间
- 更新长期记忆
- 记录决策经验
- 新增下周行动

涉及正式变更的内容仍然必须经过用户确认。

## 19. 更新后的第一阶段闭环

```text
打开 App
→ 进入聊天首页
→ 选择或默认使用上次模型，并选择推理思考等级
→ 发送文字，或录音并确认转写文字
→ 可附加图片、网页链接或文件
→ 保存用户消息和原始输入
→ 判断当前更适合陪伴聊天、辅助解答、想法梳理、经历回顾或行动协助
→ 需要个人上下文时按需检索相关记录
→ 模型请求通过统一敏感信息策略，按设置提醒或脱敏
→ 返回自然聊天、解答、梳理、回顾或行动协助结果
→ 仅在实际需要时生成结构化分析、建议或候选
→ 正式保存或业务状态变更进入确认中心
→ 确认后创建或修改正式对象
→ 继续交流、行动追踪、每日摘要和提醒
```

## 20. 第十六组：数据对象与记录边界

### 原始记录

确定为：

```text
每次用户发送内容
→ 自动形成一条原始记录
```

文字、语音转写、图片、网页链接和文件属于该记录的内容或附件。

### 聊天与原始记录

采用分层关系：

```text
聊天会话
├── 用户消息 → 独立原始记录
├── 助手回复
└── 结构化分析结果
```

聊天负责交互上下文，原始记录负责长期保存、检索和追溯。

### 原始内容与分析结果

```text
原始记录：自动保存
结构化分析结果：保存
正式目标、行动、记忆：确认后才创建或写入
```

候选结果可以保存，但不能直接当作正式对象使用。

### 多个候选项

```text
一次输入
→ 一个结构化分析结果
→ 包含多个独立候选项
→ 每个候选项有自己的确认状态
→ 用户可逐项取消或修改
→ 一次确认
→ 分别创建目标、行动或长期记忆
```

### 事实与长期记忆

所有长期记忆都应有事实或原始记录作为来源，但不是所有事实都会成为长期记忆。

```text
事实：从原始记录中提取出的陈述
长期记忆：经过确认、允许未来持续使用的内容
```

### 删除原始记录

```text
删除原始记录
→ 已确认的目标、行动和记忆不自动删除
→ 原始来源标记为“已删除”
→ 结构化数据保留必要来源摘要
```

## 21. 第十七组：记忆和历史信息调用

### 默认上下文

助手默认结合以下内容回答和建议：

```text
当前目标
+ 当前行动
+ 截止时间
+ 当前有效限制
+ 相关长期记忆
+ 相关历史结果
+ 最近相关记录
```

不默认读取全部历史。

### RAG 检索

确定采用：

```text
结构化条件筛选
+ RAG 关键词 / 语义检索
+ 模型综合判断
```

结构化数据优先，原始记录作为补充和证据。

### 过期记忆

```text
普通建议：只使用当前有效记忆
历史复盘：允许读取过期记忆
```

### 建议依据

默认折叠展示，用户可以展开查看本次使用的目标、行动、记忆和历史记录。

### 低可信度信息

根据问题重要程度处理：

- 普通问题：可以谨慎参考。
- 重要决策：提示信息可能过期或不确定。

### 敏感记忆

敏感记忆和普通记忆一样可以参与检索，但发送给外部模型前必须脱敏。

## 22. 第十八组：RAG 检索范围和引用规则

### 进入 RAG 的内容

主要检索：

- 原始记录
- 已确认长期记忆
- 目标
- 行动及执行结果
- 决策及复盘结果

谨慎检索：

- 待确认内容
- 已过期内容

待确认内容必须带状态，不能作为已确认事实使用；过期内容只在历史复盘等场景使用。

### 检索结果来源

每条检索结果应携带：

```text
内容
来源类型
来源记录
发生时间
当前状态
可信度
是否用户确认
是否敏感
```

发送给外部模型时，仅发送必要的内容、时间、状态和可信度，不发送内部 ID、路径和数据库字段。

### 找不到相关信息

```text
没有找到相关记录
→ 明确告诉用户
→ 若需要推测，明确标记为推测
→ 询问用户是否补充或重新建立记录
```

### 删除后的检索

已删除原始记录不再检索原文，但已确认的结构化目标、行动和记忆仍可检索；来源显示为“原始记录已删除”。

## 23. 第十九组：RAG 数据更新和结果控制

### 更新时机

```text
原始记录保存后立即进入 RAG
→ 结构化候选标记为待确认
→ 用户确认后更新为正式对象
```

### 过期记忆

```text
旧记忆保留
→ 标记为过期
→ 普通建议排除
→ 历史复盘允许检索
```

### 待确认内容

待确认内容可以进入 RAG，但必须带有“待确认”标记，不能作为已确认事实直接使用。

### 检索数量

```text
第一次检索最相关的一小组内容
→ 信息不足时再进行补充检索
```

### 相似记录

```text
系统识别相似记录
→ 保留多个来源
→ 正式合并长期记忆时仍需用户确认
```

### 检索依据

默认折叠，用户可以展开“本次参考”，也可以主动询问判断依据。

## 24. 第二十组：个人处境模型

### 定义

个人处境模型是根据多个正式数据对象聚合生成的当前状态快照，不是新的事实来源。

### 内容

第一期至少包含：

```text
当前重要目标
进行中的目标
行动及状态
截止时间
已确认的现实限制
当前问题
最近重要变化
风险和阻碍
最近重要决策
```

### 维护方式

```text
助手自动生成
→ 用户可以查看和修正
→ 影响重要决策的关键字段需要确认
```

### 更新方式

```text
每次输入后检查是否影响当前处境
→ 没有变化则不更新
→ 有变化则生成新的处境模型版本
```

### 历史版本

用户确认后的处境版本正式保存；当前版本用于日常建议，历史版本用于复盘和解释过去决策。

### 来源和外部使用

处境模型的重要判断需要关联目标、行动、记忆、决策或原始记录。

发送给外部模型时，只发送与当前问题相关的最小必要部分，并经过敏感信息钩子。

## 25. 第二十一组：下一步行动和决策建议

助手默认：

- 给出一个最推荐行动，并提供 1～2 个备选行动。
- 说明推荐原因，支持展开查看完整依据。
- 发现目标冲突时明确指出并给出优先级建议，不自动修改目标。
- 信息不足时先给低风险临时建议，并说明缺少的信息。
- 涉及外部影响时说明成本和风险。
- 参考过去类似行动的执行效果，避免重复失败模式。
- 用户拒绝建议时询问原因、提供替代行动，并记录本次未采纳情况。
- 不未经确认修改目标、创建行动或保存长期记忆。

建议生命周期为：

```text
建议生成
→ 用户采纳 / 创建行动
→ 用户开始执行
→ 行动完成或中断
→ 记录结果
→ 周复盘判断建议是否有效
```

## 26. 产品需求补充默认决策

本节记录在进入技术架构前，为补齐产品边界而**默认采用的建议**。后续如需改变，应明确记录变更原因和日期。

### 22.1 v1 范围分期

当前整体 v1 需求仍包含文字、语音、图片、网页链接和文件上传，但实现顺序默认拆成：

```text
v1.0 核心闭环：
聊天首页
→ 陪伴聊天 / 辅助解答
→ 按需使用个人上下文和 RAG
→ 用户需要时进入行动协助
→ 正式变更经过确认
→ 持续交流、行动追踪和每日摘要

v1.1 输入增强：
图片、网页链接、文件上传的内容解析
```

v1.0 可以先接收并保存附件；附件的完整解析放在 v1.1，避免输入入口和核心行动闭环同时失控。

### 22.2 v1 验证标准

采用连续 2～4 周的个人使用验证周期，观察：

- 是否愿意持续与助手聊天和表达。
- 陪伴回应是否让用户感到被理解。
- 是否能帮助用户梳理想法、回顾经历和理解当前状态。
- 辅助解答是否结合个人处境并真正有用。
- 用户需要行动时，行动建议和确认流程是否足够自然。
- 是否能找回相关历史信息。

v1 先验证“是否真正帮助用户”，不以功能数量、回答长度或创建行动数量作为成功标准。

### 22.3 首次打开 App

默认流程：

```text
设置应用保护
→ 配置至少一个模型
→ 测试连接
→ 输入第一条记录
→ 引导确认第一个目标或行动
```

不先展示复杂功能介绍，也不强制填写长表单。

### 22.4 助手主动追问边界

只有以下情况主动追问：

- 缺少创建行动所需的关键信息。
- 截止时间不明确。
- 多个目标互相冲突。
- 识别结果置信度较低。
- 用户表达可能对应多个不同意图。

普通聊天不连续追问。

### 22.5 待确认内容规则

待确认内容默认：

```text
首次打开 App 时提醒
→ 用户选择“暂不处理”后当天不重复提醒
→ 后续按间隔再次提醒
→ 用户可以关闭某条或全部提醒
```

待确认内容支持：

- 确认
- 修改后确认
- 拒绝
- 暂不处理
- 删除
- 标记识别错误

未确认内容永不自动升级为正式目标、行动或长期记忆。

### 22.6 删除、归档和彻底删除

默认区分：

```text
归档：仍然保留，可在历史中查看，默认不参与日常界面
删除：进入删除状态，不参与日常建议
彻底删除：从本地数据中物理清除
```

默认采用软删除，重要彻底删除需要二次确认。

删除父对象不自动删除关联对象：

- 删除目标，不自动删除行动。
- 删除行动，不自动删除目标。
- 删除记忆，不自动删除来源记录。
- 删除原始记录，不自动删除已确认结构化对象。
- 删除聊天会话，先只删除会话展示，原始记录单独处理。

### 22.7 事实生命周期

事实定义为从原始记录中提取出的、与用户相关但尚未必然长期有效的陈述。

默认生命周期：

```text
从原始记录提取
→ 自动保存为事实
→ 标记来源和可信度
→ 可被检索，但不能默认视为当前有效
→ 发生冲突时进入待确认
→ 用户确认后可转为长期记忆
```

如果用户明确指出事实识别错误，标记为“错误”，不应在相同依据下反复作为新建议提出。

### 22.8 建议效果记录

区分以下状态：

```text
建议已提出
建议已采纳 / 创建行动
行动已开始
行动已完成
行动结果已记录
建议效果已复盘
```

周复盘时可以将建议评价为：

```text
有效
部分有效
无效
无法判断
```

### 22.9 处境模型定位

处境模型是当前状态快照，不直接反向覆盖目标、行动、记忆和决策。

用户修正处境模型中的判断时：

```text
先修正处境显示或生成待确认变更
→ 不自动覆盖源对象
```

### 22.10 附件体验

所有附件默认遵循：

```text
先保存原始附件
→ 再进行解析
→ 解析失败不影响原始附件保存
→ 解析结果作为原始记录的附属分析
```

v1.0 允许接收和保存，v1.1 再完成图片、网页和文件的深度解析。

### 22.11 每日摘要中的行动展示

默认展示：

```text
一个最推荐行动
+ 1～2 个备选行动
+ 简短原因
+ 可展开查看依据
```

摘要中出现的新行动仍需用户确认，不能自动创建。

### 22.12 多设备产品承诺

在服务器同步完成前，第一期不承诺手机和电脑之间的数据实时一致。

产品层面的默认边界是：

```text
手机和电脑都提供基础使用入口
→ v1 先验证核心使用闭环
→ 跨设备连续记忆和行动同步属于后续能力
```

不在需求阶段假设两台设备可以无冲突地共享全部数据。

### 26.13 模型选择的三个概念

为避免“用户选择的模型”和“实际生成答案的模型”混淆，产品上区分：

```text
默认模型：用户设置中长期使用的模型
本次消息模型：发送前临时选择的模型
实际处理模型：最终成功生成答案的模型
```

自动切换成功后不改变用户的默认模型。下一条消息仍沿用用户的默认选择或上次主动选择。

### 26.14 模型失败和自动切换

默认采用以下用户可理解的行为：

```text
当前模型失败
→ 同一模型自动重试 1 次
→ 仍失败时按列表顺序尝试其他模型
→ 不循环，不重复尝试已失败模型
→ 全部失败后提示用户
```

只对网络、超时、限流和临时服务错误自动重试或切换。API Key 无效、权限错误、Model ID 不存在、格式不支持、能力不支持、上下文超限、内容安全拒绝和用户主动取消，不自动把同一请求发送给其他模型。

跨供应商自动切换默认需要用户在设置中明确开启；关闭时只在当前供应商可用模型范围内处理。

### 26.15 模型结果透明度

每条助手回复需要能够看到：

```text
供应商名称 / Model ID
```

如果发生切换，默认提示“已切换到其他模型完成处理”，展开后可查看原选择模型、实际使用模型、失败类型和尝试次数。

### 26.16 推理思考等级

产品统一提供：

```text
关闭
低
中
高
```

发送前可以临时调整，重试时沿用用户选择的抽象等级。模型不支持某个等级时，不静默降级；界面应隐藏不可用选项，或在发送前明确提示用户选择其他等级。

### 26.17 敏感信息处理模式

第一期提供三种设置：

```text
自动脱敏后发送
发送前查看并确认
检测到敏感信息时禁止发送
```

默认采用“自动脱敏后发送”，并在消息下方显示本次已检测并脱敏。任何外发内容都需要检查，包括用户消息、RAG 结果、长期记忆、处境模型、附件解析结果和模型重试请求。

敏感长期记忆单独分组、明显标记，不能因为“确认全部”而无提示保存。

### 26.18 模型基础调用记录

```text
任务类型
```


### 26.22 归档、删除和恢复

默认区分：

```text
归档：保留，可在历史中查看，默认不参与日常界面
删除：进入删除状态，不参与日常建议
彻底删除：从本地数据中物理清除
```

默认使用软删除，彻底删除需要二次确认。删除父对象不自动删除关联对象，最近一次重要操作建议支持撤销。

### 26.23 附件处理

```text
先保存原始附件
```

## 28. 2026 年 9 月 4 日产品定位修订

根据用户确认，本记录的产品中心修订为：

- 个人助手不是任务管理器，也不是单纯的聊天机器人，而是持续了解用户的个人智能伙伴。
- 陪伴聊天、辅助解答、行动协助是三条并列的核心主线。
- 陪伴聊天包含自然陪聊、情绪理解、想法梳理、经历回顾和持续了解用户状态。

- 正式目标、行动、记忆、决策和状态变更仍必须经过用户确认，不因产品重心调整而改变。
