## 1. 文档目的与规则层级

本文件回答的不是“模型能不能给出一个看似合理的答案”，而是：

```text
在用户的目标、截止时间、现实限制、历史结果和信息完整度都不相同的情况下，
助手如何给出可执行、可解释、不过度替用户决定的下一步？
```

产品的核心价值排序已经确认：

```text
行动执行 > 决策辅助 > 个人记忆 > 复盘成长 > 知识整理
```

因此，建议的首要产物是帮助用户开始或推进一件具体事情，而不是堆叠通用观点、资料摘要或伪精确的评分。

本文沿用以下确定性标记：

- **【已确认边界】**：来自已确认的产品需求、技术架构或确认中心，实施不得违反。
- **【本轮采用规则】**：为补齐目标与决策辅助闭环提出的 v1 工作基线；未经确认，不得倒写成上游已确认事实。
- **【待决策项】**：暂不阻塞核心闭环，但不得在实现中静默补全或伪装成既定规则。

建议、目标、行动、事实、长期记忆、决策记录和处境模型是不同对象。尤其要避免把“模型的一次建议”写成“用户已经作出的决策”，或把“行动完成”写成“建议已被证明有效”。

## 2. 关键问题 → 推荐答案

### 问题 1：什么是“最优下一步行动”，应输出几项？

**推荐答案：**【本轮采用规则】“最优下一步行动”是当前信息下，最能推动一个明确目标、能在现实限制内开始、且风险与不可逆性可接受的**一个细粒度动作**。默认先给 1 个推荐行动，再给 1～2 个有明确取舍差异的备选；不要输出无排序的待办清单。

推荐行动应尽量满足：

```text
有服务的明确目标或待解决问题
+ 能说明为什么是现在
+ 用户可在当前可用时间和资源中开始
+ 动作完成后会产生可观察的推进、信息或决策输入
```

建议的默认展示结构：

```text
推荐：先联系 1 位候选技术伙伴，约 20 分钟确认其本周可投入时间。
为什么现在：该目标的截止时间临近；当前缺少的人力信息阻塞后续排期。
完成标志：得到“可投入 / 不可投入 / 待确认”的明确回复。
备选 A：先列出所需角色与投入量（风险更低，但不能立即消除人力不确定性）。
备选 B：缩小本周交付范围（更快形成计划，但可能降低目标收益）。
```

“开始项目”“推进一下”“多做准备”等宽泛表述不能作为默认推荐行动；除非用户明确只要求方向性建议。建议不等于创建行动，创建正式行动仍需用户确认。

#### 已确认边界 / 本轮采用规则 / 待决策项

- **【已确认边界】** v1 判断“现在最应该做什么”时，必须考虑：当前明确目标、截止日期、重要程度、当前可用时间、资金/人员/技术等现实限制，以及过去类似事情的执行效果。
- **【已确认边界】** 正式行动只能在用户确认后创建；模型、RAG、后台任务和客户端都不得直接写入行动。
- **【本轮采用规则】** 推荐行动优先选取“能解除当前最关键阻塞、可在一个可感知时间块内启动、完成定义清楚”的动作。若没有足够依据断言“最优”，使用“当前更推荐”或“暂定下一步”，而不使用绝对措辞。
- **【本轮采用规则】** 备选项最多 2 个，且每个备选都必须说明与推荐项不同的成本、风险、速度或目标收益；没有差异的同义改写不应充当备选。
- **【本轮采用规则】** 默认不把紧急程度、用户精力、反复提及未行动等因素当作 v1 的硬性排序依据；若用户当次明确提供，可作为本次补充背景，并在依据中说明来源。
- **【待决策项】** 建议的具体打分模型、各因素权重、时间块的默认长度、是否允许用户配置排序偏好，以及多个推荐并列时的展示交互。

#### 验收标准

- 对有明确目标和限制的输入，结果包含 1 个可立即启动的推荐行动及至多 2 个有取舍说明的备选。
- 推荐行动能够关联至少一个目标、问题、限制、截止时间或历史结果；无法关联时明确标为低依据建议。
- “建议已展示”不会创建正式行动、提醒或目标状态变更。
- 用户选择“创建为行动”后，系统生成可编辑的行动候选并交给确认中心；未确认前不存在正式行动。

### 问题 2：建议依据如何透明展示，既能解释又不制造信息噪声？

**推荐答案：**【本轮采用规则】每条建议默认展示简短的“为什么是现在”，并可展开查看依据。解释应呈现关键驱动因素、信息状态和来源类型，而不是暴露内部评分、完整检索上下文或模型思维过程。

默认折叠层展示 2～4 条最重要依据：

```text
- 关联目标及其当前状态
- 已确认截止时间或时效状态
- 已确认现实限制
- 相关行动的执行状态或同类历史结果
```

展开后可查看：来源类型、来源记录或正式对象、发生时间、当前状态、确认状态、可信度、敏感标记和“它如何影响本次建议”。若使用了待确认内容、低可信度事实、过期记忆或模型推测，必须显式标记，不能和用户已确认信息混排。

#### 已确认边界 / 本轮采用规则 / 待决策项

- **【已确认边界】** 建议依据默认折叠，用户可展开查看本次参考内容；检索结果需携带来源、发生时间、状态、可信度、确认状态和敏感标记。
- **【已确认边界】** 结构化正式对象优先，原始记录作为补充和证据；普通建议优先使用当前有效长期记忆，过期记忆只允许用于历史复盘。
- **【已确认边界】** 找不到相关个人记录时，必须明确告知；如需推测，必须标记为推测。
- **【本轮采用规则】** 解释只说明“哪些事实或状态驱动了推荐”，不声称模型的不可验证内部推理；不显示完整 RAG 上下文、内部 ID、本地路径、API Key 或未必要的原始隐私内容。
- **【本轮采用规则】** 待确认内容可作为“待核实背景”帮助提出问题或低风险探索，但不得被表述为已确认事实，也不得单独支撑重要目标调整或高风险建议。
- **【本轮采用规则】** 当依据互相冲突时，展示冲突本身及其影响，例如“新记录称本周可投入 8 小时，旧记忆为 2 小时；本次未据此估算交付范围”。
- **【待决策项】** 展开层最多展示多少条来源、同类来源如何聚合、可信度的视觉表达和用户对依据展示的自定义程度。

#### 验收标准

- 用户能从每条建议看到简短的推荐理由，并能展开确认来源和信息状态。
- 待确认、过期、低可信度、冲突或推测信息不会被渲染成用户已确认结论。
- 无相关记录时，建议不会伪造个人化依据；界面明确显示“缺少相关历史信息”。
- 依据说明不会包含完整敏感值、完整外发载荷或内部实现细节。

### 问题 3：多个目标或行动发生冲突时，助手应该替用户选吗？

**推荐答案：**【本轮采用规则】不替用户静默放弃、延期、降级或完成任何目标。助手先识别并说明冲突，再把冲突转化为有后果说明的决策辅助；只有用户确认后，才修改正式目标、行动、截止时间或长期记忆。

目标冲突至少包括：

```text
时间冲突：同一可用时间内多个临期行动无法同时完成
资源冲突：资金、人员、技术能力或信息不足以支持多个方案并行
方向冲突：两个目标的成功条件、承诺或优先级相互排斥
历史冲突：新旧记忆、事实或过往结果对当前判断给出相反信号
```

推荐输出应将“冲突事实”和“建议取舍”分开：

```text
冲突：本周剩余可用时间不足以同时完成 A 的交付和 B 的调研。
推荐取舍：优先 A，因为其有已确认截止时间，且 B 的下一步可延期一周。
代价：B 的验证结果将推迟；这不是已确认的目标延期。
备选：缩小 A 的范围，保留 B 的 30 分钟调研。
需要你决定：确认优先级、调整截止时间，或补充可用时间信息。
```

#### 已确认边界 / 本轮采用规则 / 待决策项

- **【已确认边界】** 目标具有独立状态；关联行动全部完成也不能自动使目标完成。截止时间经过也不能自动改变正式目标或行动的业务状态。
- **【已确认边界】** 目标、行动、截止时间和状态变更均须经确认中心；周复盘和后台任务只能产生候选或提示。
- **【本轮采用规则】** 冲突检测优先使用用户已确认的目标、行动、截止时间、现实限制和明确的资源信息；模型推测只能作为“可能冲突”的提示，不能直接形成结论。
- **【本轮采用规则】** 推荐可以排序，但不得自动取消、搁置、延期或降低未被选中的对象。用户未选择时，保留原状态并仅记录本次建议或候选反馈。
- **【本轮采用规则】** 若冲突的关键事实尚不明确，优先建议一个可逆的信息收集动作，或只询问一个最能改变排序的问题。
- **【待决策项】** 冲突的正式类型枚举、跨目标依赖关系、资源容量的字段模型、冲突自动检测阈值和用户配置的优先级规则。

#### 验收标准

- 系统发现时间、资源或方向冲突时，显示冲突依据、推荐取舍和未选择方案的影响。
- 建议展示后，所有相关目标和行动保持原正式状态。
- 用户确认变更前，系统不会将“建议优先 A”写成“用户放弃 B”或“B 已延期”。
- 关键事实不足时，输出低风险澄清或信息收集建议，而不是伪造明确排序。

### 问题 4：现实限制和历史结果应该如何影响建议？

**推荐答案：**【本轮采用规则】现实限制是建议的约束，不是可被模型忽略的背景；历史结果是可解释的经验输入，不是决定用户未来必然失败或成功的标签。建议应说明哪些限制被纳入、哪些历史结果被参考，以及它们的适用边界。

建议可使用的现实限制包括：

```text
可用时间
资金预算
人员可用性
技术能力或依赖
已确认的截止时间
外部等待条件
用户明确表达的不可接受风险或偏好
```

历史结果至少区分：行动是否完成、实际耗时、延期/中断原因、结果说明和用户对建议效果的评价。相似性不足、来源已删除、记忆已过期或结果无法判断时，不应把历史当作强依据。

#### 已确认边界 / 本轮采用规则 / 待决策项

- **【已确认边界】** 资金、人员、技术等现实限制，以及过去类似事情的执行效果，是 v1 必须考虑的建议依据。
- **【已确认边界】** 决策记录保存具体选择、当时条件和结果；决策经验记忆来自多个决策或复盘中的可长期复用认识，二者不能相互替代。
- **【已确认边界】** 旧记忆发生冲突时保留历史并标记过期或不再适用，不直接覆盖；处境模型只是可追溯的聚合快照，不得反向改写来源对象。
- **【本轮采用规则】** 对历史结果的表述使用条件化语言，例如“过去两次在可用时间不足 2 小时时，该类行动均延期；本次建议先拆分为 20 分钟准备动作”。不能据此断言用户能力、意愿或人格特征。
- **【本轮采用规则】** 历史结果只在目标、约束和行动类型具有可解释相似性时影响排序；否则仅作为可展开的参考，不降低当前行动的默认优先级。
- **【本轮采用规则】** 明确的现实限制优先于模型生成的理想方案。若建议无法在限制内执行，应改为减少风险、补充资源、澄清限制或重新决策的下一步。
- **【待决策项】** 历史行动的相似性计算、结果字段和原因分类、限制的有效期、处境模型新鲜度以及不同历史证据的权重。

#### 验收标准

- 当已确认预算、时间、人员或技术限制与推荐方案冲突时，推荐不会假设该限制不存在。
- 历史结果的引用可以回溯到关联行动或决策记录，并能说明其不是绝对预测。
- 过期、冲突、低可信度或无法判断的历史信息不会作为唯一的高风险建议依据。
- 删除原始记录、索引失败或处境刷新失败时，系统能区分“没有历史结果”“历史不可用”和“依据不足”。

### 问题 5：信息不足时，怎样给出低风险建议而不装作已经理解用户？

**推荐答案：**【本轮采用规则】先明确缺少什么信息；如果仍可帮助，给出一个低成本、可逆、不会改变正式对象或向外承诺的探索动作。信息不足时，系统可以提出一个关键追问，但不应以连续追问代替帮助。

低风险建议的优先顺序：

```text
1. 询问一个最能改变建议排序的关键问题
2. 建议收集或核对关键信息
3. 建议一个短时、可撤回、无外部承诺的准备动作
4. 明确说明暂不适合给出确定排序
```

例如：当不知道可用时间和截止时间时，建议“先用 5 分钟确认这件事是否有硬性截止日期”，而不是直接创建全天计划；当不知道预算时，建议“列出可接受预算上限和两种成本方案”，而不是建议下单或签约。

#### 已确认边界 / 本轮采用规则 / 待决策项

- **【已确认边界】** 无相关记录时必须明确告知，推测必须标记为推测；待确认内容不得当作已确认事实使用。
- **【已确认边界】** 助手的主动行为有上限：每天最多 1 份行动摘要、每个明确提醒时间最多 1 次、逾期行动每天最多集中提醒 1 次、每周最多 1 次目标复盘；用户可关闭本次、稍后处理、暂时不再提醒或调整设置。
- **【本轮采用规则】** 低风险建议默认不创建正式行动、不修改目标、不保存长期记忆、不触发提醒，也不假定用户已同意对外联系、付款、承诺或共享信息。
- **【本轮采用规则】** 用户已回答或明确拒绝回答的问题不应在同一上下文中重复追问；建议可改为“基于当前未知项的保守方案”。
- **【本轮采用规则】** 若可用信息无法支撑推荐与备选的比较，应只给出“下一步获取信息”的建议，并将排序结论标为待定。
- **【待决策项】** 哪些问题属于高信息价值问题、连续缺失信息的再次询问间隔，以及低风险建议的默认时间上限。

#### 验收标准

- 信息缺少时，界面明确列出缺口或不确定性，不伪造目标、限制、历史结果或用户偏好。
- 所谓低风险建议不产生自动写入、外部发送、付款、承诺或提醒。
- 用户忽略或关闭建议后，系统遵守主动行为上限，不连续追问。
- 用户补充关键事实后，下一次建议能够说明推荐为何变化。

### 问题 6：建议、采纳、行动、结果和效果应如何形成独立生命周期？

**推荐答案：**【已确认边界 + 本轮采用规则】必须区分“建议已提出”“用户采纳/创建行动”“用户开始执行”“行动完成或中断”“记录结果”“周复盘评价效果”。建议不是行动，采纳不等于完成，行动完成也不自动证明建议有效。

建议生命周期建议表示为：

```text
分析生成
→ 已展示
→ 用户反馈：采纳 / 暂不采纳 / 忽略或过期 / 被新建议替代
→ （采纳为正式行动时）创建行动候选
→ 确认中心确认成功
→ 正式行动：待开始 / 进行中 / 已完成 / 已延期 / 暂时搁置 / 已取消
→ 记录行动结果
→ 周复盘评价建议效果：有效 / 部分有效 / 无效 / 无法判断
```

其中：

- **建议**：分析结果层中的推荐及其依据，允许记录展示和反馈，不是正式业务对象。
- **采纳**：用户明确表示愿意按建议处理；若会创建行动、修改目标、保存决策或变更记忆，必须进一步以确认中心的正式命令完成。
- **行动**：用户确认后形成的正式对象，其状态由行动状态机管理。
- **结果**：用户记录的实际发生情况，例如完成物、耗时、阻塞、收益或中断原因；不能由模型凭空补写。
- **效果**：周复盘对“该建议在当时条件下是否帮助目标推进”的评价，允许为无法判断。

#### 已确认边界 / 本轮采用规则 / 待决策项

- **【已确认边界】** 建议、采纳、创建行动、执行和效果评价必须保持独立生命周期；建议效果可评价为“有效、部分有效、无效、无法判断”。
- **【已确认边界】** 后台任务、每日摘要和周复盘可以生成建议、提醒和候选，但不能绕过确认中心写入正式目标、行动、记忆、决策或状态变更。
- **【本轮采用规则】** 采纳“转为行动”时，建议创建可编辑行动候选并带上建议来源、依据快照和关联目标；确认失败或用户取消时，建议仍是已展示/已采纳意向，不伪造正式行动。
- **【本轮采用规则】** 一条建议可对应多个行动；多个建议也可收敛到同一行动，但关联关系必须可追溯，避免把行动结果错误归因给某个单一建议。
- **【本轮采用规则】** 效果评价由用户复盘或由系统基于可观察结果提出候选，不能自动定性。缺少结果、行动未结束、目标尚无可观察进展或多因素无法拆分时，使用“无法判断”。
- **【待决策项】** 建议是否需要独立稳定标识、建议保留期限、用户反馈字段、结果模板、效果评价的量表和自动生成复盘候选的条件。

#### 验收标准

- 同一建议从展示、反馈、行动创建、执行、结果到效果评价均可区分，不会混用状态。
- 未确认的行动候选不会被算作“已采纳并开始执行”。
- 已完成行动在没有结果和复盘评价时，不会显示为“建议有效”。
- 用户可以看到某个行动关联了哪些建议及其依据，也可以看到一条建议最终未创建行动或被替代。

### 问题 7：用户拒绝建议后，系统应如何处理？

**推荐答案：**【本轮采用规则】拒绝是有效反馈，但不是永久事实、更不是目标取消。系统记录“本次建议未被采纳”的状态和可选原因；在相同目标、相同约束且没有新证据时不重复推送同一建议。出现新的目标状态、限制、截止时间、历史结果或用户主动再次询问时，可以重新提出，但必须说明重新出现的原因。

用户可选的轻量反馈：

```text
暂不采纳
不适合当前情况
优先级不对
成本或风险太高
我会用其他方式处理
不再针对此目标推荐
不填写原因
```

“拒绝建议”和“取消正式行动”必须分开：前者只影响建议生命周期；后者是正式行动状态变更，仍需确认中心处理。

#### 已确认边界 / 本轮采用规则 / 待决策项

- **【已确认边界】** 候选的拒绝和取消在候选生命周期上统一进入已取消，但正式目标、行动和记忆不会因此自动改变。
- **【已确认边界】** 用户可以关闭本次、稍后处理或暂时不再提醒；助手不得连续追问。
- **【本轮采用规则】** 拒绝原因默认可选，且不自动升级为长期记忆或用户偏好；只有用户明确确认需要长期保留时，才通过确认中心保存。
- **【本轮采用规则】** “不再针对此目标推荐”仅抑制同类建议，不取消目标、不阻止用户主动请求建议，也不影响其他目标；恢复推荐由用户主动开启或后续确认规则决定。
- **【本轮采用规则】** 当建议因新证据再次出现时，显示“此前未采纳；因截止时间/限制/目标状态已变化，本次重新建议”，避免让用户误以为系统忽略了反馈。
- **【待决策项】** 拒绝反馈的保存期限、同类建议的判定方式、抑制规则是否跨目标生效、用户管理历史建议的界面。

#### 验收标准

- 用户拒绝建议不会自动取消目标、行动、提醒、记忆或决策记录。
- 相同上下文中被拒绝的建议不会被后台任务或摘要反复推送。
- 用户主动重新请求或上下文发生可解释变化时，系统可以重新提出建议并说明变化原因。
- 拒绝原因不会在未经确认时被写成长期偏好或事实。

### 问题 8：什么情况下需要形成“重要决策记录”，记录哪些内容？

**推荐答案：**【本轮采用规则】当用户在多个方案之间作出会明显影响目标、资源、时间、人员、风险承担或后续行动的选择时，助手可提出“保存重要决策记录”候选。该记录用于未来解释“当时为什么这样选”及复盘结果，不能替代目标、行动、事实或长期记忆。

最小记录内容建议为：

```text
决策问题与关联目标
当时的时间和处境快照
可选方案及未选方案
用户最终选择（而不是模型偏好）
推荐意见及其依据
明确的现实限制、假设和风险
关联来源、行动和截止时间
后续结果与复盘结论（如有）
```

以下情况优先提示保存：

- 用户明确说出“我决定……”“在 A 和 B 之间选择……”；
- 需要放弃、暂停、重排或大幅缩小某个目标；
- 选择涉及金钱、人员、工作安排、重要文件或明显机会成本；
- 过去类似决策反复出现，未来可能需要解释或比较结果；
- 周复盘发现某个选择显著改变了目标进展。

#### 已确认边界 / 本轮采用规则 / 待决策项

- **【已确认边界】** 保存正式决策记录属于正式业务变更，必须进入确认中心；模型只可产生候选。
- **【已确认边界】** 决策记录保存具体选择、当时条件和结果；决策经验记忆必须与多个决策或复盘关联，不能用一次选择直接代替。
- **【本轮采用规则】** 助手不能自动把普通聊天或模型建议登记为“用户决策”。只有用户的明确选择，或用户确认保存的候选，才形成正式决策记录。
- **【本轮采用规则】** 重要决策记录保留当时依据的状态快照和来源引用；后续事实变化时新增结果或复盘，不静默篡改“当时为什么这样选”。
- **【本轮采用规则】** 用户可以不保存决策记录；不保存不影响创建行动或继续聊天。
- **【待决策项】** “重要”的具体阈值、决策记录的字段细化、编辑/恢复规则、是否支持一项决策关联多个目标，以及导出的展示格式。

#### 验收标准

- 保存决策记录前，用户能看到其关联目标、方案、限制、风险和来源摘要，并明确确认。
- 系统不会将模型建议、隐含偏好或未确认候选误写为用户最终选择。
- 已保存决策记录能关联当时的行动、结果和来源；后续复盘不会覆盖原始决策上下文。
- 用户拒绝保存时，不产生正式决策记录。

### 问题 9：决策经验和每周复盘如何服务未来建议，又如何避免过度归纳？

**推荐答案：**【本轮采用规则】每周复盘先展示可验证的目标、行动、结果、限制和建议效果，再提出可供用户确认的经验候选。一次成功、失败或一次“有效”评价都不能自动沉淀为长期决策经验。

周复盘的最小决策辅助内容：

```text
本周目标和行动的推进情况
已完成、延期、搁置、取消及已记录结果
建议被采纳/拒绝/未处理的概览
可评价的建议效果及“无法判断”的原因
重复出现的限制、阻塞或决策问题
下一周的一个推荐关注点和可选行动候选
```

经验候选的表达应有条件和样本范围，例如：

```text
候选经验：在“截止时间明确且需要他人配合”的事项中，先确认对方可用性，
比先细化方案更能减少延期。
依据：本周及此前两次已完成/延期记录；样本有限，需继续观察。
```

#### 已确认边界 / 本轮采用规则 / 待决策项

- **【已确认边界】** 每周最多生成 1 次目标复盘；复盘可以使用历史处境、过期记忆和过去行动结果，但不能自动写回当前正式状态。
- **【已确认边界】** 周复盘中提出的新目标、行动、记忆、决策或处境变更，必须进入确认中心；普通统计和分析可以直接展示。
- **【已确认边界】** v1 不自动把一次成功或失败固化为长期决策经验；完整决策复盘属于 v1.1 或后续增强，不阻塞 v1.0 核心闭环。
- **【本轮采用规则】** v1.0 仅提供基础的建议—行动—结果—效果关联、周度汇总和经验候选，不自动保存经验记忆。用户确认后才可保存为长期记忆或正式决策记录。
- **【本轮采用规则】** 经验候选必须说明样本、适用条件和不确定性；样本少、结果相互矛盾或因果无法分离时，展示为观察，不作为未来高风险建议的强依据。
- **【本轮采用规则】** 周复盘推荐的下一步仍是建议，不自动创建下周行动、调整目标或安排提醒。
- **【待决策项】** 每周复盘的具体时间、时区、渠道、模板、统计口径、经验候选的最小样本条件和 v1.1 完整决策复盘的范围。

#### 验收标准

- 周复盘最多按既定主动行为上限生成一次，且能区分事实统计、系统推测和用户已确认结论。
- 一次行动的完成、失败或建议效果不会自动写为长期经验。
- 经验候选可回溯到多个决策或结果，并展示适用条件和不确定性。
- 周复盘产生的正式对象变化全部通过确认中心，未确认前不改变当前目标、行动、记忆或提醒。

### 问题 10：建议如何与确认中心交接，哪些行为绝不能绕过确认？

**推荐答案：**【已确认边界】建议生成属于分析和展示；只要用户的选择会创建、更新、删除或改变正式业务对象，就必须转成独立候选，进入确认中心的校验、风险提示、幂等、事务、版本冲突和失败恢复链路。

交接流程：

```text
原始记录 / 当前正式对象 / RAG / 处境模型 / 历史结果
→ 生成建议与依据（无正式写入）
→ 用户选择采纳、调整或拒绝
→ 需要业务变更时生成可编辑候选项
→ 加入确认批次
→ 用户明确提交确认
→ Local Core 校验版本、风险和幂等
→ 原子写入正式对象、来源关系、关键变更记录和索引任务
→ 返回确认结果；索引失败进入补偿，不回滚已成功业务写入
```

必须交给确认中心的情形包括：创建或修改目标、创建行动、完成/延期/搁置/取消行动、修改目标截止时间、保存或更新长期记忆、保存决策记录、标记记忆过期、删除或彻底删除对象，以及周复盘提出的任何正式变更。

#### 已确认边界 / 本轮采用规则 / 待决策项

- **【已确认边界】** 默认选中不等于确认；一条输入可包含多个独立候选，用户可逐项修改、取消、暂不处理或部分确认。
- **【已确认边界】** 同一确认操作重复提交不得重复创建对象或重复变更状态；同一操作标识提交不同内容必须被拒绝，版本冲突不得静默覆盖。
- **【已确认边界】** 后台任务可以生成建议、提醒、候选和复盘，不得绕过确认中心执行正式写入。
- **【本轮采用规则】** 建议转为候选时，携带建议标识（如后续确定）、关联目标、来源、依据摘要、风险标记和生成时的对象版本；用户编辑候选后，显示“已基于建议修改”，但以用户最终确认内容为准。
- **【本轮采用规则】** 确认失败、版本冲突或风险确认缺失时，不把建议标为已执行；应保留可理解的失败状态，并允许用户刷新、编辑或放弃候选。
- **【待决策项】** 建议与候选的稳定标识设计、批量采纳的交互、候选有效期、冲突后的刷新策略和撤销入口保留时间。

#### 验收标准

- 普通建议、依据展示和用户浏览不会写入正式业务对象。
- 所有由建议引发的正式变更均可在确认中心逐项查看、编辑、取消和确认。
- 重复提交、版本冲突、失败重试和索引补偿不会重复创建行动或重复记录结果。
- 后台摘要或复盘生成的建议与用户输入生成的建议遵守同一确认边界。

### 问题 11：高风险建议和敏感信息应如何设边界？

**推荐答案：**【已确认边界 + 本轮采用规则】高风险建议可以被提出，但必须明确显示影响、成本、风险、依据状态和可逆性；不能默认全选或以普通建议的方式静默转成正式行动。涉及敏感信息时，“本地可保存”和“可对外发送”必须严格分离，建议解释也不得泄露秘密值。

v1 已明确需要显式风险提示的候选包括：

```text
保存敏感长期记忆
修改目标截止时间
标记记忆过期
删除或彻底删除对象
创建可能涉及金钱、人员、工作安排或重要文件的行动
```

高风险建议的最小展示内容：

```text
建议的目标与预期收益
可能影响的目标、行动、人员或文件
成本、不可逆性和主要风险
关键依据及其中的待确认/低可信度/冲突信息
不采取该建议和备选方案的主要后果
是否需要额外确认或二次确认
```

敏感信息的 v1 强制识别类别为身份证件、银行卡、密码和 API Key/其他密钥。任何外发请求的最终完整载荷——包括本次输入、RAG、记忆、处境模型、附件解析、后台任务和重试——都必须在供应商适配器前经过统一敏感信息处理。

#### 已确认边界 / 本轮采用规则 / 待决策项

- **【已确认边界】** 普通候选可批量确认；重要候选必须显式完成风险确认，彻底删除必须二次确认，“默认全选”不能替代风险确认。
- **【已确认边界】** 外发敏感处理支持自动脱敏后发送、发送前查看并确认、检测到敏感信息时禁止发送三种模式；默认自动脱敏后发送，并显示本次已检测及处理。
- **【已确认边界】** 敏感长期记忆需单独分组、明显标记，不能因“确认全部”而无提示保存；外发日志不得保存完整请求、完整 RAG 上下文、完整模型输出或 API Key。
- **【本轮采用规则】** 建议不得在默认摘要、依据展开或通知中复述完整身份证号、卡号、密码、密钥或脱敏前文本；只展示类别、受影响来源和必要的局部说明。
- **【本轮采用规则】** 待确认、低可信度或相互冲突的信息不得作为高风险建议的唯一依据。依据不足时，推荐先核验、补充信息或选择可逆的低风险动作。
- **【本轮采用规则】** v1 的“高风险”首先按已确认的业务影响范围处理；医疗、法律、投资等领域是否需要额外专业建议策略，不在本文中擅自冻结，需单独确认。
- **【待决策项】** 高风险分类的更细颗粒度、风险文案、单独提交还是同批提交、敏感识别的具体规则与误报处理、单次放行及导出时的敏感展示策略。

#### 验收标准

- 高风险建议在用户采纳前明确展示影响、风险和依据状态，且不能被默认全选静默确认。
- 删除、彻底删除、敏感长期记忆、目标截止时间和可能影响金钱/人员/工作安排/重要文件的行动均触发对应风险提示。
- 建议、复盘、通知、日志和外发请求不会泄露未脱敏的身份证件、银行卡、密码或密钥。
- 敏感或低可信度信息不足以单独推动高风险正式变更；系统改为核验或低风险建议。

- 给出最优下一步行动、1～2 个备选及其取舍说明；
- 使用目标、截止时间、重要程度、可用时间、现实限制和历史结果生成建议；
- 展示建议依据、来源状态、不确定性和冲突；
- 处理目标冲突、信息不足、低风险建议和用户拒绝建议；
- 定义建议—采纳—行动—结果—效果的关系；
- 提出重要决策记录、经验候选和周复盘的产品规则；
- 定义建议向确认中心、高风险提示和敏感处理的交接边界。

### 本文件不负责

- 目标与行动状态的完整允许/禁止转移、提醒时区和渠道；
- 确认中心的具体卡片交互、命令字段、事务实现、幂等算法和撤销实现；
- RAG 的向量库、分块、Embedding、召回数量和排序公式；
- 事实、长期记忆、处境模型、原始记录和索引的完整数据模型；
- 模型供应商协议、推理等级、重试参数和调用日志字段；
- 敏感识别器、脱敏格式、误报处理和导出加密格式；
- 自动替用户执行外部操作、跨设备同步或多用户协作。

### 版本边界

- **v1.0：** 基础建议依据展示、单一推荐加备选、低风险信息不足处理、建议与行动分层、拒绝反馈、基础结果关联、每周复盘中的基础效果展示和确认中心交接。
- **v1.1：** 图片/网页/文件深度解析带来的更完整依据、完整决策复盘、处境模型高级历史分析、复杂经验归纳和更丰富的建议管理。
- **v2 或后续确认：** 跨设备连续决策历史、多用户/协作决策、自动模型路由、外部自动执行，以及尚未确认的专业领域高风险策略。

## 4. 跨流程总体验收标准

完成后续实现时，至少应满足：

1. 用户输入后，助手可以基于已确认目标、行动、限制、截止时间和历史结果生成细粒度建议，并将推荐项与备选项的取舍说清楚。
2. 每条建议均能说明依据、来源状态和不确定性；没有相关数据时明确说明，不伪造个人化结论。
3. 系统识别冲突时，只展示冲突和候选取舍，不自动修改、取消、延期、完成或放弃任何正式对象。
4. 信息不足时，系统优先提供关键追问、信息收集或可逆低风险动作，不虚构目标、限制或用户偏好。
5. 建议、采纳、行动创建、执行、结果和效果评价可独立追踪；行动完成不自动等于建议有效。
6. 用户拒绝建议后，系统不反复推送同一建议，不把拒绝写成目标取消或长期偏好；重新建议时能说明新依据。
7. 保存重要决策记录、创建/修改目标或行动、保存长期经验、删除和所有其他正式变更均经确认中心处理。
8. 周复盘能展示可验证的进展、结果和效果，经验沉淀仅作为候选，未经确认不写入长期记忆或正式决策。
9. 高风险建议有显式风险确认；敏感信息在本地保存、展示、日志和外发之间遵守不同边界，不泄露未脱敏秘密值。
10. 模型失败、RAG 无结果、索引滞后、确认失败或后台任务重试不会丢失原始记录、制造重复行动，或把建议误标为已执行。
