## 1. 文档目的

本文件回答：

```text
用户输入的内容何时成为正式原始记录？
文字、语音和附件如何统一进入分析链路？
附件保存与附件解析如何解耦？
模型如何从输入中提出摘要、事实、问题、目标、行动和记忆候选？
哪些结果可以自动保存，哪些必须交给确认中心？
```

统一原则：

```text
统一输入入口
→ 用户提交可分析原始内容
→ 本地保存原始记录和附件
→ 异步分析或解析
→ 保存分析结果和候选
→ 用户确认正式业务变更
```

输入阶段不要求用户预先选择“记录、目标、行动、记忆、决策”等业务类型。

```text
统一入口
≠ 用户预先选择业务类型
≠ 用户确认正式业务变更
= 用户向助手提交可被保存和分析的原始内容
```

## 2. 版本范围

### 2.1 v1.0 核心范围

v1.0 必须支持：

```text
文字输入
语音转文字并由用户确认
图片接收、原始保存和关联
网页链接接收、原始链接保存和关联
文件上传、原始保存和关联
原始记录
输入后的结构化分析
目标候选和行动候选
长期记忆候选
统一确认中心交接
```

### 2.2 v1.0 附件边界

v1.0 对图片、网页链接和文件的承诺是：

```text
接收
→ 原始保存
→ 关联原始记录
→ 生命周期管理
→ 导出
```

v1.0 不承诺：

```text
OCR
网页抓取
网页快照
文档抽取
附件可搜索正文
附件语义检索
基于附件内容的事实、目标、行动或记忆提取
```

### 2.3 v1.1 优先增强

v1.1 优先增加：

```text
图片深度解析
网页链接内容解析
文件内容提取
成功解析内容的检索和结构化提取
```

解析成功后的内容是附件派生数据，不能覆盖原始附件、原始链接或原始记录正文。

## 3. 关键问题与推荐答案

### 问题 1：用户是否需要先选输入类型或业务类型？

**推荐答案：** 不需要先选业务类型，使用聊天式统一入口。

用户打开 App 后可以：

```text
直接输入文字
或
开始语音输入
或
附加图片、网页链接、文件
```

用户无需在输入前判断：

```text
这是记录还是目标？
这是行动还是记忆？
这是问题还是决策？
```

这些由提交后的分析链路识别。图片、网页链接和文件的附件选择是输入媒介选择，不是业务类型选择。

### 问题 2：文字点击发送后，什么时候算正式提交？

**推荐答案：** 用户点击发送，表示确认把当前文字作为原始输入提交；Local Core 持久化成功后，形成正式原始记录并登记分析任务。

文字流程：

```text
用户编辑文字
→ 点击发送
→ 客户端生成 input_submission_id
→ Local Core 校验输入
→ 写入 OriginalRecord
+ 写入 SessionMessage → OriginalRecord 引用
+ 登记输入分析任务
→ 返回已提交、分析中
→ 异步生成助手回复和结构化结果
```

规则：

- 空字符串或仅空白字符不得创建原始记录，也不得启动分析。
- 原始正文必须是用户实际发送的版本；后续摘要、候选和用户修改候选都不得改写正文。
- 同一次发送的网络重试必须复用 `input_submission_id`。
- 用户后来再次主动发送同样文本，视为新的输入，使用新的提交标识；系统不按文本内容自动去重。
- 普通文字发送不是确认中心的 `SubmitConfirmationBatch`；它只确认“把文本交给助手保存和分析”。

### 问题 3：文字提交成功的事务边界是什么？

**推荐答案：** 以下内容构成一次输入提交的最小成功边界：

```text
OriginalRecord
+ 用户 SessionMessage 对 OriginalRecord 的引用
+ 输入分析任务或 AnalysisRun 的登记
```

提交成功后：

- 原始记录可以长期保存、追溯和导出。
- 分析可以异步执行。
- 模型失败不会回滚原始记录。
- 分析任务登记失败时，不应把输入展示为已经正式提交成功。

`input_submission_id` 只保障同一次提交操作的传输幂等，不判断两次输入是否语义重复。

### 问题 4：语音从录音到提交的最小流程是什么？

**推荐答案：** 语音必须先转写、允许用户编辑、再由用户确认发送，才进入正式输入链路。

```text
点击录音
→ 录音
→ 语音转写
→ 展示转写文本
→ 用户检查和修改
→ 用户确认发送
→ 创建正式原始记录
→ 开始输入分析
```

推荐语音草稿生命周期：

```text
空闲
→ 录音中
→ 音频已就绪
→ 转写中
→ 转写编辑中
→ 确认提交中
→ 已提交
```

异常分支：

```text
录音中 / 转写中 / 转写编辑中
→ 已取消

录音中 / 转写中
→ 失败
→ 重试或丢弃
```

语音草稿不是正式聊天消息，也不是正式原始记录。

### 问题 5：语音转写确认前后，哪些数据可以处理？

**推荐答案：** 确认前只允许临时草稿数据；确认后才与文字输入收敛为同一正式处理链路。

#### 确认前

允许临时保存：

- 临时音频文件；
- 临时转写文本；
- 用户正在编辑的转写文本；
- 录音、转写、错误和重试状态。

确认前禁止：

- 创建 `OriginalRecord`；
- 创建正式用户 `SessionMessage`；
- 调用内容分析模型；
- 提取事实、目标、行动、限制或长期记忆；
- 创建 CandidateItem、ConfirmationBatch 或正式对象；
- 写入正式 RAG 索引；
- 将未确认转写作为内容分析模型上下文。

#### 确认后

```text
最终编辑后的转写文本
→ OriginalRecord 正文
→ 可选 Attachment：原始音频（仅当后续决定保留）
→ SessionMessage 引用 OriginalRecord
→ 输入分析任务
→ AnalysisRun / StructuredAnalysis / CandidateItem
```

确认后的语音文本与文字输入共享后续分析、候选、确认、索引和失败恢复规则，不另建语音专属业务链路。

### 问题 6：语音转写确认、隐私外发确认和业务确认有什么区别？

**推荐答案：** 三者必须分开。

| 确认类型 | 用户确认的问题 | 成功后允许发生 | 不能替代 |
|---|---|---|---|
| 语音转写确认 | 这段最终文字是否代表我要提交的原始输入？ | 创建原始记录、正式用户消息、输入分析 | 不创建行动、目标、长期记忆或状态变更 |
| 隐私外发确认 | 此次外发载荷是否允许按指定策略离开设备？ | 按策略发出某次外部请求 | 不确认正式业务对象 |
| 业务变更确认 | 模型提出的候选是否正式生效？ | 写入正式对象、来源、变更记录和索引任务 | 不改写原始正文，不授权未处理敏感外发 |

因此：

```text
确认语音转写
≠ 确认创建行动

确认敏感外发
≠ 确认保存长期记忆

确认业务变更
≠ 同意外发未脱敏内容
```

### 问题 7：外部语音转写是否可以作为默认路径？

**推荐答案：** 当前不锁定本地或外部语音转写技术；外部语音转写不能被实现为静默默认路径。

#### 本地转写

```text
音频和临时转写均留在设备
→ 用户确认转写后才进入内容分析
```

#### 外部语音转写

若未来使用外部语音服务：

- 原始音频、流式音频片段或实际外发载荷属于独立外发请求。
- 必须经 Local Core 统一控制，客户端不得直连供应商。
- 用户确认最终转写文本，不等于同意音频此前或之后对外发送。
- 在外部语音转写的隐私提示、提醒/阻止模式和单次放行范围未确定前，不得把它设为静默默认实现。
- 外部语音转写不能替代后续内容分析的敏感信息处理。

本文件不决定具体语音供应商、协议、音频编码、转写模型或临时音频保留时长。

### 问题 8：用户取消录音、取消分析或删除记录，分别意味着什么？

**推荐答案：** 三者必须区分。

#### 取消语音草稿

```text
取消录音 / 放弃转写编辑
→ 清理临时转写状态
→ 按临时文件规则处理临时音频
→ 不创建原始记录
→ 不创建正式用户消息
→ 不启动分析
```

#### 取消已提交后的分析

```text
原始记录已保存
+ 分析尚未开始或可停止
→ 分析任务标记取消
→ 原始记录继续保留
→ 不产生候选和正式对象
```

若外部请求已经发出，系统只能尽力取消后续等待和重试，不能承诺撤回已经离开设备的请求。

#### 删除原始记录

删除已经提交的内容必须进入已有删除流程：

```text
软删除
或
彻底删除（二次确认）
```

取消分析不等于删除原始记录；删除原始记录也不自动删除已确认正式对象。

### 问题 9：附件与原始记录的关系是什么？

**推荐答案：** 图片、网页链接和文件都是从属于 `OriginalRecord` 的独立附件对象，不取代原始记录正文，也不与解析结果混为一体。

```text
OriginalRecord
├── 正文：文字、确认后的语音转写或用户补充文本
├── Attachment（0..N）
│   ├── 图片
│   ├── 网页链接
│   ├── 文件
│   └── 原始音频（如果后续决定保留）
└── AttachmentParseResult（每个附件可有 0..N 次尝试）
```

规则：

- 原始记录可以没有附件。
- 附件型输入可以正文为空或只包含用户补充文字，但必须有至少一个附件。
- 网页链接作为原始链接附件保存，而不是仅保留为聊天显示文本。
- 原始文件、原始链接和原始记录正文不能被摘要、解析结果或正式对象覆盖。
- 正式对象、事实、分析结果和建议需要能够回溯到原始记录、具体附件及其解析结果。

### 问题 10：附件提交成功的边界是什么？

**推荐答案：** 原始记录、原始附件/链接引用、关联关系和后续处理状态登记共同构成附件提交成功边界。

```text
用户确认发送附件
→ 创建 OriginalRecord
→ 保存 Attachment 原始内容或原始链接引用
→ 建立关联关系
→ 登记附件解析任务或“未安排深度解析”状态
→ 返回附件已保存
```

不能出现：

```text
用户看到附件已发送
但原始记录没有保存
或附件没有关联
或系统没有任何可追踪的后续处理状态
```

附件提交成功不等于附件解析成功。

### 问题 11：v1.0 附件解析状态如何表达？

**推荐答案：** 附件对象、附件解析结果和后台任务分别保存状态。

建议语义：

```text
未安排深度解析（v1.0）
→ 排队中
→ 执行中
→ 成功
→ 失败
→ 可重试 / 已取消
```

职责分层：

- `Attachment`：当前解析状态，用于界面和查询。
- `AttachmentParseResult`：每次解析尝试、解析类型、成功结果或错误摘要、当前采用结果。
- `BackgroundJob`：排队、执行、失败、取消、重试、幂等和补偿状态。
- `AnalysisRun`：附件解析成功后触发补充输入分析时使用，不替代附件解析记录。

同一附件可以有多次解析尝试，但只能有一个当前采用的成功结果。

### 问题 12：网页链接在 v1.0 如何保存？

**推荐答案：** 用户提交的原始链接本身是附件原始内容；页面标题、正文、快照、重定向结果和提取文本只能作为后续派生解析结果。

v1.0：

```text
保存原始链接
+ 关联原始记录
+ 支持删除、来源追溯和导出
```

v1.0 不承诺：

- 页面可访问；
- 网页全文抓取；
- 页面快照；
- 跟随重定向；
- 动态网页解析；
- 登录页面解析；
- 网页内容进入 RAG。

网页链接解析会产生对外网络访问。v1.1 如增加该能力，需要在外部网页访问、隐私和内容获取策略中继续明确，不在本文件锁定。

### 问题 13：附件解析失败后怎么办？

**推荐答案：** 坚持：

```text
附件保存成功
≠ 附件解析成功
```

解析失败时：

- 原始附件和原始记录继续保留。
- 保存可展示的失败状态和最小错误摘要。
- 不凭空生成附件摘要、事实、行动候选、记忆候选或可检索正文。
- 不因失败删除原始附件。
- 不以失败结果覆盖已有有效解析结果。
- 可重试失败保留任务和尝试关系。
- 图片和文件解析失败后仍可导出原始文件；网页解析失败后仍可导出原始链接。

附件解析失败与原始记录分析失败是两条独立失败链路，不能互相覆盖。

### 问题 14：同一附件或链接重复提交时如何处理？

**推荐答案：** 保留每次用户提交的原始记录语境和附件关系，不自动逻辑合并。

- 同一文件、图片或链接在不同原始记录中出现，仍可以分别存在。
- 内容哈希可以在后续用作可能重复提示或物理存储复用依据，但不能改变逻辑来源关系。
- 相同链接字符串不等于网页内容相同。
- 相同文件内容不等于两次输入业务语义相同。
- 解析任务以附件和解析上下文为边界做幂等，不能产生多个并列当前解析结果。

物理去重、存储复用、哈希规则和相似附件提示仍待后续技术选型。

### 问题 15：输入分析何时触发？

**推荐答案：** 文字提交、语音转写确认提交后，都先保存原始记录，再启动输入分析。

```text
用户确认提交
→ OriginalRecord
→ AnalysisRun
→ 输入分析
→ StructuredAnalysis
→ CandidateItem
→ 必要时 ConfirmationBatch
→ 普通回复和 / 或确认卡片
```

需要区分：

- 文字输入：提交后启动分析。
- 语音输入：确认转写后启动分析。
- 附件输入：原始保存后可进行基础记录分析；附件深度解析完成后可再触发补充分析。
- 用户主动重新分析：创建新的 AnalysisRun 和新的结果版本。
- 模型连接测试：不属于输入分析，不创建原始记录、候选或确认批次。

普通聊天可以执行轻量分析或普通回复生成，但不因为启动分析就强制展示确认卡片。

### 问题 16：输入分析经过哪些调用链？

**推荐答案：** 输入分析由 Local Core 编排，客户端不得直接调用外部模型。

```text
OriginalRecord
→ 分析编排器
→ 判断是否需要个人 RAG
→ 结构化筛选和必要检索
→ 最小上下文组装
→ 外发请求构造
→ Sensitive Information Policy Hook
→ Model Gateway
→ 用户选择的当前模型
→ 响应协议解析
→ 结构化结果校验
→ 业务边界、来源和候选校验
→ 保存分析结果和候选
→ 返回助手回复与交互数据
```

每次模型重试或切换：

- 重新确认任务上下文；
- 重新组装外发载荷；
- 重新经过敏感信息处理；
- 不改变用户当前默认模型和模型列表顺序。

模型选择、超时、重试和协议兼容规则遵循《v1-模型配置与调用》。模型调用不能绕过敏感信息处理和 Local Core。

### 问题 17：输入分析至少提取哪些信息？

**推荐答案：** 结构化分析结果至少表达以下语义，不在本文件固定 JSON Schema 或提示词。

```text
内容摘要
事实
问题
目标候选
行动候选
截止时间候选
现实限制候选
长期记忆候选
建议
不确定性、冲突和推测说明
```

分析结果还需要关联：

```text
来源原始记录
分析运行
结果版本
分析时间
分析状态
是否部分成功
使用模型
是否调用个人记忆
是否发生敏感处理
```

候选项至少表达：

```text
候选类型
候选内容
来源和依据
可信度
表达方式
敏感标记
业务影响
是否需要确认
用户修改内容
候选状态
```

无法建立来源、关键字段不完整或业务语义无法校验的模型内容，不得形成可提交的正式变更候选。

### 问题 18：普通聊天和确认卡片如何区分？

**推荐答案：** 确认卡片不是输入分析默认产物，只在存在需要用户确认的正式业务变更候选时展示。

只返回普通回复的情况：

- 普通闲聊；
- 一般知识问答；
- 普通问题回答；
- 内容摘要；
- 普通事实抽取；
- 建议和建议依据；
- RAG 检索结果；
- 不涉及正式对象变化的不确定性说明。

需要展示确认卡片的情况：

- 创建或修改正式目标；
- 创建或修改行动；
- 修改行动或目标状态；
- 修改截止时间；
- 保存长期记忆；
- 记忆冲突更新或旧记忆过期；
- 保存正式决策记录；
- 建议转化为正式行动；
- 需要确认的处境结论；
- 删除或彻底删除对象。

同一输入可以同时返回：

```text
普通助手回复
+
结构化候选确认卡片
```

卡片展示、默认选中、展开、编辑、关闭页面或后台提醒都不构成确认。

### 问题 19：一条输入包含多个事项时如何处理？

**推荐答案：** 保持原始记录完整，在分析结果内部拆分多个独立候选。

```text
一条 OriginalRecord
→ 一次 AnalysisRun
→ 一份 StructuredAnalysis
→ 多个 CandidateItem
→ 一个 ConfirmationBatch
→ 分别创建或更新正式对象
```

规则：

- 每个目标、行动、记忆、决策或正式变更候选独立处理。
- 用户可以逐项确认、修改、取消或暂不处理。
- 候选之间可以关联到同一目标、同一来源或同一分析结果。
- 一次确认可以提交不同类型候选。
- 单次确认提交内部必须原子化。
- 跨多次用户操作允许批次部分处理。
- 省略候选不等于取消；候选保持待确认。
- 被取消候选未来再次提出时，使用新的候选标识。

### 问题 20：事实、候选和建议如何区分？

**推荐答案：** 三者不能混用。

#### 事实

事实是有来源的陈述，可以自动保存，但必须带有：

```text
来源
时间
可信度
表达方式
当前状态
敏感标记
确认状态
```

事实不自动代表当前有效结论，也不自动升级为长期记忆。

#### 候选

候选是可能需要用户确认的业务或长期理解变化，例如目标、行动、记忆、决策、状态变更、截止时间变更和删除。

候选必须进入确认中心后才可能产生正式对象。

#### 建议

建议是助手给出的可选方案：

```text
建议生成
→ 用户采纳或要求执行
→ 行动候选
→ 用户确认
→ 正式行动
```

建议本身不是行动，模型提出建议不等于系统已经创建行动。

#### 推测

助手推测必须明确标记为推测、线索、低可信度或待确认，不能伪装成已确认事实、现实限制、行动状态或长期记忆。

### 问题 21：分析失败、部分成功和重新分析怎么处理？

**推荐答案：** 原始记录保存与分析成功严格解耦。

#### 完全失败

```text
OriginalRecord：保留
AnalysisRun：失败
StructuredAnalysis：不产生有效候选，或只保存失败摘要
CandidateItem：不创建非法候选
ConfirmationBatch：不创建可提交批次
正式对象：不创建或修改
```

#### 部分成功

只有协议和业务校验通过的部分可以保存，例如：

```text
摘要成功
普通事实提取成功
问题识别成功
但目标、行动或记忆候选失败
```

部分成功不能被包装成完整成功。关键字段不完整、来源不可信或业务语义无效时，不创建对应候选。

#### 自动恢复

遵循模型调用的有限恢复规则：

- 暂时性网络、超时、限流和临时服务错误可在预算内重试。
- 同一模型最多一次受控重试。
- 结构化结果无效可一次受控重试。
- 每次重试重新经过敏感信息处理。
- 全部失败后停止自动恢复，等待用户主动重新分析。

#### 重新分析

重新分析创建新的运行和结果版本：

```text
OriginalRecord
├── AnalysisRun / StructuredAnalysis 版本 A
└── AnalysisRun / StructuredAnalysis 版本 B
```

重新分析不得：

- 改写原始记录；
- 静默覆盖旧分析结果；
- 自动撤销或修改已确认正式对象；
- 复用旧候选标识作为新的正式变更候选。

### 问题 22：输入分析何时使用 RAG，如何处理敏感信息？

**推荐答案：** 只有当前输入确实需要个人上下文时按需启用 RAG，不默认读取全部历史。

输入分析优先可用：

```text
当前目标
当前行动与截止时间
当前有效限制
当前有效长期记忆
相关行动结果
相关决策和复盘结果
必要事实
最近相关原始记录
已解析附件的有效派生结果
```

RAG 使用遵循：

- 已确认正式对象正常使用。
- 自动抽取事实携带来源和可信度。
- 待确认候选受限召回且带状态。
- 已取消候选不作为普通正向依据。
- 过期内容普通建议排除，历史复盘可使用。
- 已删除原始记录原文和已彻底删除内容不得召回。

最终外发载荷：

```text
当前输入
+ RAG 结果
+ 处境和记忆上下文
→ 最终外发载荷
→ 敏感信息处理
→ Model Gateway
```

外部模型不得看到未经策略处理的敏感值。重试和模型切换重新执行敏感处理。隐私外发确认与业务变更确认独立。

### 问题 23：结构化结果如何交给确认中心？

**推荐答案：** 只有通过结构化、来源和业务边界校验的正式变更候选才创建确认批次。

```text
StructuredAnalysis
→ 筛选需要确认的 CandidateItem
→ 创建 ConfirmationBatch
→ 展示候选、来源和影响
→ 用户逐项编辑、取消、保留或暂不处理
→ SubmitConfirmationBatch
→ Local Core 校验
→ 原子写入正式对象
→ 登记 IndexUpdateJob
```

普通摘要、事实、问题、建议和依据不强制进入确认中心。目标、行动、记忆、决策和正式状态变更必须进入确认中心。

### 问题 24：如何禁止模型直接写入正式对象？

**推荐答案：** 模型输出只停留在分析和候选层。

```text
模型
→ AnalysisRun
→ StructuredAnalysis
→ 事实 / 建议 / 候选 / 待确认内容
```

模型不得直接生效：

- 正式目标；
- 正式行动；
- 长期记忆；
- 决策记录；
- 目标或行动状态变化；
- 截止时间修改；
- 记忆过期或冲突覆盖；
- 删除或彻底删除；
- 索引中的正式业务状态变化。

正式对象必须经过：

```text
模型输出校验
→ CandidateItem
→ 用户明确确认
→ Local Core 业务校验
→ 事务写入
```

## 4. 输入、附件和分析的任务关系

```text
InputSubmission
├── OriginalRecord
│   ├── SessionMessage 引用
│   ├── Attachment（0..N）
│   │   ├── AttachmentParseResult（0..N）
│   │   └── AttachmentParseJob（0..N）
│   └── AnalysisRun（1..N）
│       ├── StructuredAnalysis
│       ├── Fact
│       ├── CandidateItem（0..N）
│       ├── Suggestion（0..N）
│       └── ConfirmationBatch（0..N）
└── 输入提交状态和幂等关系
```

任务边界：

- 输入提交任务：负责原始记录、用户消息引用和输入分析登记。
- 附件解析任务：负责附件派生内容，不影响原始附件保存。
- 输入分析任务：负责基于原始记录及可用上下文生成分析结果。
- 附件补充分析任务：附件解析成功后可创建新的分析运行，不覆盖原分析。
- 用户主动重新分析：创建新的分析运行和版本，不改写已确认对象。

## 5. 已确认边界、本轮采用规则和待决策项

### 5.1 已确认边界

- 用户不需要先选择记录、目标、行动或记忆等业务类型。
- 支持文字、语音、图片、网页链接和文件上传。
- 语音转写必须由用户检查、修改并确认后才能发送。
- 未确认语音转写不得分析、提取记忆或创建行动。
- 每次用户发送内容形成原始记录。
- 原始记录自动保存；正式目标、行动和长期记忆需确认后创建或写入。
- 附件先保存原始内容，再异步解析；失败不影响原始附件保存。
- v1.0 先保证附件接收和保存；深度解析后置 v1.1。
- 结构化分析识别摘要、事实、问题、目标、行动、截止时间、限制、记忆候选和需要确认的内容。
- 普通聊天不强制展示确认卡片；发现正式变更候选时展示结构化内容。
- 一段输入含多个事项时自动拆分多个候选，创建正式对象前统一确认。
- 外部模型调用前必须经过敏感信息处理；模型重试也重新处理。
- 模型不能直接创建或修改正式对象。

### 5.2 本轮采用的详细规则

1. 文字提交和确认后的语音提交统一使用 `input_submission_id` 保证输入级幂等。
2. 原始记录、用户消息引用和输入分析任务登记构成输入提交成功边界。
3. 语音草稿、已提交分析和已保存原始记录分别拥有取消语义，不互相替代。
4. 外部语音转写属于独立隐私外发边界，未确定前不得作为静默默认路径。
5. 附件型输入允许原始记录正文为空，但必须有至少一个附件。
6. 网页链接作为原始链接附件保存，访问结果只能作为派生解析数据。
7. 附件解析任务、附件解析结果、输入分析任务独立保存状态。
8. 附件解析失败与输入分析失败互不回滚。
9. 输入分析按需启用 RAG，不默认读取全部个人历史。
10. 重新分析和附件补充分析创建新运行、新结果和新候选，不静默覆盖历史或正式对象。
11. 只有通过来源、结构化和业务边界校验的候选才进入确认中心。
12. 模型输出中的“已创建、已完成、已保存、已删除”等表述必须视为待校验文本或候选意图，不能直接展示为已生效。

### 5.3 仍待决策项

以下内容不因本文件而锁定：

- 语音转写供应商、SDK、协议、模型、音频编码和录音时长。
- 本地转写和外部转写的最终技术选型。
- 原始音频是否长期保存、保留期限、临时清理和额外加密。
- 外部语音转写的隐私确认交互、单次放行和取消语义。
- 文本、录音、图片、网页链接和文件的格式、大小、权限和上传限制。
- 网页抓取、网页快照、重定向、动态页面、登录内容和失效链接处理。
- OCR、文档抽取、网页解析的本地或外部实现、模型和重试策略。
- 附件内容哈希、物理去重、存储复用和相似附件提示。
- 附件解析自动重试次数、间隔和用户操作入口。
- 精确提示词、JSON Schema、模型供应商字段映射和结构化输出协议。
- 输入分析的具体超时、模型预算、上下文长度和重试参数。
- 彻底删除附件的物理清除范围、备份处理和恢复边界。

## 6. 验收标准

### 6.1 统一入口和文字提交

- 用户无需预先选择业务类型即可提交文字、语音或附件。
- 空白文字不创建原始记录。
- 文字提交成功后存在原始记录、用户消息引用和输入分析登记。
- 用户重复点击发送不会创建重复原始记录。
- 用户后来再次发送相同文本会形成新的原始记录。

### 6.2 语音确认

- 语音转写可被用户查看和编辑。
- 未确认转写不会创建原始记录、正式消息、分析、候选或正式对象。
- 确认后的最终文本成为原始记录正文。
- 语音转写确认不会自动创建行动、目标或长期记忆。
- 外部语音转写不能绕过隐私外发边界。

### 6.3 附件

- 图片、网页链接和文件可以形成关联附件。
- 附件保存成功不依赖解析成功。
- v1.0 不把未深度解析附件伪装为已获得正文或事实提取。
- 网页解析失败不影响原始链接保存和导出。
- 附件重复提交保留各自原始记录语境。
- 删除或彻底删除后，附件内容不会继续作为普通 RAG 依据或被索引重建恢复。

### 6.4 输入分析和结构化提取

- 文字提交和语音确认提交会创建输入分析运行。
- 输入分析可提取摘要、事实、问题、目标、行动、截止时间、限制、记忆候选、建议和不确定性。
- 普通聊天不强制展示确认卡片。
- 正式业务候选会进入确认批次。
- 一条输入中的多个事项可以拆成多个独立候选。
- 模型失败不会丢失原始记录。
- 部分成功不会生成不完整或无来源的正式变更候选。
- 重新分析不会改写原始记录或已确认正式对象。

### 6.5 安全、RAG 和确认

- 输入分析按需读取个人 RAG，不默认读取全部历史。
- 最终外发载荷包含输入和上下文后统一经过敏感信息处理。
- 每次重试和模型切换重新执行敏感处理。
- 模型不能直接写入正式对象。
- 正式变更必须经过确认中心和 Local Core 事务。

## 7. 与其他子需求的边界

- **《v1-原始记录与结构化存储》：** 定义 OriginalRecord、Attachment、AnalysisRun、StructuredAnalysis、CandidateItem、任务和来源关系的数据边界；本文件定义它们在输入阶段如何创建和衔接。
- **《v1-确认中心》：** 定义候选处理、确认批次、确认命令和正式写入；本文件定义何时产生可交接候选。
- **《v1-模型配置与调用》：** 定义模型选择、协议、重试和日志；本文件定义输入分析作为业务任务如何接入该调用链。
- **《v1-敏感信息处理》：** 定义外发策略、识别和隐私确认；本文件定义输入、附件和可能外部语音转写的外发边界。
- **《v1-事实与长期记忆》：** 定义事实和记忆生命周期；本文件定义输入分析如何产出事实和记忆候选。
- **《v1-RAG与处境模型》：** 定义检索场景、状态过滤和最小上下文；本文件定义输入分析何时按需启用 RAG。
- **《v1-行动状态机》与《v1-目标状态机》：** 定义正式状态变化；本文件只能产出状态候选，不直接变更状态。
- **后续《v1-数据导出》：** 定义输入、附件、解析结果和分析版本的具体导出格式与加密。

## 8. 当前不做的事情

v1.0 暂不做：

- 深度 OCR、网页抓取、文档内容抽取和附件语义检索。
- 自动把附件内容转为正式事实、目标、行动或长期记忆。
- 未经用户确认的语音转写内容分析。
- 未经隐私策略处理的外部语音转写或附件解析外发。
- 让模型直接写入正式对象。
- 用一次重新分析覆盖历史分析或已确认对象。
- 在本文件中锁定语音、OCR、网页解析、文件抽取或模型供应商技术选型。
