## 1. 文档目的与边界

本文件回答：

```text
一项已经被用户确认创建的行动，
在待做、执行、暂时搁置、完成、取消和超过截止时间时分别代表什么，
哪些变化可以发生，谁可以提出、谁可以确认，
以及这些变化如何与确认中心、提醒、摘要、复盘、RAG 和存储一致地协作？
```

本文件只定义行动的业务状态机，不定义：

- 目标状态机；
- 提醒渠道、用户时区、具体提醒时间和再次提醒间隔；
- 周期性/重复行动；
- 数据库、接口、任务调度器和索引产品；
- 归档、软删除和彻底删除的完整对象生命周期；
- `ActionResult` 的具体表结构和完整复盘模板。

行动状态不能替代候选状态、确认批次状态、提醒状态、索引任务状态或对象删除状态。它们分别记录不同事实：

```text
候选项：用户是否已确认某个拟议变更
行动执行状态：这件事现在是否仍要做、是否正在做、是否完成或取消
行动时效状态：已确认截止时间相对于当前时间是否到期
提醒状态：某次通知是否已发送、关闭、稍后或失败
删除/归档状态：对象在日常界面和检索中是否可用
```

## 2. 关键问题

### 问题 1：行动应只有一个状态，还是要区分“是否在做”和“是否到期”？

**推荐答案：** 采用“已确认的执行状态 + 已确认的计划状态 + 自动计算的时效状态”三个维度，不把“已延期”或“已过期”与“待开始/进行中/暂时搁置”混成互斥的执行状态。

原因是：延期是用户对计划日期的确认，截止时间到达只是时间事实；二者都不等于用户决定暂停、取消或完成。若把它们混进单一执行状态，会丢失“行动仍要做”的语义，也会违反“修改行动状态需要确认”的边界。

```text
用户确认的执行状态：待开始 / 进行中 / 暂时搁置 / 已完成 / 已取消
                 +
用户确认的计划状态：正常 / 已延期
                 +
系统按当前时间计算的时效状态：无截止时间 / 未过期 / 已过期
                 ↓
用户看到的组合状态，例如：进行中（已延期）、待开始（已过期）
```

### 问题 2：延期是否应当成为一个长期状态？

**推荐答案：** 延期不是执行状态，也不是“已不做”的状态；但它应保留为产品可见的计划状态“已延期”。

延期确认后，行动保留原执行状态，并将计划状态标记为“已延期”：

```text
待开始 + 延期 → 仍为待开始，使用新截止时间
进行中 + 延期 → 仍为进行中，使用新截止时间
暂时搁置 + 延期 → 仍为暂时搁置，使用新截止时间
```

系统同时保留延期前后时间、确认操作和可选原因，供追溯与复盘。延期不能隐式完成、取消、暂时搁置或重新创建行动。

### 问题 3：截止时间已到但用户没有决定下一步时，系统应如何表达？

**推荐答案：** 表达为“已过期”，其业务含义固定为：**行动尚未完成、尚未取消，且没有用户已确认的新截止时间或其他下一步决定。**

“已过期”由当前时间和已确认截止时间计算；它不是后台任务写入的正式执行状态。若存在尚未确认的延期候选，行动仍显示“已过期（存在待确认延期建议）”，不能提前按候选新日期恢复为未过期。

### 问题 4：暂时搁置与取消的区别是什么？

**推荐答案：** 暂时搁置是可恢复的暂时不推进；取消是用户确认“不再做”。

```text
暂时搁置：保留行动、来源和截止时间，之后可以确认恢复
取消：正常前向流程中不再恢复为待开始或进行中；如未来仍要做，应创建新的行动
```

取消后的原行动仍可用于历史、复盘和来源追溯；它不再参与当前执行建议或到期提醒。确认中心允许在满足版本条件时撤销最近的取消操作，但这是一条新的反向操作，不是普通的“取消 → 恢复”前向转移。

### 问题 5：助手识别到用户可能已经完成行动时，能否自动完成？

**推荐答案：** 不能。助手、RAG、每日摘要、提醒和周复盘都只能生成“可能完成”的候选，并说明依据；只有用户确认后，Local Core 才能把行动改为已完成。

用户在界面点击“完成”也不等于客户端直接写库。该操作必须形成可确认的状态变更意图，并由 Local Core 校验当前版本、当前状态和确认要求后提交。

### 问题 6：是否允许从已完成或已取消直接重新开始？

**推荐答案：** 不允许普通前向转移直接重开终态行动。

- 用户发现已完成判断有误，或误取消了行动：走确认中心的“撤销原状态变化”流程；
- 用户决定再次做一件已取消或已完成的事：创建新的行动，并可关联原行动作为来源或历史参考；
- 不通过修改旧行动来抹去完成、取消和历史结果。

这样可以保留执行结果和复盘证据，避免历史统计被静默改写。

## 3. 推荐答案：本轮采用的状态模型

本轮建议固定以下模型；其与上游已确认边界的关系见第 9 节。

### 3.1 执行状态

执行状态采用产品侧已确认的用户语言：

```text
待开始 / 进行中 / 暂时搁置 / 已完成 / 已取消
```

| 状态 | 含义 | 是否需要用户确认写入 | 是否为终态 | 日常执行建议 |
| --- | --- | ---: | ---: | --- |
| `待开始` | 已确认创建，仍要做，尚未确认开始执行 | 是 | 否 | 可作为当前行动 |
| `进行中` | 用户确认已开始推进，仍要做 | 是 | 否 | 可作为当前行动 |
| `暂时搁置` | 用户确认暂时不推进，但保留未来恢复可能 | 是 | 否 | 默认降级并标记暂时搁置 |
| `已完成` | 用户确认该行动已完成 | 是 | 是 | 不作为当前待办；可用于复盘 |
| `已取消` | 用户确认该行动不再做 | 是 | 是 | 不作为当前待办或正向依据 |

规则：

1. 新创建且未立即确认开始的行动，初始执行状态为 `待开始`。
2. 状态必须由 Local Core 在确认成功事务中写入；客户端、模型、RAG、索引和后台任务均不能直接写入。
3. `开始时间` 在首次确认进入 `进行中` 时写入；`完成时间` 在确认进入 `已完成` 时写入；取消、暂时搁置、延期分别记录对应关键信息。
4. 已完成或已取消不因时间、提醒、模型推断或关联目标变化而自动改变。
5. 归档、软删除和彻底删除是对象生命周期字段，不是上述执行状态的同义词。

### 3.2 计划状态

| 状态 | 判定条件 | 是否写入行动执行状态 | 含义 |
| --- | --- | ---: | --- |
| `正常` | 最近一次确认未改变截止时间 | 否 | 按当前计划执行 |
| `已延期` | 用户确认修改了截止时间，但行动仍然要做 | 否 | 保留延期前后时间和原因，不改变执行状态 |

`已延期`是产品可见的计划状态，不是执行状态，也不是终态。它可以与`待开始`、`进行中`或`暂时搁置`同时出现。

### 3.3 时效状态

| 状态 | 判定条件 | 是否写入行动执行状态 | 含义 |
| --- | --- | ---: | --- |
| `无截止时间` | `deadline_at` 为空 | 否 | 行动没有已确认的到期约束 |
| `未过期` | 非终态行动且 `deadline_at` 晚于当前时间 | 否 | 仍在已确认期限内 |
| `已过期` | 非终态行动且 `deadline_at` 不晚于当前时间，且无用户已确认的新截止时间 | 否 | 到期未完成、未取消，用户尚未确认下一步 |
| `不适用` | 执行状态为已完成或已取消 | 否 | 终态行动不再生成到期提醒 |

`已延期`和`已过期`都可以与执行状态组合出现。`已过期`仅改变展示、检索排序、提醒候选和复盘统计，不会自动把执行状态改为暂时搁置、取消或完成。

### 3.4 延期、开始、恢复和完成是操作，不是新增执行状态

| 操作 | 前提 | 写入结果 |
| --- | --- | --- |
| 创建 | 用户确认行动候选 | 创建 `待开始` 行动；若用户同时确认开始，可直接创建为 `进行中` |
| 开始 | 当前为 `待开始` | 改为 `进行中`，记录开始时间 |
| 暂时搁置 | 当前为 `待开始` 或 `进行中` | 改为 `暂时搁置`，记录暂时搁置信息 |
| 恢复 | 当前为 `暂时搁置` | 由用户选择恢复为 `待开始` 或 `进行中` |
| 完成 | 当前为任一非终态状态 | 改为 `已完成`，记录完成时间和可选行动结果 |
| 取消 | 当前为任一非终态状态 | 改为 `已取消`，记录取消信息和可选原因 |
| 延期 | 当前为任一非终态状态且有新截止时间 | 执行状态不变，计划状态变为`已延期`，更新截止时间、延期信息和提醒计划 |
| 修改内容/截止时间 | 行动存在且可修改 | 不改变执行状态；仍须确认、版本校验和变更记录 |

## 4. 状态定义

### 4.1 `待开始`

行动已被用户确认创建，仍需完成，但用户尚未确认已经开始推进。它可以有截止时间、提醒和关联目标，也可以独立存在。

`待开始`不表示助手可以自行催促或擅自开始；它只允许在既定频率限制内生成提醒、摘要或建议。

### 4.2 `进行中`

用户已确认自己正在推进该行动。该状态不要求记录工时，也不表示系统知道实时进度；它只是用户确认的执行阶段。

若助手从输入中推断“似乎已做完”或“似乎停止了”，只能提出完成、暂时搁置或取消候选，不能据此写入任何状态。

### 4.3 `暂时搁置`

行动仍保留、仍可能恢复，但用户暂时决定不推进。暂时搁置可保留原截止时间；如该时间已经过去，展示为`暂时搁置（已过期）`，而不是擅自延期。

暂时搁置后：

- 默认不发送普通到期提醒；是否保留或关闭未来提醒计划由本次确认变更明确记录；
- 每日摘要可在“暂时搁置事项”中低优先级展示；
- 用户恢复时可选择回到`待开始`或直接进入`进行中`；
- 暂时搁置不是取消、删除或归档。

### 4.4 `已完成`

用户确认行动已完成。完成可以从`待开始`、`进行中`或`暂时搁置`进入，以适应用户没有先点击“开始”但实际已完成的短行动。

完成后可附带`ActionResult`，包括结果摘要、实际花费时间、发生时间和来源；未填写结果不阻塞完成。助手可提出结果摘要候选，但不得把推断结果当作用户已确认的行动结果。

### 4.5 `已取消`

用户确认不再做此行动。取消前应允许填写原因或结果类型，但 v1 不要求原因必填。

取消不删除行动、来源、历史变更或已保存的结果；它只结束该行动的日常执行路径。若日后需要做相同事项，创建新行动，不直接重开旧行动。

### 4.6 `已过期`

`已过期`是用户可见的时效判断，而非独立可确认的执行状态。它表示当前时间已经越过已确认截止时间，而行动仍处于非终态。

系统应在行动详情、提醒、每日摘要、复盘和 RAG 依据中保留“已过期”标记及原截止时间。系统不得因为行动过期而：

- 自动延期；
- 自动暂时搁置；
- 自动取消；
- 自动创建替代行动；
- 自动认定用户放弃或失败。

## 5. 允许转移

### 5.1 执行状态转移表

表中“确认”表示必须经确认中心提交；“撤销”表示第 8 节定义的反向操作，不能作为普通前向按钮。

| 当前状态 | 待开始 | 进行中 | 暂时搁置 | 已完成 | 已取消 |
| --- | --- | --- | --- | --- | --- |
| 待开始 | 不适用 | 确认开始 | 确认暂时搁置 | 确认完成 | 确认取消 |
| 进行中 | 禁止 | 不适用 | 确认暂时搁置 | 确认完成 | 确认取消 |
| 暂时搁置 | 确认恢复为待开始 | 确认恢复并开始 | 不适用 | 确认完成 | 确认取消 |
| 已完成 | 仅可撤销恢复原状态 | 仅可撤销恢复原状态 | 仅可撤销恢复原状态 | 不适用 | 禁止 |
| 已取消 | 仅可撤销恢复原状态 | 仅可撤销恢复原状态 | 仅可撤销恢复原状态 | 禁止 | 不适用 |

补充规则：

- 完成、取消和暂时搁置前不要求行动必须曾进入`进行中`。
- 恢复暂时搁置时，用户必须明确选择恢复为`待开始`还是`进行中`；系统不根据猜测选择。
- 延期不出现在表内，因为它不改变执行状态；可在每个非终态状态中经确认执行。
- 当截止时间到达时，时效状态自动从`未过期`变为`已过期`；这不是表中的转移，也不需要创建确认候选。

### 5.2 与时效状态组合时允许的操作

| 当前组合 | 可提出/确认的操作 | 不得自动发生 |
| --- | --- | --- |
| 待开始（未过期） | 开始、暂时搁置、完成、取消、延期、编辑 | 任意状态写入 |
| 进行中（未过期） | 暂时搁置、完成、取消、延期、编辑 | 自动完成或自动暂时搁置 |
| 暂时搁置（未过期/已过期） | 恢复、完成、取消、延期、编辑 | 因暂时搁置或到期而取消 |
| 待开始/进行中（已过期） | 完成、暂时搁置、取消、延期、编辑 | 自动延后、自动关闭或自动创建下一步 |
| 已完成/已取消 | 查看、归档/删除流程、按条件撤销 | 再次提醒、自动重开、普通前向恢复 |

## 6. 禁止转移与禁止推断

以下规则是 v1 的硬约束：

1. 模型、助手回复、RAG 结果、处境模型、索引更新、提醒任务、每日摘要和周复盘均不得直接修改行动执行状态。
2. “可能已完成”“可能已中断”“看起来不再重要”只能生成候选；候选被默认选中、展示或重复提醒都不构成确认。
3. 截止时间到达只能产生`已过期`时效标记和受频率限制的提醒机会，不能自动延期、暂时搁置、完成或取消。
4. 延期必须保留“仍要做”的语义；不得把“延期”显示或存储成已完成、已取消或独立终态。
5. 暂时搁置必须可通过确认恢复；不得把暂时搁置当作取消，也不得因暂时搁置时间过长自动取消。
6. 已取消表示“不再做”。普通状态机不允许从已取消直接回到任何非终态；需要重新做时创建新行动。
7. 已完成、已取消都不能因关联目标、关联行动、提醒关闭、摘要生成或 RAG 判断而被静默改变。
8. 关闭本次提醒、稍后提醒、调整通知渠道和忽略摘要，只能改变提醒或摘要交互记录，不能改变行动状态。
9. 行动完成不自动完成关联目标；目标状态机独立处理该判断和确认。
10. 删除、归档和恢复不等同于完成、取消或暂时搁置；不得用对象可见性字段绕过状态机。

## 7. 确认和事务边界

### 7.1 必须进入确认中心的操作

下列操作都属于正式业务变更，必须先有候选项或即时生成的确认项，再由用户明确确认：

```text
创建行动
开始行动
暂时搁置行动
恢复行动
完成行动
取消行动
延期或修改截止时间
修改行动内容
写入或修改行动结果
撤销上述可逆变更
```

用户从行动详情主动发起的操作，可以创建“即时确认项”，以减少界面跳转；但它仍遵循确认中心的候选、风险、版本、操作标识和审计规则。客户端不得因用户点击按钮而直接更新正式对象。

### 7.2 候选所需的最小信息

行动状态候选至少要能表达：

```text
目标行动和当前版本
变更类型
变更前执行状态
变更后执行状态（延期时为“不变”）
原截止时间与新截止时间（如适用）
暂时搁置、取消或延期原因（如用户填写）
行动结果候选（如适用）
来源和提出者：用户明确指令 / 助手分析 / 提醒 / 摘要 / 复盘
风险标记、可撤销性和关联确认批次
```

涉及金钱、人员、工作安排、重要文件或其他上游定义的高风险行动时，确认卡片还必须显式展示影响、成本或风险，并要求`risk_acknowledged`；默认全选不能替代这一确认。

### 7.3 一次确认提交的事务内容

行动创建或状态变更确认成功时，Local Core 必须在同一事务边界内完成：

```text
校验候选、行动和批次版本
+ 写入用户确认操作
+ 更新候选项/确认批次状态
+ 创建或更新 Action
+ 写入延期、暂时搁置、完成或取消等关键变更记录
+ 写入 ActionResult（本次确认包含时）
+ 写入来源关系
+ 写入或更新未发送的提醒计划记录
+ 登记 IndexUpdateJob
```

其中：

- 任一正式写入失败，整次提交回滚，不留下半个行动、半条状态变化或孤立提醒计划；
- 索引任务登记必须与正式对象写入同事务成功；索引实际更新异步进行，失败后进入补偿，不回滚用户已确认的行动变化；
- 通知实际发送不在上述事务内。事务只保证其计划记录与已确认状态一致；
- 同一确认批次可分多次处理，但单次提交仍遵循全有或全无。

### 7.4 状态校验顺序

Local Core 在提交前至少依次校验：

```text
候选仍处于可确认状态
→ 候选版本匹配
→ Action 存在、未删除且对象版本匹配
→ 当前执行状态允许目标状态
→ 延期的新截止时间有效
→ 高风险确认已明确完成
→ 幂等操作标识和命令指纹一致
→ 再执行事务写入
```

若行动在用户查看确认卡片后已被其他本地操作更新，返回版本冲突并要求重新加载；不得静默以旧状态覆盖新状态。

## 8. 提醒、摘要、复盘与 RAG 的交叉边界

### 8.1 提醒

提醒系统读取行动执行状态、时效状态和已确认提醒计划，但不拥有行动状态写入权。

| 提醒交互 | 允许行为 | 禁止行为 |
| --- | --- | --- |
| 到达明确提醒时间 | 发送一次通知并更新提醒自身状态 | 自动完成、暂时搁置、取消或延期行动 |
| 截止时间已过 | 生成每日最多一次的逾期集中提醒机会 | 把过期写成正式状态变化 |
| 点击“完成” | 生成完成确认项 | 直接标记已完成 |
| 点击“延期” | 生成包含新日期的延期确认项 | 先改日期再确认 |
| 点击“暂时搁置” | 生成暂时搁置确认项 | 直接搁置行动 |
| 关闭本次/稍后提醒 | 改变本次提醒或下次通知计划 | 静默改变行动状态 |

已完成和已取消行动应取消或失效未来未发送提醒计划；这项计划变更随状态变更事务一并写入。具体通知渠道、时区、补偿时机和提醒间隔仍由《v1-行动摘要与提醒》确定。

### 8.2 每日行动摘要

每日摘要可以使用当前已确认行动、截止时间、限制、行动结果和待确认内容生成展示，且可按`已过期`、`进行中`、`待开始`、`暂时搁置`分组。

每日摘要可以：

- 展示当前行动和已过期行动；
- 提示存在待确认的完成、延期、暂时搁置或取消候选；
- 提出新行动或状态变更建议；
- 说明信息不足、来源冲突或索引不完整。

每日摘要不得：

- 自动确认或执行状态候选；
- 把待确认候选显示为已完成或已延期；
- 因摘要已生成而改变行动状态；
- 绕过确认中心创建行动或修改截止时间。

### 8.3 每周复盘

周复盘可以读取历史行动、执行状态变化、延期记录、过期情况、行动结果、建议效果、当前/历史处境和过期记忆，以分析计划与实际差异、未完成原因和下一步建议。

周复盘产生的“下周行动”“完成/取消/暂时搁置判断”“延期建议”“行动结果”均为候选。统计展示可以直接给出；任何正式行动创建、状态改变、截止时间修改或结果写入仍需确认。

### 8.4 RAG 与处境模型

RAG 和处境模型只能提供状态感知的上下文与依据：

| 使用场景 | 行动状态使用规则 |
| --- | --- |
| 当前行动建议 | 优先召回待开始、进行中及其截止时间；已过期作为高优先级时效标记 |
| 日常建议 | 暂时搁置行动可作为现实限制或低优先级背景，必须标记暂时搁置 |
| 历史复盘 | 可读取已完成、已取消、暂时搁置、延期和过期历史，并保留当时状态和时间 |
| 待确认候选 | 可受限召回，但必须标记待确认，不能当作正式行动事实 |
| 已取消候选/已取消行动 | 不作为普通正向行动依据；仅在历史查看、复盘或用户明确询问时使用 |

RAG 结果、处境模型和模型输出不得直接改写 Action。若它们发现可能完成、需要延期或应暂时搁置，只能形成带依据的候选；外发上下文还必须遵循最小化与敏感信息处理边界。

## 9. 异常、幂等与撤销

### 9.1 幂等

所有行动创建和状态变更确认都使用确认中心定义的`confirmation_operation_id`和命令指纹：

```text
同一操作标识 + 相同命令内容
→ 只提交一次；重试返回 already_committed

同一操作标识 + 不同命令内容
→ 返回幂等键冲突；不执行任何新写入
```

以下重复行为不得产生重复正式副作用：

- 用户重复点击完成、延期、暂时搁置、恢复或取消；
- 客户端超时后的重试；
- 同一到期提醒的重复调度；
- 每日摘要或复盘的补偿执行；
- 索引更新任务、提醒计划任务的重试。

### 9.2 并发、失效和失败

| 情况 | 处理规则 |
| --- | --- |
| 用户打开确认卡片后行动已变化 | 返回`version_conflict`，重新加载后再决定 |
| 候选已取消、已处理或已失效 | 返回`not_confirmable`，不得恢复旧候选 |
| 延期候选未确认但原截止时间已过 | 行动显示已过期；候选仍只是待确认线索 |
| 正式写入失败 | 整个提交回滚，可使用原操作标识重试 |
| 索引更新失败 | 正式变更保持成功，索引任务进入补偿；结构化查询仍可工作 |
| 通知发送失败或 App 离线 | 只影响提醒任务记录与补偿，不回滚行动状态 |
| ActionResult 写入失败且本次把它作为确认内容 | 视为正式事务失败并回滚；不得只完成状态而丢弃用户确认的结果 |

v1 不承诺设备离线或进程终止时精确按时执行通知，但在 App 运行或用户当天打开 App 时应按持久化任务和幂等键补偿检查，且不重复改变行动状态。

### 9.3 撤销

撤销遵循确认中心既定原则：撤销是新的、可审计的反向操作，不删除原确认记录或原关键变更记录。

行动状态变更可撤销的前提：

```text
原状态变更被标记为可撤销
+ 当前 Action 版本仍等于原操作产生的版本
+ 没有后续状态、内容、结果、删除或冲突性变更
+ 原状态仍可安全恢复
+ 用户确认撤销
```

撤销成功后：

- 恢复原执行状态及必要的原截止时间/提醒计划；
- 新增一条反向`ChangeHistory`和新的确认操作；
- 登记对应索引更新任务；
- 使用独立幂等操作标识，防止重复撤销。

不能承诺撤销：

- 已彻底删除的数据；
- 已发生的外部副作用；
- 已被后续操作修改的行动；
- 已有无法安全还原的结果、合并或替代关系的状态变化。

撤销失败时不能强行覆盖当前状态；应展示冲突并允许用户创建新的行动或新的状态变更候选。

## 10. 已确认与待决策

### 10.1 上游已确认、必须遵守的边界

下列内容已由上游架构、确认中心、原始记录与 RAG 文档确认；本文件只是采用，不重新决定：

1. 创建行动和修改行动状态都必须经过用户确认。
2. 助手识别到可能完成时只能提出确认，不能自动标记完成。
3. 模型、后台任务、提醒、摘要、复盘、RAG 和处境模型不能绕过确认中心写入正式行动或状态。
4. 客户端只提交确认命令；Local Core 负责校验、正式写入、版本控制和索引任务登记。
5. 单次确认提交内的正式写入全有或全无；同一操作标识重试必须幂等；候选和正式对象使用乐观版本校验。
6. 成功事务包含正式对象、来源关系、关键变更记录和索引任务登记；索引异步失败不回滚已确认对象。
7. 提醒点击后的完成、延期或搁置仍必须通过确认规则；关闭本次和稍后提醒不应静默改变业务状态。
8. RAG 检索必须携带状态、时间、来源、可信度和确认状态；待确认内容不能冒充已确认事实；RAG 不直接产生正式状态变更。
9. 已取消候选不能被直接恢复；再次提出应使用新的候选标识。此规则适用于候选生命周期，不等于已取消行动的对象撤销机制。

### 10.2 本轮明确采用、此前尚未由上游完整确定的规则

上游文档明确把“行动状态机的完整允许和禁止转移”列为待拆分事项。为使 v1 可实现、可验收，本轮建议采用：

1. 执行状态固定为`待开始 / 进行中 / 暂时搁置 / 已完成 / 已取消`。
2. `已过期`固定为由截止时间计算的时效状态，不作为后台自动写入的执行状态。
3. `延期`固定为确认后的截止时间调整操作，行动仍要做，不是执行状态、更不是终态。
4. `暂时搁置`固定为可恢复状态；恢复时由用户明确选择`待开始`或`进行中`。
5. `取消`固定为“不再做”的终态；普通前向流程不直接恢复，未来重新做时新建行动。
6. `已完成`和`已取消`固定为终态；仅在确认中心的版本安全条件满足时，通过独立撤销操作恢复原状态。
7. 截止时间到达、摘要、提醒、RAG 判断均只能形成时效展示、提醒机会或候选，不能替代确认。
8. 状态变更事务同时维护关键变更记录、来源关系、提醒计划记录和索引任务登记。

上述八项是本文件的推荐决策，不应被表述为“技术架构总览已确认的原始结论”。在产品侧确认本文件前，实现应将其视为待确认的详细规则，而非静默改写上游基线。

### 10.3 仍待后续子需求或产品确认的事项

以下内容不由本文件锁定：

- 用户时区、提醒渠道、具体提醒时间、逾期集中提醒的交互文案和补偿窗口；
- 待确认状态候选的有效期和再次提醒间隔；
- 撤销入口保留时长、最近一次操作范围和批量撤销交互；
- 归档、软删除、彻底删除与恢复的完整操作清单和保留期限；
- 周期性/重复行动、子行动、依赖关系和批量状态变更；
- 行动结果的具体字段、结果类型枚举、复盘模板和建议效果计算；
- 目标是否引用行动状态作为进度信号的具体算法；目标完成仍不得由行动完成自动触发；
- RAG 的具体排序权重、向量/关键词实现、索引重建产品和任务调度实现；
- 高风险行动的更细分类、展示文案和是否需要单独提交。

## 11. 验收标准

### 11.1 状态语义与转移

- 用户确认创建普通行动后，行动初始为`待开始`；未确认候选不创建正式行动。
- `待开始`可以在确认后进入`进行中`、`暂时搁置`、`已完成`或`已取消`。
- `进行中`可以在确认后进入`暂时搁置`、`已完成`或`已取消`，不能普通前向返回`待开始`。
- `暂时搁置`可以在确认后恢复为`待开始`或`进行中`，也可以确认完成或取消。
- `已完成`和`已取消`不能通过普通状态操作直接重开。
- 暂时搁置不会自动取消；取消表示不再做；延期后行动仍保留为待做/进行中/暂时搁置中的原执行状态。

### 11.2 截止时间与过期

- 非终态行动的已确认截止时间到达后显示`已过期`，且保留原执行状态。
- 已过期行动不会被系统自动延期、暂时搁置、完成、取消或创建替代行动。
- 存在未确认延期候选时，原截止时间仍有效，行动仍可显示已过期。
- 用户确认延期后，系统保存新截止时间、延期记录并更新提醒计划；行动仍要做。
- 已完成和已取消行动不再以`已过期`参与当前待办和到期提醒。

### 11.3 确认、事务与来源

- 创建行动、所有执行状态变化、延期和截止时间修改都不能由客户端、模型或后台任务直接写入。
- 助手识别“可能完成”时只生成可查看依据的候选，未确认前行动状态保持不变。
- 同一确认操作重复提交不会重复创建行动、重复写状态变化、重复写行动结果或重复安排提醒。
- 同一操作标识提交不同内容被拒绝；候选或行动版本冲突不会静默覆盖。
- 一次成功的行动变更确认同时具有确认操作、Action 变化、关键变更记录、来源关系、提醒计划调整和索引任务登记；任一正式写入失败时整体回滚。
- 索引实际更新失败不回滚已确认行动变更，并能被补偿任务重试。

### 11.4 提醒、摘要、复盘与 RAG

- 同一明确提醒时间最多发送一次，逾期行动每天最多进入一次集中提醒；重复调度不重复通知。
- 关闭本次提醒或稍后提醒不会改变行动执行状态。
- 点击提醒中的完成、延期、暂时搁置或取消均先进入确认，不直接写入行动。
- 每日摘要和每周复盘可以展示状态、延期、过期和结果，但产生的正式变更均为候选。
- 当前建议能区分待开始、进行中、暂时搁置和已过期；历史复盘能保留完成、取消、延期和当时状态。
- 待确认行动或状态候选进入 RAG 时携带待确认标记，不会被描述为已经完成、已经延期或用户已确认的事实。

### 11.5 撤销与异常

- 在没有后续冲突变更且版本匹配时，用户可通过确认中心撤销一次可逆行动状态变化；撤销保留原操作和反向操作历史。
- 存在后续变更、物理删除或外部副作用时，系统拒绝自动撤销，不覆盖当前状态，并提示创建新的候选或新行动。
- App 离线、通知失败、索引失败或后台补偿不会改变已确认行动状态，也不会造成重复状态变化。
