# 项目架构说明

> 状态：通用 Agent 技术底座已收口，正式业务数据闭环暂缓
>
> 更新时间：2026 年 9 月 5 日

## 1. 项目定位

紫灵AI 是一个个人助手产品，目标是围绕个人输入、事实与长期记忆、行动、目标、确认中心、提醒和决策辅助，形成可追溯、可确认、可撤销的长期信息管理闭环。

当前技术底座已稳定以下基础边界，业务仍冻结在 P1-01 完成、P1-02 尚未开始：

- 产品需求与技术架构的对应关系；
- Local Core、NestJS、Pi Agent Runtime、Python AI/RAG 之间的职责；
- 数据库、文件存储、任务和索引的一致性边界；
- 前端、后端和 AI 服务之间的接口契约；
- 本地开发、私有部署和后续扩展的仓库组织方式。

## 2. Git 仓库策略

### 2.1 产品主仓库

当前目录 `partnerAgent` 是产品主仓库。以下内容应由主仓库跟踪：

- `docs/02-需求/` 中的产品和技术文档；
- `apps/partner-agent-backend/` 中的 NestJS 业务后端；
- `packages/contracts/` 中的跨端共享契约；
- 已初始化的 Expo / React Native 前端项目；
- 后续创建的 Python AI/RAG 项目；
- 接口契约、数据库迁移、部署文件和项目级脚本；
- 产品级 README、变更记录和开发约定。

### 2.2 Pi 参考仓库

`pi/` 是官方 Pi 项目的本地克隆，目的是方便 Agent 学习、阅读源码和进行技术分析。

它具有独立的 `.git` 和官方远程仓库，因此遵循以下规则：

- 不纳入 `partnerAgent` 主仓库；
- 不使用 Git Submodule；
- 不把 Pi 源码复制进产品目录提交；
- Pi 的 Git 操作只在 `pi/` 目录中进行；
- 对 Pi 的阅读结论可以整理到主仓库的分析文档中；
- 如果将来真正依赖 Pi，应通过明确的包版本、服务边界或独立部署方式接入，而不是把参考源码混入主仓库。

根目录 `.gitignore` 中的 `/pi/` 是这一边界的自动保护措施。

### 2.3 本地文件与敏感数据

以下内容只保留在本地，不进入 Git：

- `node_modules/`、Python 虚拟环境和缓存；
- `.env`、API Key、数据库密码和本地凭据；
- 本地数据库、上传文件、索引文件和运行时状态；
- 构建产物、测试覆盖率、日志和临时文件；
- Agent 本地会话、缓存和实验输出。

## 4. 当前服务边界

技术架构基线如下：

```text
前端
  │
  │ HTTP / WebSocket / 文件上传
  ▼
NestJS 业务后端
  │
  ├── 业务 API、认证、权限和任务编排
  ├── Local Core 领域逻辑
  ├── PostgreSQL / 文件存储
  └── Pi Agent Runtime 调用
          │
          └── Python AI/RAG 服务
```

这里的关系是产品架构边界，不表示当前所有服务都已经实现。当前只记录职责方向，不提前固化具体模块、端口或部署方式。

## 6. 何时拆分独立仓库

当前使用一个产品主仓库，不按语言拆分。只有出现以下情况时，才重新评估拆仓库：

- 模块由不同团队独立维护；
- 模块需要独立权限控制；
- 模块有完全独立的发布和部署周期；
- 模块需要作为多个产品复用；
- 主仓库体积或 CI 成本已经影响开发效率。

在这些条件出现前，单一产品仓库更有利于同步需求、接口和跨服务变更。

## 7. 变更规则

- 需求变更先更新 `docs/02-需求/` 文档，再进入实现；
- 跨模块接口变更必须同步记录契约和影响范围；
- Pi 学习结论进入分析文档，不直接改变产品架构；
- 不因为初始化某种语言就自动新建 Git 仓库；
- 不提交凭据、本地数据、依赖目录和构建产物；
- 恢复开发前，先更新本文件中的阶段状态。
