## 1. P0-1：Local Core 运行形态和通信（对应原 11.1）

### 决策项

| # | 待决策 | 默认建议 | 论证 |
|---|---------|---------|------|
| 1 | 手机端采用嵌入式核心还是本地服务进程 | **独立服务进程（本地服务）** | 技术选型已定型为"私有核心主机 + 手机走网络"，且需求明确"本地优先 = 数据在私有主机，不是每个终端独立本地库" |
| 2 | 电脑端是否使用独立 Local Core 进程 | **同一套 NestJS 服务**，不做第二个进程 | 客户端（手机/电脑）共用同一个私有核心，避免两套逻辑分叉 |
| 3 | 客户端与 Local Core 通信 | **Command/Query 走 HTTP(REST)，流式事件走 WebSocket** | 见下方论证 |
| 4 | 客户端断开后任务是否继续 | **继续**（后台任务与连接解耦，任务持久化） | 与 8.1 节"Background Job 由本地调度器执行"一致，也符合 3.2 节 Local Core 职责 |
| 5 | Local Core 启停、健康检查、崩溃恢复 | **提供 `GetCoreHealth` query + 崩溃后可重建** | 8.9 节已列 `GetCoreHealth`；崩溃恢复依赖数据库持久化 + 后台任务幂等 |
| 6 | 查询支持流式事件、轮询或两者 | **Command 可流式（响应流）/ 可轮询（任务状态），Query 默认轮询** | 聊天、答案需要流式体验；长时任务（分析、摘要、导出）用任务状态轮询 |

### 论证：为什么传输层要拆开（这是纠正当前"全塞 WS"的关键）

第 8 节开头明确"本节只定义逻辑接口，**不锁定 REST、IPC、本地 HTTP、函数调用**"。第 12 节再次强调"接口设计第一版**不需要锁定具体传输协议**"。

但当前实现把 `chat` / `cancel` / `resume_session` 全塞进一个 Socket.IO 网关。缺陷：

- Command/Query 是**请求-响应**语义（提交命令 → 返回 `operation_id`/`status`/`resource_refs`），天然适合 **REST**；
- 流式事件（`text_delta`）和**服务端主动推送**（Agent 主动推候选、提醒、摘要、确认卡）才适合 **WS 双向**；
- Local Core 职责里有大量**非流式交互**（模型配置、导出、确认批次查询、健康检查），这些用 WS 是错的。

**收口结论**：
```text
REST(HTTP)  → 所有 Command 提交 + Query 查询（幂等、版本、错误码都在 REST 层表达）
WebSocket   → 流式事件 + 服务端主动推送（聊天 token、工具过程、候选、提醒、摘要）
```

当前 `chat` 通道保留为由 REST 发起的流式长连接——即前端通过 REST 提交 `SubmitTextInput`，拿到 `response` 后订阅 WS 频道接收 `text_delta`。**不建议把`chat`/`cancel` 直接长挂在 WS 的 request/response 上。**

## 2. P0-2：Command/Query 契约（对应原 11.2）

### 决策项

| # | 待决策 | 默认建议 | 论证 |
|---|---------|---------|------|
| 1 | 通用信封字段最终命名 | 见下方 `CommandEnvelope` / `CommandResult` | 按 8.2 节字段落定，保持不变 |
| 2 | 操作标识生成规则 | **客户端生成 `operation_id`（UUID），服务端回显** | 用于幂等去重，客户端生成可跨重试保持稳定 |
| 3 | 幂等冲突返回格式 | 返回 `status: 'duplicate'` + 原 `operation_id` 对应结果 | 客户端用同一 `operation_id` 重试即得相同结果 |
| 4 | 版本冲突返回格式 | 返回 `version_error`，携带 `expected_version` / `current_version` | 乐观并发控制 |
| 5 | 同步返回和异步任务返回格式 | 短命令同步返回；长任务返回 `task_refs` 由 `GetTaskStatus` 查询 | 区分"立即生效"与"排队任务" |
| 6 | 错误码和错误分类 | 见下方统一错误码表 | 第 12 节要求"错误分类"必须锁定 |
| 7 | 分页、游标、排序和过滤 | 统一 `QueryParams`（`cursor`/`limit`/`sort`/`filter`） | 见 8.9 节查询接口通用化 |
| 8 | 查询结果的敏感字段裁剪 | 服务端在响应前裁剪，接口定义处标注 `@sensitive` | 客户端不接触原始敏感值 |
| 9 | 接口版本策略 | 契约包走 `v1` 命名空间，向后兼容规则文档化 | 避免破坏已发布客户端 |

### CommandEnvelope（提交方）

```ts
interface CommandEnvelope<P = unknown> {
  operation_id: string;          // 客户端生成的幂等标识（UUID）
  client_source: string;         // 客户端来源标识（ios/android/web）
  request_fingerprint: string;   // 请求哈希，检测同操作不同载荷
  expected_version?: string;     // 适用于有版本字段的对象（乐观锁）
  payload: P;                    // 具体命令参数
}
```

### CommandResult（返回方）

```ts
interface CommandResult<R = unknown> {
  operation_id: string;          // 回显
  status: 'accepted' | 'completed' | 'duplicate' | 'rejected';
  resource_refs?: ResourceRef[]; // 新建/更新的对象引用
  new_versions?: Record<string, string>; // 对象 id → 最新版本
  task_refs?: TaskRef[];         // 异步任务引用（长任务）
  warnings?: string[];
  validation_errors?: ValidationError[];
}
```

> 注意：`status: 'accepted'` 表示已受理但任务可能仍在排队；`completed` 表示已同步完成。二者都依赖 `operation_id` 幂等。

### 统一错误分类（第 12 节"错误分类"落定）

错误码分三层：`类别` + `领域` + `序号`。

| 错误码 | 含义 | HTTP 映射 |
|---|---|---|
| `AUTH_001` | 未认证 / 令牌无效 | 401 |
| `AUTH_002` | 所有权校验失败；会话等私有资源为防枚举按不存在处理 | 403；私有资源返回 404 |
| `AUTH_003` | 应用访问保护未通过 | 403 |
| `VALIDATION_001` | 载荷校验失败 | 422 |
| `VALIDATION_002` | 必填字段缺失 | 422 |
| `IDEMPOTENCY_001` | 幂等冲突（operation_id 已用但载荷不同） | 409 |
| `VERSION_001` | 版本冲突（expected != current） | 409 |
| `CONFIRMATION_001` | 高风险候选需单独确认 | 409 |
| `CONFIRMATION_002` | 候选已过期 / 不可确认 | 409 |
| `CONFIRMATION_003` | 候选与正式对象状态冲突 | 409 |
| `RATE_001` | 超出每用户会话数 / 限额 | 429 |
| `RATE_002` | 单会话并发请求冲突 | 429 |
| `TASK_001` | 任务已取消 | 409 |
| `TASK_002` | 任务不可重试 | 409 |
| `MODEL_001` | 模型未配置 | 503 |
| `MODEL_002` | 模型连接失败 | 502 |
| `MODEL_003` | 模型切换失败 | 502 |
| `MODEL_004` | 当前模型不可用 | 503 |
| `EGRESS_001` | 外发被阻止（拒绝发送） | 403 |
| `EGRESS_002` | 外发等待隐私决定 | 425 |
| `EGRESS_003` | 外发脱敏后允许 | 200（带标记） |
| `DEPS_001` | 来源不存在 / 已删除 | 404 |
| `DEPS_002` | 依赖的正式对象缺失 | 409 |
| `NOT_IMPLEMENTED_001` | 路由契约已登记，业务 handler 尚未实现 | 501 |
| `INTERNAL_000` | 未知内部错误 | 500 |

## 3. P0-3：正式确认和撤销（对应原 11.3）

### 决策项

| # | 待决策 | 默认建议 | 论证 |
|---|---------|---------|------|
| 1 | 删除、恢复、撤销是否全部走 `SubmitConfirmationBatch` | **是，统一走**，不提供旁路写接口 | 3.4 节、8.5 节明确 |
| 2 | 高风险候选能否与普通候选同批提交 | **不能**，高风险（敏感记忆、重要处境变更）必须拆分单批 | 前端文档 4.5 节：高风险必须有额外提示，不能"全部确认"静默处理 |
| 3 | 候选有效期 | **24 小时**，过期后需重新生成 | 已确认 |
| 4 | 撤销窗口和可撤销操作范围 | **不设固定天数**；软删除/状态变更在无后续版本冲突且仍可逆时可撤销；彻底删除、已过期候选不可撤销 | 已确认 |
| 5 | 多对象确认操作是否整体撤销 | **是**，同批次一起撤销 | 8.5 节"多对象整体" |
| 6 | 失败尝试的最小记录模型 | 记录 `operation_id` + `attempts` + `last_error` | 幂等 + 可重试 |

### SubmitConfirmationBatch 信封（草案）

```ts
interface SubmitConfirmationBatchPayload {
  items: ConfirmationItem[];        // 一个或多个候选
  mode?: 'confirm' | 'cancel' | 'edit';  // 编辑=修改后再确认
}

interface ConfirmationItem {
  candidate_id: string;
  kind: 'goal' | 'action' | 'fact' | 'memory' | 'decision' | 'situation' | 'reminder';
  action: 'create' | 'update' | 'status_change' | 'archive' | 'soft_delete' | 'permanent_delete' | 'restore' | 'undo';
  expected_version?: string;
  risk?: 'normal' | 'high';         // 高风险强制拆分单批
}
```

其中 `archive`、`soft_delete`、`permanent_delete`、`restore`、`undo` 是不可混用的显式生命周期动作；不得再用含糊的 `delete` 依赖 payload 推断语义。撤销资格查询必须返回原 `confirmation_action_id`、原 `confirmation_batch_id`、整批撤销范围以及因可逆性、版本冲突或不兼容后续变更产生的阻塞原因；撤销本身仍需新的 `SubmitConfirmationBatch`，不设固定 TTL。

## 4. P0-4：状态机正式冻结（对应原 11.4）

### 决策项

| # | 待决策 | 默认建议 | 论证 |
|---|---------|---------|------|
| 1 | Action 三维状态模型是否升级为正式实现基线 | **是**，执行/计划/时效三维拆分 | 4.5 节明确"进行中（已过期）"需分开表达 |
| 2 | Goal 状态转移和"已过期"确认规则 | **Goal 不因 Action 完成自动完成；Goal 到期不自动改状态** | 4.6 节 + 前端 4.8 节 |
| 3 | 目标和行动的恢复、重建和关联变更 | **恢复走确认中心；重建不破坏原对象的来源 + 变更历史** | 3.8 节来源可追溯 |
| 4 | Fact 高风险场景是否需要独立确认 | **是**；`ExtractedFact/FactCandidate` 可作为非正式分析产物保存，进入 `business_objects` 的 Confirmed Fact 一律经确认批次，敏感/重要事实必须单独确认 | 前端 4.10 节敏感事实单独提示 |
| 5 | Memory 冲突、合并、恢复和删除边界 | **冲突生成候选待用户确认；合并不产生新事实；过期标记非删除** | 4.8 节 + 3.8 节 |

### Action 三维状态（冻结基线，来自 4.5 节）

```text
执行状态 execution: todo | in_progress | paused | done | cancelled
计划状态 plan:       normal | rescheduled
时效状态 timeliness: no_deadline | not_due | overdue | not_applicable
```

三条状态**独立表达、可组合**（如"进行中（已过期）" = 执行 `in_progress` + 时效 `overdue`）。

### Goal 状态（冻结基线，来自 4.6 节）

```text
goal_status: planning | active | completed | paused | abandoned | expired
```

- Goal 不因 Action 全部完成而自动完成（需确认）。
- Goal 到期不自动改变状态（只将 `goal_deadline_observation` 置为 `due`）；进入 `expired` 必须由用户确认。
- `archived` 属于 `lifecycle_status`，不是 Goal 业务状态。

## 5. 收口后锁定契约范围（第 12 节顺序）

接口设计第一版，按第 12 节顺序先做前 9 项，**不先写客户端页面**：

```text
1. 通用 Command/Query 信封                    ← 本文档第 2 节已定
2. 聊天会话、输入提交与输入级幂等              ← 下一份契约实现
3. 聊天响应任务、流式事件和取消
4. 陪伴聊天的上下文读取与回复查询
5. 辅助解答、想法梳理和经历回顾的按需 RAG/依据接口
6. 按需分析、建议和决策辅助任务
7. 行动协助入口与行动候选
8. 候选与确认批次查询
9. SubmitConfirmationBatch                     ← 本文档第 3 节已定
10+（P1 后续）Action/Goal 状态校验、Reminder、Context、摘要复盘、Export、索引健康
```
