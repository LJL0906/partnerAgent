# 多实例任务执行与事件分发

> 状态：**Accepted / 技术研发已实现**
> 日期：2026 年 9 月 5 日
> 范围：通用 Agent Runtime，不涉及 Action、Goal、Memory 等业务能力。

## 背景

本文最初用于解决 ChatTask 虽已由 PostgreSQL 持久化、执行唤醒和 WS 重放仍依赖单进程内存的问题。该问题现已按下述 PostgreSQL 路线完成技术实现；当前产品仍按个人单实例部署，多实例能力是可靠性余量，不是现阶段扩容目标。

## 当前实现（2026 年 9 月 5 日）

- ChatTask 已实现 PostgreSQL 原子认领、lease/fencing、续租、过期回收、同 session 串行和优雅停机；
- task 提交后通过 `LISTEN/NOTIFY` 唤醒，并以 polling 兜底通知丢失；
- WS v1 已持久化脱敏 wire event 与每流 position，跨实例通知只传 event id，客户端可按 `event_id + stream_key` 重放；
- WS LISTEN 恢复后会对本实例活跃 stream 按最后已完成本机投递的 position 主动 catch-up；catch-up 与实时 notification 按 stream 串行并以 event id 去重，超过可配置保留窗口后发送 `recovery_required` + REST 权威对账；
- ChatTask 的 queued/running/waiting/completed/failed/cancelled 状态转换与 lifecycle outbox 行已在同一事务提交，relay 使用稳定幂等键、`FOR UPDATE SKIP LOCKED`、lease/fence 与有限重试；`ws_v1_events` 仍只是通知和短期恢复载体，不是业务真相源；
- 工具确认、拒绝、执行结果和撤销通知已纳入独立 `tool_control_outbox`，状态变更与事件写入同事务提交；relay 使用稳定事件键、租约令牌、同会话头阻塞和有限重试；
- 达到最大尝试次数的毒性 outbox 事件可通过本地、数据库权限保护的 `retry` / `discard` 命令处置，命令要求精确并发校验和确认短语，并写入脱敏审计；
- WS 事件按 count 与 age 双上限后台分批清理，`ws_v1_event_streams` 的单调 position 不随事件删除而归零；
- typed metrics 和 metadata-only trace 已接入，Provider retry 在无可靠 attempt hook 时明确标记 unavailable。

## 决策

近期采用：

```text
PostgreSQL 权威任务状态 + lease/fencing
                 ↓
LISTEN/NOTIFY 快速唤醒 + 低频 polling 兜底
                 ↓
PostgreSQL 持久事件/outbox + 各实例本地 WS 推送
```

暂不引入 Redis/BullMQ。只有当任务启动延迟、数据库争用、独立 worker 扩缩容或大量延迟任务等指标证明 PostgreSQL 路线成为瓶颈后，才演进为：

```text
PostgreSQL 权威状态/outbox
        + BullMQ 调度传输
        + Redis Streams 实时事件分发
```

即使引入 Redis，PostgreSQL 仍是业务状态和恢复的权威源。

## 任务执行语义

- HTTP 只有在 PostgreSQL task/operation 提交成功后才返回 accepted；
- 调度采用 at-least-once，不宣称 exactly-once；
- worker 使用 `FOR UPDATE SKIP LOCKED` 领取任务；
- 每次执行持有 `lease_owner`、`lease_expires_at` 和 fencing token；
- 续租、waiting、completed、failed 和事件提交必须校验 fence；
- lease 过期可以重新领取，旧 worker 的晚到写入必须失败；
- terminal 状态单向，不得被晚到 worker 覆盖；
- cancel 胜过晚到 complete，Provider 中止仍是 best-effort；
- waiting privacy/tool 状态不持有运行 lease，也不能被普通 worker 自动领取；
- 同一 session 按创建顺序执行，后续任务不得越过更早的非终态任务；
- 达到最大 attempt 后进入稳定失败状态，避免毒任务无限循环。

网络分区或 lease 误过期时，两个 Provider 调用可能短暂重叠。系统保证只有一个有效 fence 能提交权威结果，不保证第三方模型调用本身 exactly-once。

## 唤醒机制

- task 入库事务提交后发送只含 task id 的 `NOTIFY`；
- 每个实例使用专用数据库连接 `LISTEN`；
- 通知只负责降低启动延迟，不承担消息保存；
- LISTEN 断线、通知丢失或实例后启动时，由周期 polling 扫描可运行任务恢复；
- 通知失败不得丢任务，最多延迟执行。

PostgreSQL 官方将 `SKIP LOCKED` 明确列为 queue-like 多消费者场景的适用方式；`NOTIFY` 在事务提交后才对其他会话可见，并建议较大数据存表、通知只传键：

- <https://www.postgresql.org/docs/current/sql-select.html>
- <https://www.postgresql.org/docs/current/sql-notify.html>

## WS 事件模型

当前 PostgreSQL 持久事件与 outbox 语义：

- 状态变更和事件行在同一事务提交；
- 事件保存脱敏后的 wire payload、owner、channel、event id、position 和时间；
- `NOTIFY` 只发送事件行 id，实例收到后读取权威事件并推送给本机 socket；
- 每个实例保留数据库消费水位，LISTEN 重连后执行 catch-up；
- 客户端使用 channel position 从数据库重放；
- 超出保留窗口时返回 `recovery_required`，再通过 REST 权威对账。

WS 事件存储不是业务真相源；REST 和 PostgreSQL 业务表继续承担权威恢复。

## 为什么暂不使用 Redis/BullMQ

- PostgreSQL task 与 Redis job 之间存在双写，必须额外建设 transactional outbox；
- BullMQ 也是至少一次执行，worker lock 丢失后任务可能再次执行，仍然需要幂等和 fence；
- 普通 BullMQ 并发不是按 session 串行，仍需额外的 session lock 或分组能力；
- Redis Pub/Sub 不支持断线重放；WS 可靠恢复必须使用 Streams 或持久事件表；
- 当前规模没有证据证明新增 Redis HA、持久化、监控和双源对账的运维成本是必要的。

参考：

- <https://docs.bullmq.io/guide/workers/stalled-jobs>
- <https://docs.bullmq.io/guide/parallelism-and-concurrency>
- <https://redis.io/docs/latest/develop/pubsub/>
- <https://redis.io/docs/latest/develop/data-types/streams/>

## 引入 Redis/BullMQ 的触发条件

满足下列一项并经压测确认后再评审：

- enqueue-to-start p95 持续超过产品 SLO；
- task claim/polling 对 PostgreSQL 产生明显锁争用或 I/O 压力；
- worker 必须独立于 API 服务大规模扩缩容；
- 大量 delayed/repeatable jobs、优先级或强背压成为刚需。

迁移时采用 PostgreSQL task + queue outbox；relay 使用稳定 task id 投递 BullMQ，worker 执行前仍需向 PostgreSQL 领取有效 fence。Redis 状态不得覆盖 PostgreSQL 权威状态。

## 验收矩阵

当前产品按个人单实例使用，本节中的多实例与容量相关条目不纳入现阶段验收；仅在未来部署形态或负载目标发生变化时重新启用。

- worker 在模型调用前、流式输出中、结果落库前分别被终止；
- lease 过期后旧 worker 晚到；
- 多实例同时领取同一任务；
- 同一 session 存在多个 queued/waiting/running 任务；
- cancel 与 complete、cancel 与工具批准同时发生；
- LISTEN 连接中断、重连和通知丢失；
- WS 客户端连接到不同实例后按水位恢复；
- 毒任务达到最大 attempt 后稳定失败；
- 任何重放都不会重复提交 assistant message、终态事件或外部副作用。

## 需要观测的指标

- queue depth、enqueue-to-start、执行耗时；
- lease 过期/重领、attempt 分布、旧 fence 提交拒绝数；
- 取消延迟和取消后晚到提交数；
- WS 事件延迟、重放数量、recovery gap；
- LISTEN 断线和重连次数；
- polling 兜底发现的漏通知任务数。

## 回滚

LISTEN/NOTIFY 仅承担唤醒，可随时关闭并退回纯 polling；任务和事件的 PostgreSQL 权威数据不受影响。多实例出现异常时可以把 worker 并发收缩到单实例，lease/fencing 与状态约束继续生效。
