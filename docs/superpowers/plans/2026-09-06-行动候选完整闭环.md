# 行动候选完整闭环实施计划

> **执行要求：** 在当前未提交工作树上增量实施并统一收口，不回退聊天 Markdown、媒体、思考过程、滚动、账户或任务恢复改动。

**目标：** 打通“聊天行动意图 → 正式 Action Candidate/ConfirmationBatch → 用户查看、编辑并确认 → Action 查询与历史 → 生成整批撤销候选 → 再次确认生效”的首条业务纵切。

**架构：** PostgreSQL 继续作为分析、候选、确认和正式 Action 的唯一权威源。模型只能通过现有无副作用结构化输出提出内容；服务端重新校验并在 fenced 任务完成事务内创建 AnalysisRun、StructuredAnalysis、ConfirmationBatch 与 CandidateItem。所有正式写入继续只经过 `SubmitConfirmationBatch`，WS 仅发送安全资源引用，前端以 REST 做详情和恢复。

**技术栈：** TypeScript、NestJS、TypeORM/PostgreSQL、共享 contracts、Expo Router、React Native、Vitest/Jest。

**依据：** `docs/05-任务架构/2026-09-04-行动候选与确认中心首个业务纵切.md`

## 全局约束

- 只实现 `action` 首条纵切，不扩展 Goal、Fact、Memory、Decision、RAG 或提醒业务。
- 不把 `ChatPreviewV1.preview_id` 冒充正式 `candidate_id`；正式资源使用服务端生成并持久化的独立 ID。
- 所有读取按认证 owner 过滤，跨 owner 统一按资源不存在处理。
- 列表采用 `(created_at, id)` 降序 keyset cursor，禁止 offset 分页。
- 正式 Action 只能由 `SubmitConfirmationBatch` 生效；撤销命令只创建新候选批次。
- 高风险候选独立成批，确认时必须携带 `risk_acknowledged=true`。
- 前端确认成功后重新读取权威批次和 Action，不乐观声明正式对象已创建。
- 任何新增迁移必须提供可逆 `down`，真实数据库测试只允许专用 test/verify 库。
