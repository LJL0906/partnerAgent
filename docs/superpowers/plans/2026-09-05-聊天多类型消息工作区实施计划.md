# 聊天多类型消息工作区实施计划

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** 将聊天升级为可维护、可恢复、可折叠且视觉统一的多类型 Agent 消息工作区；本阶段业务数据只做结构化预览与安全打印，不进行正式业务入库。

**Architecture:** 以共享 ChatItem/事件契约为数据边界，以后端已有 ChatTask、WS v1、隐私、工具控制和候选能力为事实来源；前端按消息类型拆分独立卡片组件和状态映射，REST/WS 使用同一恢复模型。通过 preview-only 业务输出适配层展示候选，不新增旁路业务写入。

**Tech Stack:** TypeScript、NestJS、TypeORM/PostgreSQL、Expo/React Native、Zustand、WS v1、Vitest/Jest。

**Spec:** `docs/05-任务架构/2026-09-05-聊天消息列表完整闭环追踪.md`、`docs/05-任务架构/2026-09-05-聊天业务生产闭环清单.md`

## Global Constraints

- 正文消息不折叠；思考、工具、候选、审批、运行状态和详情默认可折叠。
- 不把工具调用裸露成普通文本；不把 thinking_delta 默认当作原始推理正文展示。
- 工具审批与业务候选确认严格分开。
- 本阶段业务数据只做结构化预览与安全打印；不新增、不调用正式业务入库 API。
- 不修改已有确认事务行为，不以预览、测试或 UI 状态冒充正式生效或生产验收。
- 组件按职责拆分，避免继续扩大 ChatScreen、chat-event-state、chat-message-list；单文件尽量不超过 500 行。
- 数据链路必须有稳定 ID、状态、关联关系、去重、恢复和 owner/session/task/operation 隔离。
- 不覆盖工作区已有无关改动。

## 任务分配原则

- 先冻结 Task 1 共享契约；Task 2/3/4 按契约分配不重叠写集并集成，不能在共享文件上同时写入；Task 6 可独立并行；Task 5/7 需要真实可运行链路后验收。
- 同一文件只由一个 Agent 修改；主 Agent 负责整合、审查、测试和文档收尾。
- 每个任务交付必须列出新增、修改、删除文件和验证命令结果。
