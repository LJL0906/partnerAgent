# Agent 技术底座加固

> 状态：**已完成（保留已知边界）**  
> 启动日期：2026 年 9 月 4 日  
> 当前范围：只加固通用 Agent Runtime，不实现 Action、Goal、Memory、RAG 或其他业务能力。

## 1. 目标

把现有“可运行的单 Agent 聊天主链”提升为可恢复、可控、可观测、可横向演进的技术底座，关闭以下通用风险：

1. `queued/running` ChatTask 在进程退出后无法自动恢复；
2. 同一 session 缺少数据库级串行执行保证；
3. 正式 `/ws/v1` 尚未完整承载工具审批、拒绝和撤销控制；
4. 模型调用缺少统一超时、瞬态错误分类和安全重试边界；
5. 缺少 Agent 轮次、工具次数、耗时和资源预算；
6. 缺少任务、模型、工具和 WS 的统一可观测关联；
7. 调度与 WS 事件仍主要依赖单进程内存，尚无多实例基础；
8. CI、真实 PostgreSQL、迁移和生产启动检查尚未形成自动门槛。

## 2. 不做事项

- 不接通 `request_analysis`；
- 不实现 `propose_action_candidates`；
- 不新增 Action、Goal、Fact、Memory、Decision、Reminder 等业务工具；
- 不建设 RAG、embedding、向量数据库或 Python AI 服务；
- 不改动正式业务对象只能经确认事务写入的既有边界；
- 不因技术加固批量实现现有 501 路由。

## 3. 并行任务包

### T1：持久任务运行时

文件负责人：运行时 Agent。

- 为 ChatTask 增加 PostgreSQL 权威的认领与恢复语义；
- 服务启动后恢复可执行的 `queued/running` 任务；
- 同一 session 严格串行，不允许上下文分叉或快照覆盖；
- 明确 lease、超时回收、取消和终态竞争规则；
- 覆盖重启恢复、重复认领、同 session 并发和取消竞态测试。

### T2：正式协议与工具闭环

文件负责人：协议工具 Agent。

- 在 `/ws/v1` 接通工具批准、拒绝和撤销命令；
- 所有操作基于 JWT owner 和 PostgreSQL 权威资源鉴权；
- 工具状态通过正式事件发布，并保持安全载荷边界；
- 审批后的工具结果必须能够恢复原 Agent 推理链；
- 旧 Agent Gateway 只保留兼容，不再承载新能力。

### T3：模型网关可靠性

文件负责人：模型网关 Agent。

- 增加可配置调用超时；
- 识别可重试的瞬态调用失败，并限制次数与退避；
- 流式输出已经开始后不得透明重试，避免重复文本或副作用；
- 统一安全错误分类，不向客户端泄露 Provider 明文；
- 评估并实现不破坏隐私决定绑定的模型 fallback；无法安全实现时保留明确设计边界。

### T4：运行预算与可观测性

文件负责人：主 Agent。

- 配置整轮 deadline、最大模型轮次、最大工具调用次数和输出预算；
- 统一 `request_id / operation_id / task_id / session_id / tool_call_id` 关联；
- 记录模型耗时、首 token、结束原因、工具次数、重试、取消和失败分类；
- 日志和指标不得记录提示词、工具参数、模型正文或敏感明文。

### T5：多实例执行与事件分发

依赖：T1、T2、T4。

- 将进程内任务唤醒替换为可恢复的数据库通知/轮询或独立队列；
- 提供跨实例 lease、心跳、取消与优雅停机；
- 将 WS 事件水位和短期重放移出单进程内存；
- REST 始终保持权威恢复来源，事件系统不得成为业务真相源。

多实例路线已形成 Accepted ADR 并部分实现：近期采用 PostgreSQL lease + `LISTEN/NOTIFY` + polling 兜底；Redis/BullMQ 只在指标证明有必要后引入。详见 [`多实例任务执行与事件分发`](../03-技术草案/多实例任务执行与事件分发.md)。

### T6：工程与部署门槛

依赖：T1 至 T5 的接口稳定。

- 自动执行 build、unit、e2e、lint；
- 自动验证 PostgreSQL migration up/down/up；
- 增加启动配置校验、readiness、liveness 和优雅停机；
- 提供不含密钥的本地/生产容器运行配置；
- 记录确定性 Agent、真实 PostgreSQL 和受控真实 Provider 的分层验收结果。

## 4. 执行顺序

```text
第一批：T1 || T2 || T3
             ↓
整合验收：跨模块契约、全量测试、真实 PostgreSQL
             ↓
第二批：T4
             ↓
第三批：T5
             ↓
第四批：T6
```

T1、T2、T3 可以并行，但同一文件只能由一个负责人修改。共享契约变更由 T2 统一维护；数据库迁移由 T1 统一维护；主 Agent 负责冲突处理、全量验证和文档回写。

## 5. 第一批关闭条件

- 重启后可安全恢复未完成 ChatTask，且不会重复完成同一任务；
- 同一 session 并发提交不会造成 Agent 上下文分叉；
- `/ws/v1` 可以完成工具批准、拒绝、撤销及状态查询/恢复；
- 工具获批后能够把结果继续送入原 Agent 回合；
- 模型超时和瞬态错误得到稳定、可测试的错误映射；
- 已开始输出的流不会被透明重试；
- 根 `build/test/lint`、后端 e2e 和相关真实 PostgreSQL 专项通过；
- 文档准确区分“已完成”“部分完成”和“未实现”，不提前宣称生产级能力。

## 6. 风险纪律

- 任何恢复执行都必须具备原子认领，不能用启动时无条件遍历后直接执行；
- 同一 session 的串行约束必须能覆盖多实例，而不只是进程内 `Map`；
- 自动重试不得跨越已发生的外部副作用，也不得重复流式输出；
- Provider fallback 后载荷、Provider、模型或指纹变化时必须重新经过外发策略；
- 可观测数据必须遵循现有无明文审计原则；
- 新增 migration 必须提供可逆 `down` 并在真实 PostgreSQL 上验证。

## 7. 交付记录

T1 至 T6 已完成并集成：

- T1：ChatTask PostgreSQL 原子认领、lease/fencing、心跳、过期恢复、同 session 串行、取消与晚到写保护；
- T2：正式 `/ws/v1` 工具批准、拒绝、撤销、owner 鉴权、结果快照与重启续推；外部副作用崩溃后进入 `indeterminate`，不自动重放；
- T3：模型超时、首响应前有限重试、错误分类与安全元数据；流开始后不透明重试，Provider/model fallback 因外发决定绑定而不自动执行；
- T4：每轮 deadline、模型轮次、工具次数、请求/总输出 token 预算，以及无正文、无参数、无结果的关联遥测；
- T5：PostgreSQL task 通知 + polling 兜底，WS 持久事件、原子流位置、跨实例通知和游标重放；
- T6：启动配置校验、live/ready、draining、迁移验收脚本、两层 CI 和迁移先行的后端容器基线。

最终验证：根 build、unit、lint 通过；memory e2e 112/112；PostgreSQL 16 专用空库 10 条 migration 完整 up → down → up；真实 PostgreSQL 专项 7 个文件、17/17 通过。Compose `config --quiet` 通过；镜像实构建因 Docker Hub 构建前端层持续 0B 下载而终止，尚未进入项目编译阶段。真实第三方 Provider 冒烟也未执行。

已知边界：WS LISTEN 断线窗口仍依赖客户端携 `after event_id` 重连恢复，服务端尚无主动 catch-up；task 状态与 WS event 尚未形成同事务 outbox；外部副作用执行中崩溃只能人工核对；内存模式不提供跨进程恢复。这些边界不影响 PostgreSQL 业务状态作为唯一权威源。
