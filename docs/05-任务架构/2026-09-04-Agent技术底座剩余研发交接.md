# Agent 技术底座剩余研发交接

> 状态：**已完成**
> 日期：2026 年 9 月 5 日
> 范围：仅剩余后端技术研发；不包含业务功能、真实 Provider 验收、压测、服务器部署或生产运维。

## 0. 执行结果

R1-R7 已全部关闭：

- R1 以活跃 stream 显式注册、本机投递 position 水位、按 stream 串行队列和有界批次/并发实现 LISTEN 重连主动 catch-up；重复 notification、重连并发实时事件和保留窗缺口均有确定性测试；
- R2 为 ChatTask 全生命周期状态转换建立同事务 outbox，relay 使用稳定 event key、三 stream 幂等键、`FOR UPDATE SKIP LOCKED`、lease/fence 和最多 8 次尝试；工具确认/拒绝/撤销仍保留状态事务后单独 publish 的双写边界，不宣称全域 transactional outbox；
- R3 选择“核对 + 脱敏审计 + 人工补偿、不恢复原失败任务”的状态机决策，提供本机 `tool:reconcile` CLI，固定结论为 `verified_applied`、`verified_not_applied`、`abandoned`；
- R4 提供 typed noop/in-memory/composite sink、低基数 Prometheus registry/exporter，并覆盖 Agent、模型、工具、权威 queue depth、lease/fence 与 WS 可靠性指标；Provider retry 明确标记 unavailable；
- R5 将 WS 事件保留改为 count + age 受限配置和后台 `SKIP LOCKED` 分批清理，stream position 永不删除或归零；
- R6 显式贯通 Agent `run_id`，持久化 metadata-only Run/Turn/Tool/Model trace；查询 owner-scoped、最多 7 天、最多 100 条，单 run/owner/保留期均有限额，未开放 HTTP/WS；
- R7 将旧 Gateway 移出默认 `AgentModule`，只由开发兼容模块显式装载；生产配置拒绝启用，测试客户端已改用正式 `/ws/v1 + REST`。

统一验证：根 build、unit、lint 通过（contracts 12/12、backend 314/314、frontend 80/80）；memory e2e 112/112；PostgreSQL 16 独立空库 14 条 migration 全量 up → down → up；后端全量 e2e 14 个文件、129/129，其中真实 PostgreSQL 专项 7 个文件、17/17。临时验迁/e2e 数据库和角色已删除，业务库未修改。

仍属独立验收/部署阶段：真实 Provider、容器镜像实构建、双实例故障注入、容量压测、Prometheus 网络暴露与告警、备份恢复演练。毒 outbox 事件达到最大 attempt 后会稳定停留并阻塞同 session 后续生命周期通知，目前只有安全日志，后续需增加受保护的运维处置入口。

## 2. 统一边界

- 不实现 Action、Goal、Fact、Memory、Reminder、RAG、文件解析等业务能力；
- 不引入 Redis/BullMQ，除非另开 ADR 并由指标证明 PostgreSQL 路线已成为瓶颈；
- PostgreSQL 业务表始终是权威源，WS、NOTIFY、metrics 和 trace 都不能成为业务真相源；
- 当前 `ws_v1_events` 只是持久事件表，R2 完成前不得称为 transactional outbox；
- 调度语义保持 at-least-once + fence，不宣称 Provider 或外部副作用 exactly-once；
- 日志、metrics、trace、WS event 不得保存提示词、模型正文、工具参数、工具结果、令牌、数据库 URL 或原始异常；
- 单个生产源码文件原则上不超过 500 行；同一文件在同一批次只允许一个负责人修改；
- 不读取或提交 `.env`，不修改现有业务库，不擅自 commit、reset 或清理其他人的工作树。

## 3. 任务清单

### R1：WS LISTEN 重连主动 catch-up（P0）

目标：PostgreSQL LISTEN 断开又恢复时，仍连接在本实例上的 socket 不会静默漏掉断线窗口中的事件。

建议文件范围：

- `src/ws-v1/ws-v1-event.store.ts`
- `src/ws-v1/typeorm-ws-v1-event.store.ts`
- `src/ws-v1/ws-v1.service.ts`
- 对应单元测试；必要时新增独立 catch-up 协调器，避免继续扩大现有文件。

实现约束：

- 为每个活跃 `stream_key` 维护最后已投递的 `stream_position`，不能使用无序 UUID 比较先后；
- durable/in-memory 水位只能在本机 socket 投递流程完成后推进；必须覆盖本实例 append 已提交、但本地 deliver 前失败的同源事件，不能因 `publisher_instance_id` 去回声而永久跳过；
- LISTEN 恢复后按活跃 stream 批量查询缺口，按 position 升序投递并按 `event_id` 去重；
- catch-up 与实时 notification 并发时不得乱序或重复；
- 缺口早于保留窗口时向对应 socket 发送一次 `recovery_required`，不得伪造完整恢复；
- 无活跃订阅时不得全表扫描；单次批量和并发数必须有上限。
- 活跃 stream 必须由 `WsV1Service` 的订阅表显式提供，event store 不得猜测或扫描全库发现订阅。

完成条件：断线期间写入多条事件、重连同时再写实时事件、重复 notification、保留窗口缺口四类确定性测试通过。

### R2：ChatTask 生命周期 transactional outbox（P0）

目标：ChatTask 权威状态提交成功时，相应的生命周期通知不会因进程在提交后崩溃而永久丢失。

建议文件范围：

- `src/database/entities/` 新增 runtime outbox entity；
- `src/database/migrations/` 新增下一序号可逆 migration；
- `src/database/database-definition.ts`
- `src/local-core-api/typeorm-chat-task.store.ts`
- `src/local-core-api/typeorm-chat-task-runtime.ts`
- `src/local-core-api/chat-task-runner.ts`
- `src/local-core-api/privacy-decision.service.ts`
- 任务 cancel/application 的全部状态转换入口
- 新增独立 outbox relay；完成存储层后再由单一负责人接入 `ws-v1`。

实现约束：

- `queued/running/waiting/completed/failed/cancelled` 状态更新与 outbox 行必须在同一数据库事务；
- outbox 使用稳定 event key、幂等 relay、`FOR UPDATE SKIP LOCKED`、lease/fence 和有限重试；
- relay 只在事务提交后转换为脱敏 WS wire event；每个目标 stream 使用稳定幂等键，重复 relay 或 fan-out 部分成功后崩溃都不得产生重复终态语义；
- 文本增量等非权威流事件不强行纳入业务事务；断流后仍以 Task/Session REST 对账；
- 不把现有 `ws_v1_events` 直接升级为 ChatTask 权威状态表。
- 第二阶段必须审计工具确认、拒绝、撤销的“状态提交后单独 publish”路径；要么纳入同一 outbox，要么在最终文档明确保留双写边界，不能只关闭 ChatTask 路径后宣称 transactional outbox 已全面完成。

完成条件：故障注入覆盖“状态提交后 relay 前崩溃”“relay 发布后确认前崩溃”“双 relay 并发”和“毒事件达到最大 attempt”。

### R3：`indeterminate` 工具操作人工核对入口（P0）

目标：外部副作用执行中崩溃后，运维人员能安全查看待核对记录，并明确标记“外部已成功”或“外部未发生”，完成审计和人工补偿。

建议文件范围：

- `src/tools/tool-operation.store.ts`
- `src/tools/typeorm-tool-operation.store.ts`
- `src/tools/confirmation-center.service.ts`
- 新增独立 operator CLI 或受保护的内部模块及对应测试。

实现约束：

- 在正式管理员鉴权模型落地前，优先使用本机 CLI，不开放匿名 HTTP/WS 接口；
- 必须要求 confirmation id、当前版本/状态、显式确认短语和处理结论；
- 通用核对结论限制为 `verified_applied`、`verified_not_applied`、`abandoned` 等固定枚举，不能允许操作者提交任意 JSON 伪造工具结果；
- 状态转换必须原子、幂等并写脱敏审计；普通 owner 或旧客户端不能调用；
- 不自动再次执行外部工具，不根据超时猜测副作用是否发生；
- 当前 scheduler 会把 `indeterminate` 对应 ChatTask 置为终态 `failed`，禁止直接执行 `failed → queued`；实现前必须二选一并形成状态机决策：新增 `waiting_tool_reconciliation` 状态、migration、契约和恢复规则，或者把 CLI 限定为“核对 + 审计 + 人工补偿”、明确不恢复原任务；
- 只有采用新的非终态 reconciliation 状态且具备可验证安全结果快照时，才允许恢复 Agent。

完成条件：并发核对、重复提交、错误状态、跨 owner、缺少结果快照及审计失败全部 fail-closed。

### R4：正式 metrics sink（P1，可与 R1/R2 并行）

目标：将现有 metadata-only telemetry 抽象为 typed sink，并接入单一 Prometheus exporter，而不是只写结构化日志；本轮不同时铺设 OTLP exporter。

建议文件范围：

- `src/agent/agent-runtime-telemetry.ts`
- `src/model-gateway/model-gateway-reliability.ts`
- `src/local-core-api/chat-task-scheduler.ts`
- 新增 `src/observability/` 模块与测试。

最小指标：run 总数/结束原因、模型请求耗时/首 token/错误分类、工具调用耗时/状态、queue depth、claim/lease expiry/fence reject、LISTEN reconnect、WS replay/catch-up/recovery_required。Provider retry 次数只有在 pi-ai 适配器暴露可靠 attempt hook 后才能记录；在此之前标记 unavailable，禁止从最终异常反推或伪造次数。

实现约束：metrics label 只允许低基数枚举；严禁使用 owner/session/task/operation/tool-call id、模型正文或原始错误作为 label。指标出口失败不能改变 Agent 执行结果。

完成条件：有 noop/in-memory 测试 sink 和 Prometheus registry/exporter，覆盖计数、耗时、低基数约束和 sink 故障隔离；生产网络暴露、抓取和告警配置留给部署任务。

### R5：WS 事件保留与清理策略（P1，R1 后执行）

目标：把当前硬编码“每流 100 条”变成受限配置，并避免长期遗留空 stream 元数据。

建议文件范围：

- `src/config/runtime-config.ts`
- `src/ws-v1/typeorm-ws-v1-event.store.ts`
- 新增独立 retention worker；必要时新增 migration/index。

实现约束：同时支持 count 上限与 age 上限；从 append 热路径移出同步范围清理，改为分批后台删除并限制锁时间；游标被清理后统一返回 `recovery_required`。`ws_v1_event_streams` 是单调序号水位，不得随事件清理而删除或归零；除非未来另建可靠的全局订阅注册和 tombstone 迁移方案。

完成条件：配置上下界、批量清理、并发 append、游标过期和清理后 stream position 继续单调测试通过。

### R6：Agent Run/Turn/Tool 元数据 trace（P1，可并行）

目标：形成可查询的运行元数据链，定位一次任务在哪个模型轮次、工具步骤或预算边界结束。

建议文件范围：

- `src/agent/agent-runtime-telemetry.ts`
- 新增 `src/observability/agent-run-trace*`
- `src/database/entities/`、`src/database/migrations/` 和数据库注册表。

实现约束：先把 Agent `run_id` 显式传入 `ModelGatewayObservation`，不能用现有模型 request id 冒充；只保存 run id、关联 id、枚举状态、provider/model id、耗时、token 数、预算、可可靠取得的重试次数和安全错误码；不保存 prompt/output/tool args/result/raw error。写入失败不得阻断主任务，必须有容量和保留上限。查询必须 owner-scoped、分页并限制时间范围，不能提供跨用户全表读取。

完成条件：一次普通回复、一次工具两轮、一次取消、一次预算终止和一次工具审批等待均形成连续 trace；敏感载荷负向测试通过。

### R7：旧 Agent WebSocket 物理隔离（P2，最后执行）

目标：优先删除旧 `chat/cancel/resume_session` 运行时；若仍有明确兼容需求，则不再随正式服务默认装载，只在独立开发入口中注册。

建议文件范围：

- `src/agent/agent.gateway.ts`
- `src/agent/agent.module.ts`
- `src/app.module.ts`
- `src/config/runtime-config.ts` 及测试
- `packages/contracts/src/events.ts` 及测试
- `test/agent-auth.e2e-spec.ts` 与 `test-client.html`
- 新增兼容模块及对应测试。

实现约束：正式 `/ws/v1` 与 REST 不得依赖旧 gateway；生产环境必须在配置校验阶段拒绝 `ENABLE_LEGACY_AGENT_WS=true`，不能只在连接时断开；开发显式启用时仍保留 JWT/CORS/owner 校验和安全错误映射。完成后更新测试客户端和交接文档，不能直接删除仍有测试依赖的能力。

完成条件：默认模块图不存在旧 gateway，生产环境拒绝启用，开发兼容模式测试仍通过，正式协议全量回归不变。

## 4. 推荐并行顺序与文件所有权

```text
第一批：事件 owner 先冻结 R1/R5/R2 共用 schema 与游标语义
        R1（事件 owner） || R4（Observability owner） || R3（Tool owner）
                         ↓
第二批：R5 → R2（同一事件 owner 串行） || R6（依赖 R4）
                         ↓
第三批：R7（最后执行，避开 app/config/module 冲突）
                         ↓
统一收口：契约、migration 注册、文档和全量回归
```

共享文件规则：

- R1、R5、R2 属于同一个事件可靠性文件域，由同一 owner 串行完成；`database-definition.ts` 与 migration 序号也由该 owner 统一合并；
- `ws-v1.service.ts`、`typeorm-ws-v1-event.store.ts` 在同一时间只归一个 owner；
- `agent-runtime-telemetry.ts` 先由 R4 owner 完成接口抽象，R6 只能基于该接口新增 sink；
- `app.module.ts` 只在最终集成阶段由主负责人修改；
- Contracts 若确需变更，由单一 contract owner 合并，其他负责人不得并发编辑。
