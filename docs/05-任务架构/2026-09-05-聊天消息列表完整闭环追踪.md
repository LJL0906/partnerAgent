## 2. 目标与不变量

### 2.1 总目标

将聊天消息列表从“按 role 显示纯文本/状态徽章”逐步完善为可以承载自然对话、思考状态、工具执行、结构化提案和人工确认的统一工作区，并最终形成可恢复、可追踪、可确认、可生效的闭环。

### 2.2 必须保持的不变量

- 普通聊天回复不会自动写入目标、行动、事实、长期记忆、决策或提醒；
- 模型提出的候选不等于正式业务对象；
- 正式对象只能经过用户确认和服务端确认事务后生效；
- 工具审批是工具执行授权，不等同于业务候选确认；
- 所有候选、确认、工具控制和消息恢复都必须按 owner/session/task/operation 做边界校验；
- 消息列表不能因流式增长把正在阅读历史的用户强行拉回底部；
- 断线、重启、切换会话后的恢复不能重复消息或串会话；
- 敏感内容展示和外发继续遵守现有隐私策略，不在 UI 中泄露 API Key、密码等秘密；
- UI 状态不能冒充数据库已生效状态，必须区分建议、待确认、已确认和已生效。

## 5. 后端接口与事件依据

### 5.1 当前 REST 相关接口

- `GET /api/v1/chat-sessions`：会话列表；
- `GET /api/v1/chat-sessions/:sessionId`：会话详情与持久化消息恢复；
- `POST /api/v1/inputs/text`：提交文本消息；
- `POST /api/v1/tasks/cancel`：取消聊天任务；
- `POST /api/v1/privacy-decisions/submit`：提交隐私决定；
- `POST /api/v1/messages/set-model-selection`：设置当前消息模型选择；
- `GET /api/v1/model-configs`：读取 `pi-ai` 模型目录映射后的模型能力。

候选和确认相关 REST 路由需继续以现有 Controller、共享契约和 P0 基线核对，不在本阶段自行发明绕过确认事务的写接口。

### 5.2 当前 WS v1 事件

当前前端主要处理：

- `candidate/reminder/summary` → 目前交给应用级事件路由，尚未成为聊天列表卡片。

## 7. 两条必须分开的审批链路

### 7.1 工具审批链路

```text
模型请求工具
  ↓
tool_confirmation_pending
  ↓
用户允许 / 拒绝
  ↓
tool_confirmation_confirmed / dismissed
  ↓
工具执行
  ↓
成功 / 失败
  ↓
可撤销 / 已撤销（如适用）
```

工具审批解决“是否允许执行工具副作用”。

### 7.2 候选确认链路

```text
模型生成候选
  ↓
candidate
  ↓
展示候选、来源、风险和当前状态
  ↓
用户确认 / 修改后确认 / 拒绝 / 稍后处理
  ↓
SubmitConfirmationBatch
  ↓
服务端事务校验与写入
  ↓
正式对象生效
```

候选确认解决“是否接受模型提出的业务内容并使其生效”。

两条链路不能合并为一个通用“批准”按钮，也不能让前端直接创建正式业务对象。

## 8. 目标状态模型

### 8.1 普通消息

```text
pending → streaming → completed
                    ├→ failed
                    └→ cancelled
```

### 8.2 思考内容

```text
idle → streaming → completed
                 └→ hidden / unavailable
```

思考状态和思考正文分开建模；是否展示原始推理正文需要结合模型能力、供应商协议和产品安全策略确认，不能因收到 `thinking_delta` 就默认全部展示。

### 8.3 工具调用

```text
requested
  → waiting_confirmation
  → confirmed
  → running
  → completed
  ├→ failed
  └→ cancelled
completed → undo_available → undone / expired
```

### 8.4 候选与人工确认

```text
candidate_generated
  → pending_confirmation
  → accepted
  → applied

pending_confirmation
  ├→ rejected
  ├→ later
  ├→ expired
  └→ conflicted
```

其中：

- `accepted` 表示用户决定接受；
- `applied` 表示服务端确认事务已使正式对象生效；
- `conflicted` 表示版本/所有权/状态校验不通过；
- `later` 不等于拒绝，也不等于已生效。
