# 行动候选与确认中心首个业务纵切

> 类型：一次性任务架构与交付说明  
> 状态：进行中（阶段 0 与 P1-01 已完成，下一步实施 P1-02「Action 候选生产链」）
> 制定日期：2026-09-04  
> 范围：聊天可靠性加固、隐私外发闭环、Action 候选生成、确认中心、正式 Action 查询与撤销  
> 前置任务：[核心契约收口与首条业务闭环](./2026-09-04-核心契约收口与首条业务闭环.md)

## 1. 架构结论

下一阶段只交付一条可被用户感知的核心业务纵切：

```text
自然语言输入
→ 结构化分析
→ Action 候选与确认批次
→ 用户查看、编辑和确认
→ SubmitConfirmationBatch 原子创建正式 Action
→ 执行页读取
→ 来源、版本和变更历史可追溯
→ 用户可生成撤销候选并再次确认
```

开始该纵切前必须先通过“阶段 0：可靠性加固门槛”。阶段 0 未通过时，不得扩展候选生产、确认中心 UI 或正式对象能力。

本阶段不以“批量消灭 501 handler”为目标。只实现上述纵切实际依赖的接口，避免先做出一组没有候选来源、只能返回空数据的页面和查询。

## 2. 业务位置

当前系统已经具备以下基础：

- 正式 v1 REST/WS 契约和 JWT owner 边界；
- 文字输入、ChatTask、Pi、消息持久化和 REST 会话恢复主链路；
- Candidate、ConfirmationBatch 和正式对象的数据库基础；
- `SubmitConfirmationBatch` 的批次、候选、目标三层版本校验和原子事务；
- Model Gateway 外发策略边界和无明文审计表结构；
- Expo 正式 v1 网络适配层。

但产品当前仍主要是“可持久化聊天”，尚未形成“用户表达行动意图后，系统帮助其建立并管理行动”的业务价值闭环。确认事务只能消费预先存在的候选，系统尚无正式的 Action 候选生产链、确认中心页面和执行页。

因此本阶段优先完成 Action，不同时铺开 Goal、Fact、Memory、Decision、RAG、提醒和摘要。

## 3. 目标与非目标

### 3.1 必须完成

1. 修复 WS 首次订阅丢终态事件的竞态。
2. 实现隐私外发决定的提交、恢复、取消和超时。
3. 将外发审计提升为 Provider 调用前的强制持久化门槛。
4. 对结构化上下文执行递归敏感信息扫描。
5. 明确处理 `request_analysis`，禁止静默忽略。
6. 将统一 token provider 接到可运行的登录或开发鉴权入口。
7. 从文字输入生成经过服务端校验的 Action Candidate/Batch。
8. 实现确认批次、候选详情、确认历史、Action 列表/详情/来源/历史查询。
9. 实现 Expo 确认中心和执行页的最小可用流程。
10. 实现整批撤销资格查询、撤销候选生成和再次确认。

### 3.2 本阶段不做

- Goal、Fact、Memory、Decision、Situation、Reminder 的完整纵切；
- Python AI/RAG 服务、pgvector 检索和 embedding 消费；
- Redis、BullMQ、Kafka 或微服务拆分；
- 语音、OCR、网页抓取和文件深度解析；
- 自动执行外部系统副作用；
- 完整模型配置中心和商业化账户体系；
- 上下文摘要、日报、周报和数据导出；
- 为所有已登记的 501 路由提供占位实现。

## 4. 不可破坏的架构边界

- PostgreSQL 是任务、分析、候选、确认和正式对象的唯一权威源。
- Pi/模型只能提出结构化候选，不得创建或修改正式 Action。
- 正式 Action 只能由 `SubmitConfirmationBatch` 生效。
- 服务端从持久化候选派生 owner、kind、action、risk、editable_fields、来源、版本和过期时间，不信任模型或客户端声明。
- 隐私外发决定、工具执行审批和业务候选确认是三种独立事务。
- REST 提供权威详情与恢复；WS 只推送增量事件或资源引用。
- 任何写能力都必须同时具备授权、幂等、审计、版本冲突和撤销设计。
- 不修改或复制根目录可选的 `pi/` 参考源码。

## 5. 阶段 0：可靠性加固门槛

### 5.1 WS 首次订阅与 REST 对账

> 实施状态：**已完成**。首次订阅采用 `user:self → REST 创建资源 → 动态频道 ACK → REST 对账`，订阅前完成、断线期间完成和水位过期均由权威持久化状态恢复。

原问题是 Expo 在 REST 受理后才获得 task/operation ID，并重新连接相应频道；首次订阅没有水位时，服务端不会回放已产生事件。快速 Agent 可能在订阅前完成，使客户端停留在运行状态。

统一策略：

1. 新会话在 REST 创建前只稳定订阅 `user:self`；已有权威归属的当前 session 才加入稳定频道，不能预订阅尚未入库的 session；
2. REST 返回 task/operation ID 后追加订阅对应频道；
3. 收到 `subscription_ack` 后立即并行读取 `GetTaskStatus` 和 `GetChatSession` 做权威对账；
4. WS 事件与 REST 对账结果按任务状态机合并，终态不可被旧事件回退；
5. 已有水位继续使用 `after` 重放；水位不存在不解释为“已经同步”；
6. `recovery_required` 继续触发 REST 恢复。

不采用“首次订阅自动回放整个内存窗口”的隐式语义，避免新客户端意外消费无关历史。正确性由持久化状态和显式 REST 对账保证。

### 5.2 隐私外发等待闭环

> 实施状态：**已完成**。`SubmitPrivacyDecision` 的 allow/redact/block/timeout、载荷绑定和 PostgreSQL 重启恢复闭环均已接通。

实现 `SubmitPrivacyDecision`，并持久化一个与具体外发载荷绑定的等待记录。最少包含：

- `egress_id`、owner、task、request fingerprint；
- Provider、模型和来源；
- 命中类别，不保存命中明文；
- 原载荷安全引用或可重建引用；
- 当前状态、决定、创建/过期/处理时间和版本。

决定语义：

- `allow`：仅放行当前指纹对应载荷；
- `redact`：重新执行脱敏和扫描后才能放行；
- `block`：任务进入明确终态，不调用 Provider；
- 超时：按 block 处理，不自动重试；
- 载荷、模型或上下文改变：旧决定失效，重新扫描并重新决定。

服务重启后必须能够读取等待记录并继续或终止原 ChatTask，不能依赖进程内闭包保存恢复逻辑。

### 5.3 外发审计 fail-closed

> 实施状态：**已完成**。`EgressAuditStore.record()` 已改为可等待持久化门槛，审计失败时 Provider 零调用并安全映射为 `EGRESS_001`。

将 `EgressAuditStore.record` 改为可等待的持久化操作。调用顺序固定为：

```text
完整载荷构造
→ 策略扫描与决策
→ 无明文审计成功落库
→ 生成 ApprovedEgressRequest
→ Provider Adapter
```

审计写入失败时不得调用 Provider，并把任务置为可查询的失败状态。不得使用未被调用链等待的 Promise 队列宣称“强制审计”。

### 5.4 结构化敏感信息扫描

> 实施状态：**已完成**。已实现对象/数组/字段名/字段值/自然语言的递归扫描、递归脱敏和脱敏后完整复扫，并对循环、深度、节点数、字符串长度与不安全类型 fail-closed。

扫描器必须递归遍历对象、数组和消息内容，同时执行：

- 敏感字段名识别：password、secret、token、api_key、authorization 等；
- 值格式识别：JWT、Bearer、常见 API Key、身份证件、银行卡等；
- 自然语言模式识别；
- Unicode、空白、大小写和常见分隔符归一化；
- 循环引用、超深对象和超大载荷的安全上限处理。

脱敏后必须再次扫描。扫描异常、深度超限或无法序列化时一律 fail-closed。

### 5.5 分析参数与 token 接线

> 实施状态：**已完成**。`request_analysis=true` 且分析类型合法时同步返回稳定 `NOT_IMPLEMENTED_001`；非法字段组合返回 `VALIDATION_001`，两者都不创建聊天业务数据或调用 Provider。HTTP 与 WS 已共用安全 token provider，Native 使用 SecureStore，Web 仅内存保存，并已完成 Expo 设备鉴权联调。

- 阶段 0 完成前，`request_analysis=true` 必须显式返回稳定错误，不得静默当作普通聊天。
- 阶段 1 接通后，它才返回分析任务引用并进入候选生产链。
- HTTP 与 WS 继续共享 `access-token.ts`；由登录层或明确的开发鉴权入口注册 provider。
- token 不得写入 `EXPO_PUBLIC_*`、URL、日志或持久化明文。

### 5.6 阶段 0 验收

1. 零延迟确定性 Agent 连续运行时，客户端均能得到任务终态和最终消息。
2. 订阅前完成、断线期间完成、水位过期三种情况均可通过 REST 恢复。
3. 隐私决定 allow/redact/block/timeout 及数据库重启恢复通过。
4. 审计表不可写时 Provider 调用次数为 0。
5. 嵌套 JSON、数组、自然语言和常见凭证格式不会绕过扫描。
6. 分析参数不会被静默忽略。
7. Expo 真机或模拟器能通过统一 token provider 完成 HTTP/WS 鉴权。

## 6. 阶段 1：Action 候选生产

> P1-01 实施状态：**已完成**。权威 `ANALYSIS_TYPES` 已包含 `action`；Action DTO、`AnalysisTaskRef` 和 WS `candidate` 安全资源引用已冻结；`local-core.ts` 已按稳定导出边界拆至 463 行，并新增 `local-core-analysis.ts`、`local-core-model.ts`、`local-core-queries.ts`。后端已新增 `analysis_runs`、`structured_analyses` 实体与第 8 条 migration。真实 PostgreSQL 16 已对新增第 8 条 migration 单独完成 up → down → up，P1-01 约束专项 5/5 通过，最终 8/8 已应用。
>
> P1-01 只交付契约与数据基础。Action 候选生产链、`GetAnalysisRun` handler 和前端候选卡/确认中心/执行页均未完成，下一步由 P1-02 继续实现候选生产链。

### 6.1 输入触发

普通陪伴聊天不强制分析。以下情况进入 Action 分析：

- 用户显式请求创建、安排、记录或跟踪行动；
- 客户端以 `request_analysis=true` 请求分析，且 `analysis_types` 包含已进入权威 Contracts 的 `action`；
- 服务端意图路由器高置信识别为行动协助。

意图不明确时只回复并建议用户触发分析，不擅自创建候选。

### 6.2 Pi 结构化工具

在 Pi 工具注册表增加只产生提案的结构化工具，例如：

```text
propose_action_candidates
```

使用 TypeBox 定义严格输入 Schema。至少表达：

- 标题与可选描述；
- 执行状态初值；
- 可选计划时间、截止时间和时区；
- 可选优先级；
- 模型置信度和不确定性说明；
- 对应原始文本片段或来源引用。

禁止从普通回复文本中截取或修复 JSON。工具返回值只代表模型提案，服务端还必须执行 Schema、业务、来源、时间和安全校验。

### 6.3 分析持久化

增加最小化 `analysis_runs` 和 `structured_analyses`，并与 owner、OriginalRecord、ChatTask 建立复合所有权约束。

一次成功分析在数据库事务中：

1. 完成 AnalysisRun；
2. 保存 StructuredAnalysis 原始结构化结果的受控版本；
3. 创建 ConfirmationBatch；
4. 创建一个或多个 Action CandidateItem；
5. 建立来源关系；
6. 提交后发布只含资源引用的 candidate 事件。

候选内容、批次和分析结果不得临时塞进 ChatTask 任意 JSON 字段替代正式模型。

部分候选校验失败时，不得创建无来源或不完整候选；允许把分析运行标记为部分成功并保存安全的错误摘要。

## 7. 阶段 2：确认中心与正式 Action

### 7.1 后端查询范围

只接通本纵切依赖的 Query：

- `ListPendingConfirmationBatches`；
- `GetConfirmationBatch`；
- `GetCandidateDetail`；
- `GetConfirmationHistory`；
- `ListActions`；
- `GetAction`；
- `GetChangeHistory`；
- `GetUndoEligibility`。

列表统一采用 `(created_at, id)` 的稳定 keyset cursor。所有资源按 JWT owner 过滤，跨用户访问按不存在处理。

### 7.2 确认与正式写入

继续复用现有 `SubmitConfirmationBatch`，不新建第二条正式对象写入路径。确认事务必须同时写入：

- 正式 Action；
- ObjectVersion；
- SourceRelation；
- ChangeHistory/ConfirmationAction；
- IndexUpdateJob。

`IndexUpdateJob` 本阶段只做事务内登记，不启动 embedding 或向量索引消费者。

客户端确认后不做正式状态的乐观成功展示；必须重新读取批次和 Action 权威状态。

### 7.3 撤销闭环

当前只有撤销资格查询，不足以完成产品闭环。新增“生成整批撤销候选”的 Command：

```text
POST /api/v1/object-change-candidates/undo
```

该路由只生成候选，不直接撤销。实现前先把 `CreateUndoObjectCandidatePayload`、路由和整批语义同步到 P0 决策、contracts 与路由基线。

规则：

- 以原 `confirmation_action_id` 和 `confirmation_batch_id` 确定整批范围；
- 校验所有对象当前版本、后续不兼容变更和可逆性；
- 任一对象不可逆时，整批不可撤销并返回具体阻塞原因；
- 可撤销时生成新的 ConfirmationBatch/CandidateItem；
- 用户再次调用 `SubmitConfirmationBatch` 后才执行逆向变更；
- 撤销本身产生新版本和变更历史，不删除旧历史。

### 7.4 WS 事件

Candidate 事件只包含：

- batch/candidate/analysis/task 引用；
- 安全摘要；
- 数量、风险级别和发生时间。

不得通过 WS 发送完整候选载荷、原始敏感输入或数据库内部结构。客户端收到事件后通过 REST 获取详情。

## 8. Expo 最小产品范围

### 8.1 聊天入口

- 在相关助手回复下展示 Action 候选卡片；
- 展示候选数量、标题摘要、风险和过期时间；
- 点击进入确认详情；
- 实时事件丢失时，REST 对账后仍能显示候选入口。

### 8.2 确认中心

- 待确认批次列表；
- 批次详情和来源；
- 逐项确认、修改后确认、取消、暂不处理；
- 可编辑字段由服务端返回的 Schema/字段清单控制；
- 版本冲突后刷新详情，不覆盖较新数据；
- 高风险批次独立展示额外确认，不提供混合“全部确认”。

### 8.3 执行页

- Action 列表与详情；
- 展示执行、计划、时效三维状态，不合并为一个模糊状态；
- 展示创建来源、确认记录和变更历史；
- 展示撤销资格，允许生成撤销候选并回到确认中心。

本阶段不实现复杂日历、拖拽排序、自动提醒和外部系统执行。

## 10. 统一验收场景

核心场景：

```text
用户输入：“明天下午三点提醒我提交季度报告。”
→ 系统保存原始记录并正常回复
→ 结构化分析提出 Action 候选
→ 聊天出现候选卡，确认中心可读取详情与来源
→ 用户把标题修改为“提交 Q3 季度报告”并确认
→ 正式 Action 出现在执行页，时间与时区正确
→ 来源可回到原始消息，历史可看到候选、修改与确认
→ 用户请求撤销，系统返回资格并生成整批撤销候选
→ 用户再次确认后，Action 以新版本进入被撤销后的状态
```

还必须覆盖：

1. 一条输入拆出多个 Action 候选；
2. 普通闲聊不产生候选；
3. 候选过期、候选版本冲突、目标版本冲突；
4. 重复 operation/input 不重复创建分析、候选或 Action；
5. 跨用户读取、订阅、确认和撤销全部失败且不泄露存在性；
6. 高风险批次不能与普通候选混批；
7. Provider、WS、错误和审计均不出现敏感明文；
8. 服务和数据库重启后，等待隐私决定、候选和正式 Action 均可恢复；
9. 真实供应商至少完成一次受控设备联调，但自动回归继续使用确定性 Agent；
10. 根 build/test/lint、后端 e2e 和真实 PostgreSQL 专项全部通过。
