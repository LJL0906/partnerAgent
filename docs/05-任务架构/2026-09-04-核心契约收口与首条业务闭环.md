## 2. 目标和非目标

本次交付一条最小但真实的纵向闭环：

    JWT 认证
    → POST /api/v1/inputs/text
    → 原子登记输入、消息和聊天任务
    → 经外发策略的 Pi Agent / Model Provider 调用
    → /ws/v1 订阅 task/operation/session 事件
    → 最终消息和任务状态持久化
    → 断线重放或 REST 查询补偿

同时完成确认契约迁移、真实 PostgreSQL 验证和 Expo 正式协议切换。

本次不实现 Python AI/RAG、多模态、完整正式对象页面、提醒/摘要/复盘/导出，也不引入微服务拆分、事件溯源或 CRDT。

## 3. 架构不变量

- PostgreSQL 是会话、消息、任务、候选、确认和正式对象的唯一权威源。
- memory store 仅供单元测试和显式本地调试；本次验收必须使用 PostgreSQL。
- REST 承载 Command/Query、幂等、版本和最终状态查询；WS v1 只承载订阅控制和主动推送。
- HTTP/WS 只信任带 exp 的 HS256 JWT sub，不信任 body/query 中的用户标识。
- session_id、task_id、operation_id 均持久化 owner_id；跨用户访问按不存在处理。
- 正式业务对象唯一写入路径是 SubmitConfirmationBatch。
- Tool Approval、隐私外发决定和 Confirmation Batch 是三种不同事务。

## 4. 确认命令收口

通用 CommandEnvelope 保留现有幂等字段。确认 payload 使用：

    interface SubmitConfirmationBatchPayload {
      confirmation_batch_id: string;
      batch_version: string;
      items: Array<{
        candidate_id: string;
        candidate_version: string;
        decision: 'confirm' | 'modify_confirm' | 'cancel';
        modified_payload?: Record<string, unknown>;
        target_object_id?: string;
        expected_target_version?: string;
        risk_acknowledged?: boolean;
      }>;
    }

规则：

- 服务端从候选读取 kind、业务动作、风险和目标范围，不信任客户端声明；
- 普通候选允许逐项不同决策，未提交项保持原状态；
- 任一项失败时本次提交整体回滚；
- 高风险候选必须单独成批，生效时 risk_acknowledged=true；
- modify_confirm 只允许修改候选 Schema 声明的字段；
- 更新对象时同时校验候选版本和目标版本；
- 同 operation_id + 同指纹返回首次结果，同 ID + 不同指纹返回 IDEMPOTENCY_001。

当前统一 mode 在正式客户端依赖前直接替换，不引入长期兼容层。

## 5. 敏感信息外发强制点

唯一合法调用链：

    Business Task / Agent
    → ExternalRequestBuilder 组装完整载荷
    → EgressPolicyGateway 识别与决策
    → ApprovedEgressRequest
    → ModelProviderAdapter

Provider Adapter 只接收 ApprovedEgressRequest，不公开原始上下文入口。Pi、后台任务、重试和未来 Python 调用均不得旁路。

v1 强制识别身份证件、银行卡、密码、API Key 和其他密钥。策略结果只能是：

- allowed：允许发送；
- redacted：只允许处理后载荷外发；
- pending_user_decision：持久化等待状态，不调用 Provider；
- blocked：终止外发，不自动降级。

默认方向为本地自动脱敏后发送，但用户禁止配置优先。每次重试、模型切换或载荷改变都重新执行策略；策略异常时 fail-closed。

审计只记录请求/任务标识、来源、命中类别、策略结果、供应商和时间，不记录命中明文、完整载荷或凭证。

## 6. 首条聊天闭环

### 6.1 HTTP 受理

POST /api/v1/inputs/text 必须在一个数据库事务中：

1. 校验 CommandEnvelope 和 JWT；
2. 按 owner_id + operation_id 检查命令幂等；
3. 创建或校验用户所属会话；
4. 按 owner_id + input_id 建立输入级幂等；
5. 持久化用户消息和原始记录；
6. 创建关联 owner/session/operation/input 的聊天任务；
7. 返回 accepted 及 session/message/record/task 引用。

事务提交后才调度 Agent。调度失败只更新任务状态，不删除已提交的原始输入。

任务状态至少包括：

    queued → running → completed
                     ├→ failed
                     └→ cancelled

提醒型外发策略可进入 waiting_privacy_decision。它不属于失败，不允许普通自动重试。取消按 task_id 和 owner 生效，不以 Socket 连接作为任务身份。

### 6.2 WS 订阅与恢复

1. 客户端连接 /ws/v1，handshake 提供 JWT；
2. REST 受理后订阅 task、operation 和需要的 session 频道；
3. 服务端查询权威 owner 后返回 subscription_ack；
4. 推送统一使用 snake_case ServerPushEventV1；
5. 客户端按 event_id 去重，按频道保存水位，重连时携带 after；
6. 收到 recovery_required 时查询任务和会话 REST API。

用户消息持久化后才能返回 REST accepted；助手最终消息和任务终态持久化后才能发送 done。

### 6.3 Expo 迁移

- REST 默认路径改为 /api/v1/inputs/text 和 /api/v1/tasks/cancel；
- WS 连接改为 /ws/v1；
- 发送 subscribe/unsubscribe 并处理 subscription_ack；
- 改用 ServerPushEventV1 的 event_type、session_id、tool_call_id；
- 实现事件去重、水位、REST 恢复和统一 token 传递；
- 新前端不再依赖 chat/cancel/resume_session。

旧通道仅保留到新闭环验收通过，本次不扩展其功能。

## 7. 真实 PostgreSQL 16 验证

使用独立可丢弃数据库，不使用开发或生产个人数据。记录 PostgreSQL 完整版本、扩展版本和 migration 标识。

必须执行：

1. 空库全量 migration up；
2. 检查表、索引、外键、check/unique 约束和 trigger；
3. 插入最小样本，验证用户域复合外键；
4. 回退全部项目 migration，确认无残留；
5. 再次全量 up，确认结果一致；
6. 在真实连接上运行确认事务集成测试；
7. 重启后端/数据库，验证会话、消息水位和任务恢复。

确认事务至少覆盖幂等重放、指纹冲突、同批并发、固定锁序、候选/目标版本冲突、24 小时过期、高风险单项、索引任务同事务登记和故障注入全量回滚。

pg-mem 只用于快速回归，不能作为真实 PostgreSQL 验收证据。

## 8. 队员任务包

### A. 确认契约与事务

### B. 外发策略网关

### C. 输入与聊天任务

实现 SubmitTextInput、CancelTask、GetTaskStatus，建立命令/输入双幂等，事务内登记原始输入与任务，事务后调度 Agent，持久化终态、最终助手消息和可查询错误。依赖 B 的受控 Provider 入口。

### D. WS v1 所有权与事件

使 task 和 operation 频道基于权威数据授权，将聊天任务转换为 ServerPushEventV1，验证 ACK、越权拒绝、顺序、去重、重放和恢复提示。依赖 C 的任务/命令数据。

### E. Expo 正式协议迁移

### F. 真实数据库与端到端验收

在独立 PostgreSQL 16 上执行全部数据库验证，用真实 HTTP/Socket.IO 客户端跑通聊天闭环，重启后验证会话、任务、消息和重放。依赖 A–E 完成。

## 13. 验收复核遗留项（已关闭）

2026-09-04 在进入下一条业务纵切前进行静态复核，确认原验证命令和数量记录保留，但发现以下真实用户闭环风险尚未覆盖：

1. Expo 在 REST 受理后才订阅 task/operation 频道；首次无水位订阅不回放既有事件，快速 Agent 可能在订阅前完成。
2. `waiting_privacy_decision` 已有任务状态，但 `SubmitPrivacyDecision` 尚未形成可恢复的继续、脱敏、阻止和超时闭环。
3. PostgreSQL 外发审计当前通过未等待的异步队列写入，审计失败不能保证阻止 Provider 调用。
4. 敏感扫描主要基于序列化文本，结构化字段名、嵌套值和部分自然语言格式可能漏检。
5. `request_analysis` 和 `analysis_types` 尚未实现，当前提交链会静默忽略这些字段。
6. Expo HTTP/WS 当时已共享 token provider；后续阶段 0 已通过明确的开发鉴权入口和真实设备鉴权联调关闭接线缺口，正式登录仍不在本阶段范围。

以上问题不推翻已经完成的契约、数据库和主链路验证；它们曾意味着“强制外发策略、断线恢复和 Expo 真实闭环”尚未满足本文第 10、11 节的全部关闭条件。

这些遗留项已统一纳入下一任务的阶段 0 并完成关闭，阶段 0 成果已形成基线提交 `2bdd9ce`，验证基线记录于当前权威的[开发交接说明](../01-项目/开发交接说明.md)。本任务状态据此更新为“已完成”。
