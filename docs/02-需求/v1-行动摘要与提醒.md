## 0. 规则层级与术语

- **【已确认边界】**：已有需求或架构已经确定，本文不得改写。
- **【本轮采用】**：为让摘要与提醒形成可实现闭环而补齐的规则；不把未确定的实现细节伪装成已选方案。
- **【待决策】**：不阻塞本文件的业务规则，但实现前必须由对应负责人确定。
- **业务日／业务周**：用于频率上限、固定生成和补生成去重的逻辑周期；其用户时区、具体起止时刻和周起始日由后续配置确定，本文不作决定。
- **摘要／复盘**：展示和建议产物，不是正式对象或正式状态变更。
- **提醒计划**：面向一个行动、待确认项或复盘周期的持久化调度意图；它与 Action、Goal、CandidateItem 的业务状态分离。
- **一次提醒实例**：提醒计划在一个逻辑触发机会下产生的单次投递／展示记录；关闭、稍后和投递失败只影响该实例或其后续计划，不等于修改行动状态。

## 1. 每日行动摘要应包含什么，且哪些内容不能被当成正式结论？

### 关键问题

每日摘要既要帮助用户决定“今天先做什么”，又不能把模型推断、待确认候选或过期信息伪装成已确认事实。它应读取哪些内容、怎样排序，以及如何表达不确定性？

### 推荐答案

每日行动摘要以**当前已确认对象和当前处境**为主，按“需要立即处理的行动 → 当天可推进的行动 → 目标方向 → 待确认内容”组织；模型建议仅用于解释优先级和提出候选，不直接写入正式对象。

建议的最小内容如下：

1. **今日需处理行动**：处于`待开始`或`进行中`的已确认行动，优先展示有明确截止时间、已到期观察或用户已设置提醒的行动。
2. **即将到期与已过期行动**：展示已确认截止时间、当前时效状态、延期计划状态和必要的处理入口；不能把“已过期”显示成“已取消”“已搁置”或“已完成”。
3. **当前最重要目标**：展示进行中目标，必要时补充规划中目标及其关联行动进度；已暂停、已完成、已放弃、正式已过期目标不作为正向当前目标。
4. **今日优先行动建议**：最多给出完成当天安排所需的优先建议、理由、约束或信息不足说明；建议依据可折叠查看。
5. **待确认内容**：展示尚未确认的行动、状态变更、目标、记忆或其他候选的数量、类型和入口；候选必须带“待确认”标识。
6. **数据质量说明**：当没有可执行行动、来源冲突、索引不完整、相关记录已删除或模型未生成完整建议时，摘要必须如实说明，而非补造结论。

摘要可按`已过期`、`进行中`、`待开始`、`暂时搁置`分组展示；暂时搁置项只作为背景或用户明确要求时的低优先级事项，不能被表述为当天必须执行。

### 已确认边界／本轮采用规则／待决策项

**【已确认边界】**

- 每日摘要默认包括今天需要完成的行动、即将到期或已过期行动、当前最重要目标、今日优先行动建议和待确认内容。
- 正式目标、行动、长期记忆和状态变更必须经用户确认；摘要、RAG、模型和后台任务只能生成分析、建议或候选。
- 结构化正式对象优先于原始记录；待确认内容若被使用，必须保留待确认状态，不能当作正式事实。
- 已删除对象不参与日常建议；归档、历史、低可信度、冲突或过期信息只能按其既有状态受限使用并说明。

**【本轮采用】**

- 摘要先通过结构化状态筛选，再按需使用 RAG 和处境模型补充限制、行动结果、近期记录和依据；不得先召回全部历史再交由模型决定是否使用。
- “今天优先做什么”应说明支撑因素，例如截止压力、目标关联、现实限制、历史结果或用户已确认偏好；证据不足时标为建议或推测。
- 摘要中提出的新行动、完成判断、延期、搁置、取消、目标调整、记忆更新或决策记录，均生成独立候选并交给确认中心；摘要本身不产生正式副作用。
- 若模型不可用、外发被隐私策略阻断或索引暂不可用，系统仍可依据本地已确认行动、截止时间和提醒状态生成**结构化基础摘要**，并明确标示“建议／依据不完整”；不得伪造模型分析结果。

**【待决策】**

- 摘要的具体页面布局、每类最多展示条数、排序权重、文案与是否支持用户手工置顶。
- 用户时区、业务日切分、固定生成的具体时间以及展示渠道。
- RAG 的具体召回数量、排序公式、模型提示词、上下文窗口和模型协议。

### 验收标准

- 有进行中行动、明确截止时间行动、目标和待确认项时，摘要能分别展示其当前状态，不混淆候选与正式对象。
- 行动已延期但尚未完成时，摘要展示新已确认截止时间和延期状态；存在未确认延期候选时，行动仍按原已确认截止时间计算时效状态。
- 已完成、已取消、已删除行动不会作为当前待办；暂时搁置行动不会被无提示列为今日必做。
- 无行动或无目标变化时，摘要生成简短且诚实的提示；索引或模型失败不导致错误状态或虚构建议。
- 从摘要发起的任何正式变更，均可在确认中心看到候选、来源和依据，未确认前正式对象不变。

## 2. 每日固定生成与当天首次打开补生成如何去重？

### 关键问题

系统既要在固定周期主动生成每日摘要，也要在该周期尚未生成时于用户首次打开 App 补生成。多次打开、后台恢复、任务重试或多入口触发时，怎样避免重复摘要、重复模型调用和重复提醒？

### 推荐答案

把“每日摘要”视为每个业务日最多一份的**逻辑产物**，而不是每次打开 App 都新建一份消息。固定任务与首次打开检查共用同一个摘要生成键、状态记录和持久化任务；谁先成功占用该业务日，另一方只读取已有结果或恢复未完成任务。

推荐逻辑：

```text
固定生成触发 或 当日首次打开检查
→ 计算当前业务日
→ 查询该业务日的摘要运行记录
→ 已成功：返回既有摘要，不重复生成
→ 运行中：复用／观察既有运行，不并发创建第二次
→ 未生成或可恢复失败：以同一逻辑键登记或恢复任务
→ 读取已确认对象和允许的上下文
→ 生成并持久化摘要结果
→ 标记当日摘要已成功生成
```

“当日首次打开补生成”只弥补**该业务日没有成功摘要**的情形；它不补发已关闭的提醒、不把过去多个业务日逐日补齐，也不因用户连续打开而刷新成多份日摘要。

### 已确认边界／本轮采用规则／待决策项

**【已确认边界】**

- 每天固定时间生成一次；当天尚未生成时，用户当天第一次打开 App 补生成。
- 每天最多生成一份行动摘要。
- 本地核心保存持久化任务，后台任务必须幂等；移动端或离线场景可在 App 运行或打开后补偿执行。
- v1 不承诺手机和电脑之间实时一致，因此各设备的本地数据和任务记录独立运行。

**【本轮采用】**

- 每份摘要以`本地数据空间 + 业务日 + 摘要类型`形成稳定逻辑键；该键同时用于任务去重、结果查询和恢复。
- 摘要运行至少区分“未登记／排队中／生成中／成功／可恢复失败／不可恢复失败或等待隐私决定”等执行结果；这是任务执行状态，不等于业务对象状态。
- 先持久化运行意图与逻辑键，再调用模型或写入展示结果；成功结果与当日已生成标记原子关联，避免崩溃后出现“已标记但无摘要”或“多份成功摘要”。
- 已成功摘要在同一业务日内默认稳定展示；用户新增、完成、延期或确认行动后，可以在界面显示数据已变化或允许手动查看最新状态，但不自动再生成第二份主动摘要。是否提供手动刷新及其频率另行决定。
- 若补生成前发生多次打开、进程恢复或任务扫描，仅允许一个持有同一逻辑键的任务实际执行；其他触发方记录命中已有运行，不重复发送或展示第二份摘要。

**【待决策】**

- 用户时区、固定生成时间、打开后何时判定“当天第一次”、失败后的具体重试次数与间隔。
- 摘要是否支持用户主动刷新、刷新是否调用模型、同日更新如何展示。
- 后台运行能力、进程保活、通知平台和任务调度实现。

### 验收标准

- 固定任务已成功生成后，用户同一业务日首次和后续打开 App 均复用该摘要，不新增第二份。
- 固定任务未成功执行时，当天首次打开能够登记或恢复同一逻辑任务并生成一份摘要。
- 并发打开、重复调度和客户端重试不会形成两份成功摘要、两条同日主动投递或两次正式业务写入。
- 生成过程中退出后，恢复检查能依据持久化状态安全继续或明确失败；不会因为补偿而改变行动、目标或候选状态。

## 3. 明确截止时间提醒与逾期行动提醒分别如何工作？

### 关键问题

行动可能只有日期、具有明确的时间、被延期、已完成、已取消、暂时搁置或已经逾期。怎样保证提醒准确、有用且不过度催促？

### 推荐答案

区分“**明确截止时间提醒**”与“**逾期行动集中提醒**”：前者针对已确认、具有具体时刻的行动或用户已确认的提醒计划；后者是对仍未处理的逾期行动按业务日聚合的一次处理机会。只有日期而没有具体时间的行动进入每日摘要，不自动产生精确时刻提醒。

明确截止时间提醒的判定：

```text
行动存在已确认的明确截止时刻或手工提醒计划
+ 行动未删除
+ 行动未完成、未取消
+ 对应提醒计划仍有效
→ 到达触发机会时生成一次提醒实例
```

逾期集中提醒的判定：

```text
已确认行动未完成、未取消
+ 已确认截止时间已过
+ 未有已确认的新截止时间使其恢复未逾期
+ 当日尚未产生逾期集中提醒
→ 生成当日一次聚合提醒机会
```

延期必须先由用户确认；确认成功后旧提醒计划失效或取消，并依据新已确认时间建立新计划。尚未确认的延期候选不改变现有提醒计划或行动时效判断。

### 已确认边界／本轮采用规则／待决策项

**【已确认边界】**

- 有明确截止时间的行动自动提醒，用户也可以手动设置提醒。
- 只有日期没有具体时间的行动进入每日摘要，不自动精确提醒。
- 行动延期后取消旧提醒，按新时间重新提醒。
- 逾期行动每天最多集中提醒一次，不高频催促。
- 行动的执行状态、计划状态和时效状态分离；“已过期”是按已确认截止时间计算的观察，不能由提醒任务写成正式行动状态。
- 已完成和已取消行动未来未发送的提醒计划应取消或失效，且计划变更随行动状态确认事务写入。

**【本轮采用】**

- 提醒系统只读取 Action 的已确认状态、截止时间和已确认提醒计划；它没有 Action 写入权。
- 对于暂时搁置行动，已到达的提醒实例不自动把行动恢复或取消；是否继续保留未来提醒只由已确认提醒计划或用户后续调整决定，并在投递前再次校验行动与计划状态。
- 逾期提醒按当前可处理的逾期行动聚合，展示行动数、关键截止信息和处理入口，不把每一项拆成高频连续催促。
- 同一行动在同一明确提醒机会内最多生成一个提醒实例；重复调度、离线补偿、展示失败或应用重启均复用该实例键。
- 通知或展示失败只更新提醒实例的投递／补偿状态，不回滚行动状态、截止时间、延期记录或确认事务。

**【待决策】**

- 用户时区、具体提醒时刻、提前量、手动提醒的交互、逾期集中提醒的展示时机和提醒渠道。
- 暂时搁置行动的默认提醒计划策略、提醒计划编辑字段与周期性／重复行动支持。
- 重试次数、退避策略、平台通知权限、离线限制与具体任务调度实现。

### 验收标准

- 只有日期而无具体时间的行动不会产生精确时刻提醒，但会在每日摘要中出现。
- 已确认的明确截止时间行动在对应触发机会最多出现一次提醒；重复调度不重复投递。
- 延期确认成功后旧提醒不再有效，新提醒只基于新已确认时间；未确认延期候选不会提前改变提醒或时效状态。
- 已完成、已取消或已删除行动不会继续产生未来提醒；逾期提醒不会把它们纳入聚合。
- 同一业务日的逾期行动即使多次补偿扫描，也只形成一次集中提醒机会，且不自动写入“完成”“延期”“搁置”或“已过期”正式状态。

## 4. 用户关闭、稍后和调整提醒时，系统到底改变什么？

### 关键问题

用户点“关闭本次提醒”“稍后提醒”“完成”“延期”“搁置”或“调整提醒设置”时，哪些操作只影响本次投递，哪些需要进入确认中心，哪些会改变 Action 或 Reminder 计划？

### 推荐答案

将提醒交互拆成两类：

1. **投递处置**：关闭本次、稍后提醒，只改变一次提醒实例的展示／下次投递安排，不改变行动、目标或候选的正式状态。
2. **业务变更或计划变更**：完成、延期、搁置、取消、修改截止时间等生成确认中心候选；用户直接调整未来提醒计划只修改 Reminder 计划，若该调整同时修改 Action 的截止时间或来自摘要／复盘的模型建议，则必须进入确认中心。

| 用户操作 | 直接结果 | 是否直接改 Action／Goal | 是否进入确认中心 |
| --- | --- | ---: | ---: |
| 关闭本次提醒 | 当前提醒实例标记为已关闭，不再对同一实例重复投递 | 否 | 否 |
| 稍后提醒 | 当前实例记录稍后处理意图，生成或更新同一逻辑实例的下一次投递安排 | 否 | 否 |
| 完成 | 生成“完成行动”确认项 | 否 | 是 |
| 延期 | 生成包含新截止时间的延期确认项 | 否 | 是 |
| 暂时搁置／取消 | 生成相应状态变更确认项 | 否 | 是 |
| 查看行动／待确认项 | 仅导航和展示 | 否 | 否 |
| 用户直接调整未来提醒计划 | 保存用户明确的计划设置与版本／审计信息 | 否，除非同时改截止时间 | 视是否含业务变更而定 |
| 摘要、复盘或模型建议调整提醒计划 | 形成待确认的提醒计划变更候选 | 否 | 是 |

### 已确认边界／本轮采用规则／待决策项

**【已确认边界】**

- 提醒支持完成、延期、搁置、查看行动、稍后提醒和关闭本次提醒；用户可关闭本次、稍后处理、暂时不再提醒或调整提醒设置。
- 修改行动状态、截止时间、内容和结果是正式业务变更，必须经确认中心、版本校验和 Local Core 事务写入。
- “暂不处理”待确认候选仍为待确认，不能自动变为拒绝、正式对象或正式提醒对象。

**【本轮采用】**

- “关闭本次”只消费当前提醒实例，不取消行动、未来手动提醒或待确认项；同一实例的重试／补偿必须尊重已关闭状态。
- “稍后”只影响当前实例的后续投递安排，并受全局频率上限约束；它不更改原始截止时间、执行状态或目标状态。
- “暂时不再提醒”作用于用户明确指定的提醒计划范围，必须持久化其范围、当前版本和生效状态；不应以删除 Action、关闭摘要或取消候选代替。
- 用户明确在设置页调整纯提醒计划，可由 Local Core 直接持久化为提醒对象变更并保留审计信息；若同次操作包含截止时间或行动状态变更，必须拆出并进入确认中心。由模型、摘要或周复盘提出的提醒计划调整永远只是候选。
- 所有确认中心候选必须保留来源为“提醒交互”，以便用户区分自己主动操作、系统建议与后台触发。

**【待决策】**

- “稍后”的可选方式、何时再次出现、“暂时不再提醒”的默认范围和恢复入口。
- 提醒计划具体字段、是否允许多个手动提醒、编辑界面、渠道偏好和通知权限处理。
- 用户直接调整提醒计划是否需要额外风险提示的细分条件。

### 验收标准

- 关闭同一提醒实例后，应用重启、补偿扫描或重复调度均不会再次投递该实例。
- 稍后提醒不会改变行动截止时间、执行状态、计划状态、目标状态或候选状态。
- 从提醒点击完成、延期、搁置或取消后，正式 Action 在用户确认成功前保持不变；重复点击不会创建重复候选或重复确认副作用。
- 用户调整提醒计划但不修改行动时，Action 版本与状态不变；调整包含截止时间时，未确认前旧截止时间与旧计划仍有效。
- 提醒来源的状态变更候选可以在确认中心查看来源、影响、版本与风险提示。

## 5. 待确认内容怎样提醒，才不会自动确认或反复打扰？

### 关键问题

待确认候选需要被看见，但它们既不是正式行动，也不能因反复提醒而升级。首次打开、暂不处理、关闭单条／全部提醒和后续再提醒分别如何约束？

### 推荐答案

待确认提醒以 CandidateItem／ConfirmationBatch 的待确认生命周期为权威来源；首次打开 App 可提示存在待确认内容。用户选择“暂不处理”后，同一业务日不重复提醒，之后仅按后续确定的间隔再次提醒。用户可以关闭某条或全部待确认提醒，但关闭提醒不等于拒绝候选。

推荐流程：

```text
发现仍可处理的待确认候选
→ 首次打开或到达再次提醒机会
→ 生成待确认提醒实例
→ 用户确认／修改后确认／拒绝／暂不处理／关闭提醒／查看
→ 更新候选生命周期或提醒抑制状态
→ 永不因提醒任务自动创建正式对象
```

### 已确认边界／本轮采用规则／待决策项

**【已确认边界】**

- 待确认内容首次打开 App 时提醒；用户选择“暂不处理”后当天不重复提醒，后续按间隔再次提醒；用户可关闭某条或全部提醒。
- 待确认内容可确认、修改后确认、拒绝、暂不处理、删除或标记识别错误。
- 未确认候选永不自动升级为正式目标、行动或长期记忆；候选状态不能与 Action、Goal 或 Reminder 状态混用。
- 待确认内容可以受限参与 RAG，但必须标记为待确认，不能作为已确认事实或硬约束。

**【本轮采用】**

- 待确认提醒只面向仍处于可处理待确认状态、未被删除／取消／失效的候选或批次；投递前必须再次查询权威候选状态。
- 用户“暂不处理”记录提醒抑制信息，不新增独立候选业务状态，也不改变候选内容、来源、版本或确认资格。
- 关闭某条提醒只抑制该候选／批次对应的提醒范围；关闭全部只改变待确认提醒偏好范围。两者均不等于“拒绝”或“删除”。
- 多个候选可聚合为一份待确认提示，但每个候选仍可独立确认、修改、取消或暂不处理；不得因批次提醒被关闭而静默改变其他候选。
- 待确认提醒不为候选对应的未创建 Action 预先建立到期提醒；只有 Action 经确认正式创建后才可进入行动提醒评估。

**【待决策】**

- 后续再次提醒的具体间隔、候选有效期、关闭全部的持续范围、批次与单项的默认聚合方式。
- 待确认中心的展示渠道、排序、筛选、删除候选后的恢复规则与提醒偏好界面。

### 验收标准

- 首次打开 App 时存在待确认候选会出现提示；同日选择暂不处理后再次打开不重复提示同一范围。
- 关闭提醒、稍后处理、打开卡片或默认全选均不会创建正式 Action、Goal、Memory 或修改其状态。
- 已确认、已取消、已删除或已失效候选不会再次产生待确认提醒。
- 待确认延期候选存在时，原行动仍按当前已确认截止时间和状态参与摘要／逾期判断。
- 待确认内容被摘要、复盘或 RAG 使用时，界面和模型上下文均可辨认其待确认性质。

## 6. 每周目标复盘的输入、生成与确认边界是什么？

### 关键问题

周复盘需要从执行历史中找出计划与实际差异，但不应因为模型解释或用户关闭页面就自动调整目标、行动、记忆或提醒。它用哪些资料、何时补生成、如何处理没有有效变化和用户跳过？

### 推荐答案

每个业务周最多生成一份目标复盘。固定周期触发未成功时，可在后续打开 App 时补生成该周复盘；用户明确跳过本周后，只记录跳过／抑制，不重复强提醒。没有有效行动或目标变化时，生成简短提示即可。

复盘可参考：

- 完成与未完成行动、延期、逾期、暂时搁置和行动结果；
- 目标当前状态、进展依据、关联行动与计划／实际差异；
- 用户记录的未完成原因与实际花费时间；
- 建议已提出、已采纳、已执行和结果之间的关联；
- 当前与历史处境、相关决策、过期记忆及其状态标记；
- 下周值得优先处理的行动和需要进一步确认的信息。

复盘输出应明确区分“客观统计／历史依据”“系统解释或建议”“待确认变更”“已确认状态”。

### 已确认边界／本轮采用规则／待决策项

**【已确认边界】**

- 每周复盘参考完成和未完成行动、延期、过期、搁置、目标进展、未完成原因、实际花费时间、计划和实际差异、建议效果、目标调整、长期记忆更新及下周重要行动。
- 复盘提出的目标调整、记忆更新、决策记录、新行动、行动／目标状态变更和提醒计划变更均须用户确认。
- 每周最多生成一次目标复盘；未生成时下次打开 App 补生成；用户跳过本周后不重复强提醒；无有效行动或目标变化时可生成简短提示。
- 历史复盘可使用历史处境和过期记忆，但不能自动写回当前状态。

**【本轮采用】**

- 每周复盘以`本地数据空间 + 业务周 + 复盘类型`作为稳定逻辑键，固定任务、首次打开补偿和重复调度共用该键。
- 复盘先读取结构化行动、目标、结果、建议效果、决策和状态变化，再按任务需要使用历史 RAG；历史或过期资料必须携带发生时间、状态、可信度、确认状态和敏感标记。
- 用户跳过仅改变该业务周复盘的展示／提醒状态，不自动将任何行动标记为放弃、目标标记为暂停，也不影响下周正常复盘资格。
- 复盘建议的下周行动、目标调整、计划调整、记忆或决策经验均以可逐项处理的候选进入确认中心；候选来源明确为“每周复盘”。
- 复盘生成失败时保留运行失败摘要和可恢复状态；绝不把不完整统计当作已完成复盘或正式业务结论。

**【待决策】**

- 用户时区、周起始日、固定生成的具体星期与时间、补生成窗口、复盘页面和通知渠道。
- 计划与实际差异的计算规则、时间记录入口、建议效果的量化方式和复盘内容篇幅。
- 用户能否手动触发额外复盘及其频率限制。

### 验收标准

- 同一业务周无论固定任务、首次打开补偿或重复调度均最多形成一份成功复盘。
- 复盘能区分已完成、未完成、延期、逾期、搁置和取消等行动历史，不把到期观察当成用户已确认的状态。
- 用户跳过本周后，不会在该周被重复强提醒，也不会产生任何正式状态变更。
- 复盘提出的行动、目标、记忆、决策、处境或提醒计划调整均进入确认中心；用户关闭复盘页面不构成确认。
- 没有有效行动或目标变化时，复盘输出简短提示且不虚构趋势、原因或记忆更新建议。

## 7. 主动行为频率上限如何跨触发源一致执行？

### 关键问题

固定任务、首次打开补偿、用户返回前台、离线恢复和重复调度可能同时触发主动行为。如何保证产品不因多个入口而变成高频打扰？

### 推荐答案

频率上限以**逻辑产物或提醒实例**为单位，在 Local Core 的持久化状态上统一校验，而不是依赖客户端内存、通知平台回执或模型是否执行成功。

| 主动行为 | v1 上限 | 去重单位 |
| --- | --- | --- |
| 每日行动摘要 | 每个业务日最多 1 份 | `数据空间 + 业务日 + 摘要类型` |
| 明确提醒时间 | 每个明确提醒机会最多 1 次 | `提醒计划 + 触发机会` |
| 逾期行动集中提醒 | 每个业务日最多 1 次 | `数据空间 + 业务日 + 逾期聚合类型` |
| 每周目标复盘 | 每个业务周最多 1 次 | `数据空间 + 业务周 + 复盘类型` |
| 待确认提醒 | 受首次打开、暂不处理和用户关闭范围约束 | `候选／批次范围 + 业务周期／再次机会` |

### 已确认边界／本轮采用规则／待决策项

**【已确认边界】**

- 每天最多 1 份行动摘要；每个明确提醒时间最多提醒 1 次；逾期行动每天最多集中提醒 1 次；每周最多 1 次目标复盘。
- 用户可以关闭本次、稍后处理、暂时不再提醒或调整提醒设置。

**【本轮采用】**

- 上限在创建提醒实例或摘要／复盘运行前校验，不能等到通知已经发出后才去重。
- 同一主动行为由多个入口命中时，以首次成功登记的逻辑键为准；后续入口只查询、恢复或跳过，不追加第二次投递。
- 关闭本次、投递失败和稍后处理不会绕过上限：稍后只能更新同一提醒实例的后续安排；是否允许跨周期重新提醒由后续规则决定。
- 摘要、逾期集中提醒、待确认提醒和周复盘是不同业务产物；它们不能相互伪装为已完成或绕过各自的上限。

**【待决策】**

- 业务日／业务周的具体计算、提醒合并策略、稍后提醒是否计入原触发机会、不同渠道是否共享同一投递上限。
- 每类主动行为的静默时段、用户偏好、优先级冲突和平台限流处理。

### 验收标准

- 同一业务日的固定生成、首次打开补生成和恢复扫描不会生成两份行动摘要。
- 同一明确提醒机会被重复调度时，最多形成一条有效提醒实例。
- 多个逾期行动在同一业务日形成一份集中提醒，不会按扫描次数或行动数重复轰炸。
- 同一业务周不会因多次打开 App 产生多份周复盘。
- 用户关闭、稍后或调整偏好后，后续投递仍遵守持久化上限与其指定范围。

## 8. 提醒、确认中心、行动／目标状态机之间怎样交接？

### 关键问题

提醒会展示快捷操作，摘要和复盘会提出建议，行动与目标又拥有独立状态机。如何避免“点击通知就直接写库”、待确认候选被当成正式状态，或目标／行动之间互相自动改写？

### 推荐答案

采用“**提醒只管理投递，确认中心只管理正式确认，状态机只管理正式对象状态**”的分层交接。提醒、摘要和复盘可以读取状态、展示依据和创建候选；只有确认中心收到用户明确确认并由 Local Core 校验成功后，Action、Goal、Memory、Decision 或 Reminder 计划的正式变更才生效。

```text
提醒／每日摘要／每周复盘
→ 读取已确认 Action、Goal、Candidate、Reminder 状态
→ 展示、统计、提出建议或生成候选
→ 用户明确选择正式变更
→ Confirmation Command
→ Local Core 版本／状态／风险／幂等校验
→ 原子更新正式对象、关键变更和提醒计划
→ 异步索引／处境刷新／后续任务
```

### 已确认边界／本轮采用规则／待决策项

**【已确认边界】**

- Action 由执行状态、计划状态和时效状态组成；提醒状态、候选状态、确认批次状态、删除状态与它们独立。
- Action 的完成、延期、暂时搁置、取消、内容或截止时间修改必须经过确认中心；到期和逾期提醒不得直接改变 Action。
- Goal 与 Action 松耦合：行动完成只可作为目标可能完成的依据；目标完成、暂停、放弃或过期不自动改变关联行动。
- 摘要和复盘生成的正式变更必须进入确认中心；模型、RAG、处境模型和后台任务不得直接写入正式对象。

**【本轮采用】**

- Reminder 计划的最小逻辑状态为“有效／已暂停或抑制／已失效”，一次提醒实例的最小投递状态为“待触发／已投递或已展示／已关闭／已稍后／投递失败待补偿／已失效”。这些状态仅记录提醒事实，不替代 Action、Goal 或 Candidate 状态。
- 从提醒触发“完成、延期、搁置、取消、恢复、修改截止时间”等操作时，系统生成带`来源=提醒交互`、对象版本和操作标识的即时确认项；客户端不直接更新 Action。
- 行动确认事务成功时，Local Core 同一事务内更新 Action、关键变更记录、来源关系、未发送提醒计划和索引任务；实际投递异步进行。
- 目标关联行动的状态或提醒只可作为复盘和摘要中的影响说明。若用户要处理关联行动，必须为每个行动生成独立确认项。
- 待确认行动候选没有正式 Action 标识前，不建立 Action 提醒计划；待确认状态变更候选不覆盖既有正式 Action 的提醒计划。

**【待决策】**

- Reminder 与 ConfirmationBatch 的具体存储字段、提醒计划是否支持多层级继承、撤销入口与界面形式。
- 目标提醒的独立产品规则；本文件不将“目标已到期观察”自动扩展为目标主动提醒。
- 客户端通知按钮、深链、跨端展示和本地数据库／事务实现。

### 验收标准

- 点击提醒中的完成、延期、搁置、取消或修改操作后，Action／Goal 在确认提交成功前没有任何正式变化。
- 同一提醒快捷操作重复提交时，确认中心按操作标识去重；不同内容复用同一标识时被识别为冲突。
- 目标状态变化不会自动取消、完成、搁置或延期关联 Action；行动完成不会自动完成 Goal。
- 待确认 Action 或延期候选不生成正式到期提醒，也不覆盖已确认 Action 的提醒计划。
- Reminder 实例、CandidateItem、ConfirmationBatch、Action、Goal 的状态可独立查询和解释，不发生字段或语义混用。

## 9. 后台任务怎样做到幂等、补偿且不重复产生正式副作用？

### 关键问题

本地设备可能离线、进程终止、任务重复执行或通知投递失败。后台任务如何恢复，同时确保不重复生成摘要、复盘、提醒、候选或正式业务变更？

### 推荐答案

所有摘要、复盘、提醒检查、投递和补偿均以持久化任务和稳定逻辑键运行；后台任务可以登记分析、提醒、候选和补偿记录，但不得绕过确认中心创建或修改正式业务对象。补偿的目标是让应有的逻辑产物最终可见，而不是重放已完成副作用。

推荐的通用任务流程：

```text
触发／恢复扫描
→ 构造任务逻辑键与命令／载荷指纹
→ 原子登记或取得已有任务
→ 校验前置对象版本、删除状态、频率上限与提醒抑制
→ 执行业务计算／模型调用／投递
→ 原子保存结果或失败分类
→ 需要时登记后续补偿任务
→ 不直接提交 Action、Goal、Memory、Decision 正式变更
```

### 已确认边界／本轮采用规则／待决策项

**【已确认边界】**

- v1 后台任务包括输入分析、索引更新、每日行动摘要、明确截止时间提醒、逾期行动提醒、每周目标复盘、待确认内容提醒、处境模型刷新等。
- 本地持久化任务记录必须支持幂等和打开 App 后补偿执行；通知失败或离线不回滚 Action 状态。
- 正式对象写入与索引任务登记应在确认事务中一致；索引更新失败进入补偿，不回滚已成功的正式变更。
- 同一确认操作和同一命令内容只能提交一次；重复操作返回既有结果，操作标识与内容不一致时拒绝执行。

**【本轮采用】**

- 每类后台任务必须有稳定逻辑键：每日摘要按业务日、每周复盘按业务周、明确提醒按计划和触发机会、逾期提醒按业务日聚合、待确认提醒按候选／批次与提醒机会；补偿任务复用原键而非新建同类副作用。
- 执行前后均校验权威对象：行动是否仍有效、候选是否仍待确认、提醒是否已关闭、上限是否已占用、源对象版本是否已变化。前置条件失效时，将实例标记为已失效／无需执行，而不是继续投递旧内容。
- 模型调用、通知投递、索引刷新和结果保存拆分记录：模型或投递失败不回滚已确认业务对象；正式确认失败不保留半个 Action、Goal、提醒计划或变更历史。
- App 打开后的补偿只扫描可恢复、未成功且未被抑制的任务；它不追补多个过期业务日的日摘要，不补发已关闭实例，也不重新执行已提交的确认操作。
- 任务日志和用户可见错误只保留最小必要元数据与错误摘要，不保存完整敏感上下文、完整模型输出或 API Key。

**【待决策】**

- 任务队列／存储技术、锁实现、并发模型、重试次数、超时、退避、失败保留期、死信处理及平台后台能力。
- 通知成功回执的定义、离线时是否展示应用内补偿提示、任务监控页面和诊断导出格式。

### 验收标准

- 重复调度、进程中断后恢复和客户端重试不会重复创建日摘要、周复盘、明确提醒实例、逾期集中提醒或待确认提醒。
- 已关闭、已稍后、已失效或已成功的提醒实例不会被补偿逻辑当作新的提醒再次投递。
- 行动／目标／候选在任务执行期间发生变化时，旧任务不会覆盖新状态或基于旧截止时间发送提醒。
- 模型调用、索引更新或通知投递失败时，已确认的 Action／Goal 状态和历史保持正确；恢复成功后不产生第二次正式变更。
- 后台任务无法在没有用户确认的情况下创建正式目标、行动、记忆、决策、截止时间或状态变化。

## 10. 模型、RAG 与敏感信息在主动生成中有哪些硬边界？

### 关键问题

摘要、复盘和后台补偿可能需要模型、RAG、长期记忆、处境模型和历史记录。怎样既保证建议有个人上下文，又不扩大外发、泄露敏感信息或让模型直接改业务状态？

### 推荐答案

每日摘要和每周复盘按显式任务类型使用最小必要 RAG 与处境上下文；若要调用外部模型，最终外发载荷必须在供应商适配器前重新经过统一敏感信息策略。模型只能返回展示内容、分析、建议或候选；所有正式变更仍走确认中心。

### 已确认边界／本轮采用规则／待决策项

**【已确认边界】**

- 每日摘要可读取当前目标、行动、截止时间、限制、相关结果和待确认内容；每周复盘可读取当前／历史处境、目标、行动结果、建议效果、决策和过期记忆。
- RAG 采用结构化硬筛、关键词／语义召回、状态复核和最小上下文；结构化正式对象优先，待确认、过期、冲突、删除和敏感状态必须随上下文传递。
- 所有外部模型请求，包括 RAG 请求、每日摘要、周复盘、后台任务和每次重试，都必须在最终外发请求形成后经过敏感信息处理钩子。
- v1 强制识别身份证件、银行卡、密码、API Key 和其他密钥；本地完整保存与外发严格分离；基础调用日志不保存完整上下文、完整 RAG 结果、完整原始输出或 API Key。
- 模型、RAG、处境模型和后台任务不得直接创建、修改、删除 Action／Goal／Memory／Decision 或正式状态。

**【本轮采用】**

- 摘要优先用当前有效、已确认对象；复盘允许按历史场景使用过期记忆和历史处境，但必须保留其历史／过期标签，不能回写为当前状态。
- 外发载荷只包含完成当前摘要或复盘任务的最小内容；不得包含内部 ID、本地路径、数据库字段、API Key 或无关完整历史。
- 对摘要／复盘产生的每次外部模型请求、自动切换和重试，都重新组装最终载荷并重新执行敏感检测与策略判定；不得复用过期的放行、脱敏或模型结果。
- 敏感处理要求用户决定时，后台任务进入“等待隐私决定”而非静默外发；在此期间可展示本地结构化基础内容，但不得假称完整模型摘要／复盘已经生成。
- 若模型输出包含行动、目标、记忆、决策、处境或提醒计划调整，只可保存为带来源与依据的候选；模型输出无效、冲突或不完整时不创建可提交的非法候选。

**【待决策】**

- 敏感信息的具体识别器、脱敏替换格式、误报／漏报处理、隐私提醒交互、单次放行与外部 Embedding／OCR／语音能力边界。
- 模型供应商、协议、提示词、模型选择细节、重试次数、超时、错误分类和模型调用日志保留策略。
- 本地数据库及原始附件加密方案、导出结构与加密格式。

### 验收标准

- 每日摘要和周复盘只使用与当前任务相关的最小上下文；普通闲聊不会因系统具备摘要能力而自动读取个人历史。
- 待确认、低可信度、已过期、冲突或已删除来源信息不会被模型或界面包装成当前已确认事实。
- 摘要、复盘、后台补偿、模型重试和自动切换均经过统一敏感信息处理；供应商适配器拿不到未经处理的完整载荷。
- 外发日志、任务日志和错误信息不含 API Key、完整敏感明文、完整 RAG 上下文或完整模型原始输出。
- 模型建议在用户确认成功前不改变任何正式对象；敏感外发确认与业务变更确认可以分别追溯，且互不替代。

## 11. 本文件的边界与待拆分事项

### 本文件负责

- 每日行动摘要、固定生成与首次打开补生成的逻辑规则。
- 明确截止时间提醒、逾期集中提醒、待确认提醒与每周目标复盘的产品边界。
- 主动行为频率上限、提醒交互语义、状态机交接、后台幂等与补偿规则。
- 摘要／复盘的模型、RAG、确认中心和敏感信息交叉边界。

### 由其他文档继续负责

- **确认中心**：候选、批次、确认命令、风险提示、撤销、事务和版本校验的完整通用规则。
- **行动／目标状态机**：状态定义、完整允许／禁止转移与撤销条件。
- **模型配置与调用**：供应商协议、模型选择、结构化输出、错误分类和具体重试策略。
- **敏感信息处理**：识别器、脱敏、隐私模式、误报／漏报和外发确认交互。
- **RAG 与处境模型**：索引、召回、排序、上下文格式、处境版本与重建实现。
- **原始记录与结构化存储**：具体对象字段、数据库、事务和导出实现。

### 本轮明确不决定

- 用户时区、业务日／业务周的具体切分、固定生成时间、提醒提前量或再次提醒间隔。
- 通知渠道、跨端表现、后台平台能力、调度器、数据库、任务队列或客户端实现。
- 任何重试次数、超时、退避参数、模型供应商、模型协议和平台通知参数。
