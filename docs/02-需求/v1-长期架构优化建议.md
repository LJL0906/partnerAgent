## 1. 混合 Agent 架构的统一抽象

### 1.1 当前架构

v1.0 采用混合 Agent 架构：
- Pi Agent（TypeScript）：实时交互
- LangGraph（Python）：复杂工作流

### 1.2 长期优化方向

**建立统一抽象层，让两者无缝协作**：

```typescript
// 统一的 Agent 接口
export interface UnifiedAgent {
  execute(request: AgentRequest): AsyncIterator<AgentEvent>;
  cancel(): Promise<void>;
  checkpoint(): Promise<AgentCheckpoint>;
  resume(checkpoint: AgentCheckpoint): Promise<void>;
}

// Pi Agent 适配器
export class PiAgentAdapter implements UnifiedAgent {
  private agent: Agent;
  
  async *execute(request: AgentRequest): AsyncIterator<AgentEvent> {
    for await (const event of this.agent.stream()) {
      yield this.mapToUnifiedEvent(event);
    }
  }
}

// LangGraph 适配器
export class LangGraphAdapter implements UnifiedAgent {
  async *execute(request: AgentRequest): AsyncIterator<AgentEvent> {
    const stream = await this.pythonClient.streamWorkflow(request);
    for await (const event of stream) {
      yield this.mapToUnifiedEvent(event);
    }
  }
}

// 统一调度器
export class AgentOrchestrator {
  async execute(request: AgentRequest): AsyncIterator<AgentEvent> {
    const agent = this.selectAgent(request);
    return agent.execute(request);
  }
  
  private selectAgent(request: AgentRequest): UnifiedAgent {
    if (request.requiresCheckpoint || request.estimatedDuration > 60) {
      return this.langGraph;
    }
    return this.piAgent;
  }
}
```

### 1.3 核心原则

- 业务层只依赖 `UnifiedAgent` 接口
- 两个 Agent 系统都是可插拔的实现
- 未来可以无缝切换或添加新的 Agent 实现

### 1.4 何时考虑

当协调代码超过 3000 行时，考虑构建自己的 Agent Runtime，吸收 Pi Agent 和 LangGraph 的优点。

## 2. 多模态支持的插件化架构

### 2.1 当前架构

v1.0 全面支持多模态（图片、语音、文档、网页）。

### 2.2 长期优化方向

**插件化的模态处理器**：

```typescript
// 统一接口
export interface ModalityHandler {
  canHandle(input: Input): boolean;
  process(input: Input): Promise<ProcessedInput>;
}

// 图片处理器
export class ImageHandler implements ModalityHandler {
  async process(input: ImageInput): Promise<ProcessedInput> {
    const vision = await this.visionService.analyze(input.url);
    const ocr = await this.ocrService.extract(input.url);
    return { 
      vision, 
      ocr, 
      embedding: await this.embed(vision + ocr) 
    };
  }
}

// 音频处理器
export class AudioHandler implements ModalityHandler {
  async process(input: AudioInput): Promise<ProcessedInput> {
    const transcript = await this.whisperService.transcribe(input.url);
    return { 
      transcript, 
      embedding: await this.embed(transcript) 
    };
  }
}

// 统一管道
export class MultimodalPipeline {
  private handlers: ModalityHandler[] = [];
  
  async process(input: Input): Promise<ProcessedInput> {
    const handler = this.handlers.find(h => h.canHandle(input));
    if (!handler) throw new Error('Unsupported modality');
    return handler.process(input);
  }
}
```

### 2.3 本地 + 云端混合策略

```typescript
export class HybridModalityService {
  async process(input: Input, privacy: PrivacyLevel): Promise<Result> {
    if (privacy === 'strict') {
      return this.localHandlers.process(input);
    } else {
      return this.cloudHandlers.process(input);
    }
  }
}

// 本地能力
const localHandlers = {
  vision: LocalLLaVA,
  ocr: PaddleOCR,
  speech: WhisperCPP,
  embedding: BGEM3
};

// 云端能力
const cloudHandlers = {
  vision: ClaudeOpusVision,
  ocr: GoogleCloudVision,
  speech: WhisperAPI,
  embedding: OpenAIEmbedding
};
```

### 2.4 优势

- 每个模态都是独立的处理器
- 新增模态不影响现有代码
- 统一的输出格式（文本 + Embedding）
- 隐私场景有本地兜底，非隐私场景享受云端质量

## 3. Obsidian 双向同步的最佳方案

### 3.1 当前架构

v1.0 支持 Obsidian 双向同步。

### 3.2 长期优化方向

#### 方案 A：CRDT（冲突无关复制数据类型）

```typescript
import { Automerge } from '@automerge/automerge';

export class ObsidianSyncService {
  private documents: Map<string, Automerge.Doc<Goal>> = new Map();
  
  async syncGoal(goalId: string): Promise<void> {
    const dbGoal = await this.goalService.findById(goalId);
    const mdGoal = await this.obsidianService.readGoal(goalId);
    
    // CRDT 自动合并（无冲突）
    const dbDoc = Automerge.from(dbGoal);
    const mdDoc = Automerge.from(mdGoal);
    const merged = Automerge.merge(dbDoc, mdDoc);
    
    // 双向写回
    await this.goalService.update(goalId, merged);
    await this.obsidianService.writeGoal(goalId, merged);
  }
}
```

**CRDT 优势**：
- 数学上保证最终一致性
- 无需中央协调
- 离线编辑完全支持
- 无"冲突解决"对话框

#### 方案 B：事件溯源

```typescript
interface GoalEvent {
  id: string;
  timestamp: number;
  source: 'app' | 'obsidian';
  type: 'created' | 'updated' | 'completed';
  changes: Partial<Goal>;
}

export class EventSourcingSync {
  async sync(goalId: string): Promise<void> {
    const appEvents = await this.getAppEvents(goalId, this.lastSyncTime);
    const mdEvents = await this.getObsidianEvents(goalId, this.lastSyncTime);
    
    // 按时间戳排序
    const allEvents = [...appEvents, ...mdEvents].sort((a, b) => 
      a.timestamp - b.timestamp
    );
    
    // 重放到两端
    const finalState = this.replay(allEvents);
    await this.applyToApp(goalId, finalState);
    await this.applyToObsidian(goalId, finalState);
  }
}
```

**事件溯源优势**：
- 完整的修改历史
- 可以回溯任意时间点
- 冲突解决有明确的顺序
- 可以实现"撤销"功能

#### 方案 C：明确的所有权（v1.0 推荐）

```typescript
interface SyncMetadata {
  owner: 'app' | 'obsidian';
  lastModified: number;
  conflictResolution: 'owner-wins' | 'manual';
}

const syncRules = {
  goals: { owner: 'app' },           // 目标在 App 中编辑
  dailyNotes: { owner: 'obsidian' }, // 日记在 Obsidian 中编辑
  memories: { owner: 'app' },        // 记忆在 App 中编辑
};
```

**所有权模型优势**：
- 避免真正的冲突
- 用户有明确的心智模型
- 实现简单，v1.0 可用
- v1.1+ 再升级到 CRDT/事件溯源

## 4. Agent 能力的可组合性

### 4.1 概念

不要把 Agent 当成黑盒，而是**能力的组合**。

### 4.2 实现

```typescript
// 能力原子化
interface AgentCapability {
  name: string;
  execute(context: Context): Promise<Result>;
}

// 能力可以自由组合
const chatAgent = new Agent([
  new RAGCapability(),
  new MemoryCapability(),
  new ToolCallingCapability(),
]);

const analysisAgent = new Agent([
  new RAGCapability(),
  new DeepThinkingCapability(),  // 多轮推理
  new StructuredOutputCapability(),
]);
```

### 4.3 优势

- 新能力可以插入到任何 Agent
- 测试更容易（单元测试每个能力）
- 可以 A/B 测试不同的能力组合

## 7. 多层记忆架构（v1.0 已包含）

### 7.1 设计

```sql
-- 工作记忆（短期，当前对话）
CREATE TABLE working_memory (
  id UUID PRIMARY KEY,
  session_id UUID REFERENCES sessions(id),
  content TEXT,
  expires_at TIMESTAMP
);

-- 情景记忆（中期，重要事件）
CREATE TABLE episodic_memory (
  id UUID PRIMARY KEY,
  event_type TEXT,
  importance INT,
  emotion TEXT,
  embedding VECTOR(1536)
);

-- 语义记忆（长期，提取的事实）
CREATE TABLE semantic_memory (
  id UUID PRIMARY KEY,
  fact_type TEXT,
  subject TEXT,
  predicate TEXT,
  object TEXT,
  confidence FLOAT,
  embedding VECTOR(1536)
);

-- 程序记忆（元，用户习惯）
CREATE TABLE procedural_memory (
  id UUID PRIMARY KEY,
  pattern_type TEXT,
  trigger TEXT,
  action TEXT,
  frequency INT,
  success_rate FLOAT
);
```

### 7.2 优势

比简单的 RAG 更接近人类记忆模型。

## 8. 长期架构原则总结

### 8.1 统一抽象层 > 单一实现

允许底层技术演进，不影响上层。

### 8.2 插件化架构 > 单体架构

新能力是插入，不是重写。

### 8.3 本地 + 云端混合 > 纯云端

隐私和质量兼得。

### 8.4 CRDT/事件溯源 > 传统冲突解决

数学上的正确性 > 工程上的妥协。

### 8.5 可观测性内建 > 事后添加

追踪、监控、日志是一等公民。

### 8.6 数据版本化 > 一次性设计

假设所有数据结构都会演进。

## 9. 实施时机建议

### 9.1 立即可用（v1.0）

- 多层记忆架构
- 可观测性内建（Prometheus + Grafana + OpenTelemetry）
- 数据版本化（从第一张表开始）
- Obsidian 明确所有权模型

### 9.2 v1.1 时机

- 多模态插件化架构（新增模态时）
- 本地 + 云端混合策略（隐私需求明确时）
- Obsidian 事件溯源（冲突场景增多时）

### 9.3 v1.2+ 时机

- 统一 Agent 抽象层（协调代码超过 3000 行时）
- Agent 能力可组合性（需要灵活组合能力时）
- Obsidian CRDT（需要完美的离线支持时）

### 9.4 v2.0 时机

- 自建 Agent Runtime（Pi Agent/LangGraph 都无法满足需求时）

## 10. 注意事项

### 10.1 不要过早优化

这些都是长期方向，不是 v1.0 的必需品。只在遇到具体问题时才应用。

### 10.2 保持架构灵活性

v1.0 的设计已经为这些优化预留了空间（接口、抽象层、插件化）。

### 10.3 渐进式演进

每次只应用一个优化，验证效果后再继续下一个。
