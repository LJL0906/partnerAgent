## 1. 文档目的

本文件回答：

```text
用户如何配置和选择模型，
Local Core 如何安全地组织一次模型调用，
模型失败时如何分类、重试和切换，
以及模型结果如何可靠地进入分析结果和确认中心？
```

本文件只定义业务边界和逻辑契约，不锁定：

- 具体模型接入框架；
- 具体供应商协议或 SDK；
- 具体数据库、加密产品或客户端框架；
- 具体提示词文本；
- 具体上下文窗口数值、超时数值和退避间隔；
- 具体结构化输出协议实现。

核心原则：

```text
本地保存完整内容
→ 组装完成当前任务所需的最小上下文
→ 外发前统一经过敏感信息处理钩子
→ 通过 Model Gateway 调用模型
→ 校验协议和结构化结果
→ 只保存分析结果和候选
→ 正式对象仍须经过用户确认
```

## 2. 关键问题与推荐答案

### 问题 1：一个模型配置至少需要哪些字段？

**推荐答案：** v1 的用户可配置模型至少包含以下四个业务字段：

```text
供应商名称
Base URL
API Key
Model ID
```

字段含义和规则：

| 字段 | 用途 | v1 规则 |
| --- | --- | --- |
| 供应商名称 | 展示、识别供应商和区分配置 | 必填；用于界面和结果展示，不等于自动路由规则 |
| Base URL | 指定供应商或兼容接口的服务地址 | 必填；保存前校验格式，实际可访问性由测试连接确认 |
| API Key | 访问模型服务的凭证 | 必填；写入本地加密安全存储，界面默认不回显，不能进入普通日志或模型上下文 |
| Model ID | 指定供应商侧可调用的模型 | 必填；连接测试和正式调用都必须使用该值 |

建议逻辑上为每份配置分配一个本地稳定的配置标识，用于列表排序、当前选择和调用关联；该标识不是用户输入，也不发送给外部模型。

配置保存和使用还必须满足：

- API Key 不能由客户端直接写入业务数据库，也不能由客户端直接发送给外部供应商；由 Local Core 接收并保存到本地安全存储。
- 界面可以提供“已配置”或部分掩码状态，但不能默认展示完整 API Key。
- Base URL、供应商名称和 Model ID 可以展示；API Key 只允许在明确编辑时重新输入或替换。
- 同一供应商可以配置多个 Model ID，也可以配置不同 Base URL；不能仅用供应商名称作为唯一键。
- v1 不要求为每个模型增加“主模型”“备用模型”固定角色；列表顺序和本次消息选择共同决定调用顺序。

### 问题 2：模型列表如何展示和排序？

**推荐答案：** 模型列表由用户手动维护顺序，当前顺序既是展示顺序，也是失败后的候选尝试顺序。

推荐展示至少包含：

```text
供应商名称
Model ID
当前是否选中
是否可用或最近一次测试状态（如果有）
```

排序规则：

1. 用户可以拖动模型配置改变顺序。
2. 新顺序持久化到本地配置，重新打开 App 后保持。
3. 系统不得因为某次调用失败、成功或自动切换而自动改动列表顺序。
4. 当前消息选中的模型先尝试；其余模型按列表顺序依次查找可尝试项。
5. 已经尝试失败的模型不再在同一次请求中重复尝试。
6. 列表顺序不代表模型能力高低，也不触发按任务类型的自动路由。
7. 删除、失效或不可用配置不应被静默替换为另一个模型；需要在设置或发送前给出明确状态。

当当前模型在列表中不是第一项时，推荐采用：

```text
本次选中的模型
→ 其他模型按列表从前到后遍历
→ 跳过已尝试模型和不符合自动切换边界的模型
```

这样既保留用户对本次消息的明确选择，也保留列表作为备用顺序的可预测性。

### 问题 3：什么是默认模型、本次模型和实际处理模型？

**推荐答案：** 必须区分三个概念，不将自动切换结果反写为用户选择：

```text
默认模型：设置中保存的长期默认模型
本次消息模型：用户发送前为当前消息选择的模型
实际处理模型：最终成功生成当前结果的模型
```

推荐行为：

- 设置中允许用户指定长期默认模型。
- 用户发送前可以临时选择其他已配置模型。
- 系统记住用户上次主动选择的模型，下次发送时优先使用该模型；如果该配置已删除、禁用或失效，不应静默选择另一个模型，应提示用户处理或重新选择。
- 本次消息选中的模型用于第一次尝试。
- 自动切换成功后，不改变长期默认模型，也不改变模型列表排序。
- 每条最终回复显示实际成功的供应商名称和 Model ID；如果发生切换，提供可展开的简要过程。
- 后台任务使用其触发时确定的模型选择规则，不得因为前台某次自动切换而永久改变设置。

一次消息默认只使用一个选中的模型完成业务处理，不按“输入分析、建议、摘要”等任务类型自动路由。失败后的其他模型仅作为受限的恢复路径。

### 问题 4：推理等级如何统一？

**推荐答案：** 对用户提供统一的四级抽象选项：

```text
关闭
低
中
高
```

推荐行为：

- 设置中保存一个默认推理等级。
- 发送前允许用户仅为当前消息临时调整等级。
- 临时选择只影响当前消息，不覆盖设置中的默认值。
- 同一消息的所有重试和自动切换请求保持相同的抽象推理等级。
- Local Core 将抽象等级交给 Model Gateway，由适配层映射为具体供应商参数。
- 某个模型不支持该等级时，不得静默降级为其他等级；应将其归类为能力或请求不匹配，并按错误边界提示用户或结束本次自动恢复。
- 推理等级不是模型列表排序依据，也不是自动路由依据。

模型不支持推理等级的处理建议为：在正式发送前由 Model Gateway 根据已知能力做预检查；能力未知时允许发起一次受控请求，但如果供应商明确返回不支持，不能换成低等级继续伪装成功。

### 问题 5：测试连接应该测试什么？

**推荐答案：** 设置中的“测试连接”只验证这份配置是否具备基本可调用性，不执行用户业务任务，也不使用个人数据、RAG 上下文或长期记忆。

至少检查：

```text
Base URL 是否可访问
API Key 是否有效
Model ID 是否可调用
返回格式是否符合接入框架要求
```

推荐测试流程：

```text
用户点击测试连接
→ 客户端提交待测试配置意图
→ Local Core 临时读取或安全保存凭证
→ 使用无个人数据的最小测试请求
→ Model Gateway 调用指定供应商和 Model ID
→ 校验协议响应、模型可用性和基础文本/结构化能力
→ 返回成功或明确失败分类
```

测试连接的边界：

- 不发送用户原始记录、个人记忆、RAG 结果、附件内容或真实业务提示词。
- 不创建原始记录、分析结果、候选项、正式对象或确认批次。
- 不把测试请求的 API Key、完整请求或完整响应写入普通调用日志。
- 测试成功只表示“当前配置可完成基础调用”，不保证该模型支持所有 v1 任务、所有输入类型或全部推理等级。
- 测试失败应明确区分地址不可达、认证失败、模型不存在、协议不兼容、能力不支持和暂时性服务错误。
- 测试请求是否产生供应商费用、使用哪个最小测试接口、是否执行结构化能力探测，仍需结合具体接入框架确定。

### 问题 6：一次业务模型请求经过哪些步骤？

**推荐答案：** 所有外部模型请求统一经过 Local Core 内的模型调用链路，不允许客户端直接调用供应商。

```text
业务任务
→ 分析编排器确定任务类型和输出模式
→ 上下文组装器选择最小必要上下文
→ 请求构造器形成逻辑请求
→ 敏感信息策略钩子识别并提醒或脱敏
→ Model Gateway 选择当前尝试的配置并调用供应商
→ 响应协议解析
→ 结构化输出校验
→ 业务字段和候选边界校验
→ 保存分析运行、分析结果和候选项
→ 返回助手回复和确认卡片数据
```

每一次尝试，包括同一模型重试和切换到其他模型，都必须重新经过敏感信息处理钩子。不得复用未经重新检查的外发请求。

一次业务请求应当保留以下逻辑上下文，但不锁定具体传输协议：

```text
任务类型
本次消息选中的模型配置
当前消息推理等级
请求内容和必要上下文
期望输出模式
上下文长度估计或限制状态
本次请求的超时和恢复预算
```

客户端只提交用户意图、当前选择和必要输入；完整上下文由 Local Core 根据本地权威数据、RAG 结果和敏感信息策略组装。外部模型只接收完成当前任务所需的最小、已处理内容。

### 问题 7：普通回复和结构化输出如何区分？

**推荐答案：** v1 至少区分“普通对话输出”和“结构化分析输出”两种逻辑模式。

#### 普通对话输出

适用于普通闲聊、一般回答或不需要正式业务候选的场景：

- 返回可展示的助手回复。
- 不强制生成目标、行动或长期记忆候选卡片。
- 如果同时发现正式变更候选，必须切换为或附带结构化分析结果。

#### 结构化分析输出

适用于输入分析、建议生成、行动结果提取、每日摘要、每周复盘和处境模型更新建议等任务。逻辑上至少能表达：

```text
摘要
事实或事实候选
问题
目标候选
行动候选
截止时间候选
现实限制候选
长期记忆候选
建议
不确定性或推测说明
```

结构化输出规则：

1. 模型输出只是分析结果、候选项、建议或待确认内容，不是已经生效的目标、行动、记忆、删除或状态变更。
2. 需要正式变更的内容必须进入候选层和确认中心；模型不能返回一个“已创建行动”并让客户端直接展示为已生效。
3. 目标、行动和记忆候选要能逐项处理，支持用户取消、修改或暂不确认。
4. 普通事实抽取可以保存为分析结果或事实记录，但必须携带来源和可信程度，不能自动升级为用户确认事实或长期记忆。
5. 结构化结果必须通过协议解析、任务格式、必填字段、状态值和来源关系校验；校验失败不得创建非法候选。
6. 模型未提供可靠来源时，Local Core 不得替模型补造内部来源；可保留为无来源的临时分析失败或要求重新处理。
7. 模型表达的猜测必须明确标记为推测或不确定，不得在结构化结果中伪装成确定事实。
8. 用户修改结构化候选后，以修改后的内容作为确认提交内容；原始输入仍保持不变。

结构化输出的具体字段名、协议格式和供应商能力映射属于技术选型和接口契约阶段，不在本文件锁定。

### 问题 8：模型返回格式错误时如何处理？

**推荐答案：** 将“协议可解析”和“业务结构有效”分成两层校验：

```text
第一层：接入协议和响应封装可解析
第二层：任务要求的结构化内容有效
```

处理规则：

- 第一层失败：本次尝试无有效模型结果，记录简要错误类别。
- 第二层失败：不保存非法候选；可以在同一模型上按一次受控重试重新请求。
- 同一模型再次返回无效结构时，是否允许切换到其他支持该任务和输出模式的模型，推荐按“模型响应无效”处理，但必须受跨供应商开关、总超时和能力校验限制。
- 如果返回内容只是普通文本，而任务必须产生结构化候选，不得把普通文本猜测性解析成正式候选；可以返回“分析未完成，请重试”的结果并保留原始记录。
- 如果只完成了不涉及正式变更的摘要或事实部分，可以按 `部分成功` 保存；不能因为部分成功就创建不完整的正式对象。
- 无论模型结果成功还是失败，原始记录都不受影响。

模型错误、结构化校验错误和用户确认失败是三个不同阶段，不能混成一个“保存失败”。

### 问题 9：上下文长度由谁负责，超限时怎么办？

**推荐答案：** 上下文长度由 Local Core 和 Model Gateway 共同负责：Local Core 负责内容优先级和裁剪，Model Gateway 负责供应商能力、窗口估计和最终发送前校验。

上下文优先级建议为：

```text
第一优先：当前用户输入、任务指令和必要输出约束
第二优先：当前有效目标、行动、截止时间和现实限制
第三优先：相关当前有效长期记忆和相关历史结果
第四优先：少量相关原始记录和 RAG 依据
第五优先：较旧的对话历史、低相关候选和可选说明
```

处理规则：

1. 发送前先估算输入内容、系统指令、结构化输出约束和预留输出空间的总长度。
2. 优先移除低相关、较旧或可选的 RAG 内容，不直接截断当前用户输入。
3. 如果需要缩短对话历史，应保留本次任务必需的信息，并在分析运行中记录发生了上下文裁剪的简要状态。
4. 不因上下文裁剪而修改或覆盖原始记录；本地原文和完整历史仍按存储规则保存。
5. 若裁剪后仍超过当前模型可用上下文，正式请求不得发送，返回明确的上下文超限结果。
6. 上下文超限默认不是跨模型自动切换理由；不同模型的上下文能力差异是否允许用户主动改用其他模型，属于显式用户选择，不得在后台静默切换。
7. 同一消息的结构化输出预算必须计入上下文边界，不能只计算输入文本。

上下文长度的具体计量方式、分词器、输入与输出预算比例、不同模型能力发现机制仍待技术选型确定。

### 问题 10：错误如何分类，哪些错误可以自动恢复？

**推荐答案：** 至少分为本地配置/校验错误、永久请求错误、暂时性调用错误、结果校验错误、敏感信息策略中断和用户主动取消六类。

| 错误类别 | 示例 | 默认处理 |
| --- | --- | --- |
| 本地配置或校验错误 | 配置缺字段、Base URL 格式错误、模型未选择、推理等级参数无法映射 | 不发送请求，提示用户修正，不自动切换 |
| 认证或权限错误 | API Key 无效、权限不足、账户不可用 | 不在同一请求中自动重试或切换，提示用户修正配置 |
| 资源或模型不存在 | Model ID 不存在、Base URL 路径不对应、模型已下线 | 不自动切换同一请求，提示用户检查配置 |
| 请求不匹配 | 输入格式不支持、输入类型不支持、推理等级不支持、结构化能力不支持 | 不静默降级；原则上不自动切换，除非用户明确选择兼容模型 |
| 上下文超限 | 当前请求超出模型可用上下文 | 先按上下文裁剪规则处理；仍超限则结束本次请求，不静默切换 |
| 内容安全拒绝 | 供应商或模型拒绝生成 | 不自动重试或切换相同请求，向用户说明需要调整内容 |
| 暂时性网络错误 | DNS/连接暂时失败、连接中断 | 可按重试预算重试 |
| 超时 | 连接、响应或模型处理超时 | 可按重试预算重试 |
| 限流 | 供应商限流、配额短时限制 | 可短暂退避后重试；受总超时限制 |
| 服务暂时不可用 | 5xx、供应商维护、临时网关错误 | 可按重试预算重试或切换候选模型 |
| 响应协议错误 | 响应封装无法解析、返回体损坏 | 同一模型最多一次受控重试，之后按结构化结果策略处理 |
| 结构化结果无效 | 缺字段、字段类型错误、候选越权、无法表达来源 | 不创建非法候选；可一次受控重试，后续是否切换按能力和预算决定 |
| 敏感信息策略中断 | 用户选择不发送、提醒模式等待处理 | 等待用户操作或取消，不自动重试 |
| 用户主动取消 | 用户取消发送或取消任务 | 立即停止后续自动重试，不切换模型 |

“可自动恢复”只表示允许在当前请求预算内执行恢复，不表示所有错误都必须重试。错误分类应同时提供用户可理解的摘要和内部稳定分类，二者都不能包含 API Key、完整上下文或不必要的敏感原文。

### 问题 11：重试和自动切换的边界是什么？

**推荐答案：** v1 采用有限、可预测、不可循环的恢复流程：

```text
本次消息选中的模型失败
→ 同一模型自动重试 1 次
→ 仍失败时按模型列表顺序尝试其他符合条件的模型
→ 每个其他模型最多尝试 1 次
→ 不循环、不重复尝试已失败模型
→ 全部失败后返回明确失败结果
```

恢复规则：

- 同一消息的推理等级在所有尝试中保持不变。
- 每次重试或切换都重新经过敏感信息策略钩子。
- 当前模型的永久错误不触发同一请求的自动切换；暂时性网络、超时、限流、临时服务不可用和临时网关错误允许恢复。
- 结构化响应无效可以触发同一模型的一次受控重试；切换到其他模型需满足输出能力、跨供应商设置和总时间预算。
- 跨供应商自动切换默认关闭，只有用户在设置中明确开启后才允许跨供应商尝试。
- 未开启跨供应商切换时，可以在同一供应商范围内尝试其他符合条件的配置；没有符合条件的模型则结束本次请求。
- 自动切换不得改变默认模型、本次消息选择记录或模型列表顺序。
- 失败模型、失败分类、尝试顺序和最终成功模型可以在当前回复中简洁展示，并支持展开查看。
- 全部失败时，原始用户记录仍保留；失败的分析运行保留失败状态；不产生正式结构化对象。

重试不是后台无限任务。客户端或 Local Core 的单次调用预算结束后，应由用户主动发起新的请求，而不是继续在后台循环调用。

### 问题 12：超时由哪一层控制？客户端超时后怎么办？

**推荐答案：** 将客户端等待、Local Core 任务和单次 Model Gateway 尝试分开，不让客户端的展示超时直接破坏本地任务状态。

推荐边界：

```text
客户端等待预算：只决定界面何时显示等待或可查询状态
Local Core 任务预算：决定本次业务任务是否继续执行
单次模型尝试超时：决定当前供应商请求何时失败并进入重试判断
总恢复预算：限制所有重试和切换的累计时间与次数
```

处理规则：

- 单次尝试必须有明确超时，不能无限等待供应商响应。
- 所有重试和切换必须受总时间、总次数和用户取消状态共同约束。
- 客户端暂时未收到响应时，优先查询 Local Core 的分析运行状态，不因为界面超时自动生成第二个业务请求。
- 用户明确取消后，不再发起新的重试或自动切换；正在进行的供应商请求尽力取消，不能保证外部服务已停止。
- 对于已经提交的确认操作，必须沿用《v1-确认中心》定义的 `confirmation_operation_id` 查询或重试规则；不能因为客户端超时生成新的确认操作。
- 对于分析任务，若本地任务仍在执行，客户端可以展示处理中；若任务已失败，展示失败分类；若已成功，返回实际模型和结果。
- 具体连接超时、读取超时、单次尝试超时、总预算和退避间隔仍待决策，不能在实现前擅自写死为产品承诺。

### 问题 13：基础模型调用日志保存什么？

**推荐答案：** v1 只保存能够解释“调用了什么模型、何时调用、服务于什么任务、是否使用个人记忆”的最小调用记录，不保存完整模型输入输出。

基础调用日志至少包含：

```text
使用的供应商名称和 Model ID
调用时间
任务类型
是否调用个人记忆
```

为支撑失败恢复和界面展示，可以在分析运行或短期运行状态中保留最小的：

```text
分析状态
最终是否成功
是否发生模型切换
实际成功模型
简要错误分类
推理等级标识（不含具体私密参数）
```

这些运行状态不等于详细调用日志。以下内容默认不得自动复制到基础调用日志：

- 完整模型输入上下文；
- 完整 RAG 召回结果；
- 完整原始模型回复；
- API Key、Authorization Header 或其他凭证；
- 本地数据库主键、文件路径和内部字段名；
- 未经必要处理的敏感原文。

日志和分析运行记录中的错误摘要应经过脱敏和长度限制。基础日志保存周期、是否支持用户清理和本地数据库层的额外加密仍待《v1-数据导出》或安全子需求进一步确定。

### 问题 14：客户端、Local Core 和 Model Gateway 的边界是什么？

**推荐答案：** v1 将 Model Gateway 视为 Local Core 内的逻辑模块，不提前拆成独立微服务。三者职责如下。

| 层 | 负责 | 不负责 |
| --- | --- | --- |
| 客户端 | 模型配置界面、模型列表展示和拖动排序、当前模型选择、推理等级选择、测试连接入口、等待/失败/切换结果展示 | 直接调用外部模型、保存业务数据库、读取完整 RAG 上下文、执行敏感信息判断、创建正式对象、改变模型列表顺序 |
| Local Core | 保存和校验模型配置、保护 API Key、记忆默认/本次选择、编排业务任务、读取本地数据和 RAG、组装最小上下文、调用敏感信息钩子、控制重试和切换、保存分析结果和基础运行记录 | 不把候选直接视为正式对象，不绕过用户确认，不向客户端暴露凭证，不把供应商协议细节交给客户端处理 |
| Model Gateway | 统一调用入口、供应商适配、请求协议转换、推理等级参数映射、能力和上下文限制检查、超时控制、响应归一化、供应商错误分类 | 不决定产品业务任务、不直接读写业务库、不直接创建候选或正式对象、不绕过敏感信息钩子、不自行改变模型列表顺序 |

调用边界：

```text
客户端
→ Local Core 逻辑接口
→ 业务编排与上下文组装
→ 敏感信息策略钩子
→ Model Gateway
→ 外部模型供应商
```

进一步约束：

- 客户端提交的是配置意图、模型选择、推理等级和用户输入，不是可直接执行的供应商请求。
- Local Core 是业务权威边界；客户端和 Model Gateway 都不能直接写入目标、行动、记忆、确认批次或索引。
- Model Gateway 可以返回统一的响应和错误分类，但正式候选由 Local Core 的结果校验器生成和保存。
- 外部模型永远不应收到 API Key、本地内部 ID、本地文件路径、数据库字段名或超出任务需要的完整个人数据。
- 电脑端可以将 Model Gateway 与 Local Core 放在同一本地核心进程或同一套本地模块中；手机端可以采用嵌入式运行时。部署形态不改变上述逻辑边界。

## 3. 已确认边界与待决策项

### 3.1 已确认边界与本轮采用的详细规则

以下列表中，明确来自上游需求与架构文档的内容属于已确认约束；其中关于推理等级名称、单模型重试次数、错误恢复范围和跨供应商切换的具体规则，属于本轮按推荐方案收口的详细技术规则。两类内容均作为当前 v1 文档基线使用，但不得倒置为“原始产品需求早已确认”。

1. v1 可以配置多个模型，每份配置使用供应商名称、Base URL、API Key 和 Model ID。
2. API Key 保存在本地加密安全存储中，不能进入普通调用日志。
3. 模型列表由用户手动排序，列表当前顺序决定失败后的候选顺序；系统不因调用结果自动改序。
4. 用户可以在发送消息前选择模型，系统记住上次主动选择的模型。
5. 默认模型、本次消息模型和实际处理模型必须区分。
6. 单次消息默认使用发送时选中的一个模型，不按任务类型自动路由。
7. 推理等级支持设置默认值与当前消息临时调整；本轮采用“关闭、低、中、高”作为内部展示名称，供应商映射仍由适配层实现。
8. 当前消息选定的推理等级在重试和自动切换中保持一致；模型不支持时不得静默降级。
9. 设置中提供测试连接；至少检查地址、凭证、Model ID 和接入框架返回格式。
10. 所有模型请求，包括 RAG、后台任务和重试请求，都必须在发出前经过敏感信息处理钩子。
11. 模型只能产生分析结果、候选项、建议和待确认内容，不能直接创建或修改正式对象。
12. 本轮采用：当前模型失败后，同一模型自动重试 1 次，再按列表顺序尝试其他模型；不循环、不重复尝试已失败模型。
13. 本轮采用：网络暂时不可用、超时、限流、服务暂时不可用和临时网关错误属于默认可自动恢复的暂时性错误。
14. 本轮采用：API Key 无效、权限错误、Model ID 不存在、输入或能力不支持、上下文超限、内容安全拒绝和用户主动取消，默认不触发同一请求的自动切换。
15. 本轮采用：跨供应商自动切换默认关闭，需要用户在设置中明确开启。
16. 每条回复显示实际成功的供应商和 Model ID；自动切换不改变默认模型和列表顺序。
17. v1 只保留基础模型调用记录，不保存完整模型输入上下文、完整 RAG 结果和模型原始回复作为详细调用日志。
18. 客户端不直接访问外部模型或业务数据库；正式写入和状态变更由 Local Core 负责。
19. Model Gateway 是 Local Core 内的统一模型调用逻辑边界，不因 v1 架构而引入微服务。
20. 模型失败不影响原始记录保存；只有结构化结果有效且用户确认后，才进入正式目标、行动或记忆。

### 3.2 仍待决策项

以下内容尚未通过本轮详细规则收口，不能冒充为已确认产品决策：

- 具体模型接入框架、协议兼容范围和供应商适配方式。

- 测试连接具体调用哪个接口、是否产生费用、是否执行结构化能力探测及探测结果保存方式。

- 供应商返回错误到内部稳定错误分类的完整编码表。

## 4. 验收标准

### 4.1 配置和列表

- 可以创建、编辑和删除多份模型配置，核心字段包括供应商名称、Base URL、API Key 和 Model ID。
- API Key 在本地安全存储中保存，界面默认不显示完整值，基础调用日志和错误摘要中不存在 API Key 或凭证头。
- 模型列表显示供应商名称和 Model ID，并支持手动拖动排序。
- 重新打开设置后，用户保存的列表顺序仍然存在。
- 一次调用失败不会自动改变列表顺序，也不会把备用模型永久写成默认模型。
- 当前模型不在列表第一项时，第一次仍使用用户本次选择的模型，后续候选才按列表顺序处理。

### 4.2 选择和推理等级

- 设置中可以保存默认模型和默认推理等级。
- 发送前可以临时选择模型和推理等级，临时值只影响当前消息。
- 系统会记住用户上次主动选择的模型；配置不可用时会明确提示，不静默替换。
- 推理等级只展示“关闭、低、中、高”四个统一选项。
- 当前消息的推理等级在同一消息的重试和自动切换中保持一致。
- 目标模型不支持当前推理等级时，不会静默改用其他等级继续返回成功。

### 4.3 测试连接

- 测试连接至少能区分地址不可达、认证失败、Model ID 不存在、协议格式错误和暂时性服务错误。
- 测试连接不发送个人原始记录、RAG 结果、长期记忆、附件内容或业务上下文。
- 测试连接不会创建分析结果、候选项、正式对象或确认批次。
- 测试结果能够说明“配置可调用”与“完整 v1 任务能力已验证”之间的区别。

### 4.4 请求和结构化输出

- 客户端不能直接向供应商发请求；正式请求统一经 Local Core 和 Model Gateway。
- 当前输入、RAG、记忆、后台任务和每次重试在外发前都会经过敏感信息处理钩子。
- 普通回复不会无条件生成确认卡片；识别到正式业务候选时，结构化结果能逐项表达候选。
- 无效协议响应、缺字段、类型错误、越权写入意图或无法追溯来源的结果不会创建非法候选。
- 模型输出不能直接使目标、行动、记忆、删除或状态变更生效。
- 原始记录始终保留，模型失败或结构化校验失败不会删除或覆盖原始内容。

### 4.5 上下文长度

- 发送前会检查输入、指令、结构化输出要求和输出预留空间的总长度。
- 上下文不足时优先减少低相关或较旧的 RAG/历史内容，不静默截断当前用户输入。
- 裁剪后的请求不会改写本地原始记录，并能在分析运行状态中表达发生过上下文裁剪。
- 裁剪后仍超限时，系统明确返回上下文超限，不发送超出模型能力的请求。
- 上下文超限不会在后台静默切换到另一个模型。

### 4.6 错误、重试和自动切换

- 暂时性网络错误、超时、限流、服务暂时不可用和临时网关错误可以进入有限恢复流程。
- 当前模型失败后最多同模型重试 1 次；其他符合条件的模型每个最多尝试 1 次。
- 同一请求不会循环，也不会重复尝试已经失败的模型。
- API Key 无效、权限错误、Model ID 不存在、能力不支持、上下文超限、内容安全拒绝和用户取消不会触发默认跨模型自动恢复。
- 跨供应商自动切换只有在用户设置中明确开启后才发生。
- 用户取消后不再发起后续重试或切换。
- 最终结果显示实际成功的供应商和 Model ID，并能查看简要失败分类和尝试过程。
- 全部失败时不产生正式对象，但保留原始记录和可追溯的失败状态。

### 4.7 基础调用日志

- 最小调用日志至少记录使用的供应商和 Model ID、调用时间、任务类型、是否调用个人记忆。
- 为解释本次结果而保留的分析运行状态不包含完整请求、完整 RAG 上下文或完整原始输出。
- 日志错误摘要经过脱敏和长度限制，不暴露 API Key、本地路径、内部数据库字段名或不必要敏感原文。

### 4.8 三层职责边界

- 客户端只负责配置和选择界面、用户输入、结果展示及状态查询，不直接访问模型或数据库。
- Local Core 负责配置安全、上下文组装、敏感信息处理、调用编排、重试切换、结果校验、候选保存和基础运行记录。
- Model Gateway 负责供应商协议适配、参数映射、能力检查、超时控制、响应归一化和错误分类，不直接写业务对象。
- 任何正式目标、行动、记忆、决策、删除或状态变更都必须继续经过确认中心和 Local Core。
- Model Gateway 不得绕过敏感信息处理钩子，客户端不得绕过 Local Core。
